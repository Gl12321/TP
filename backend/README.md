# Бэкенд «Разбора»

Бэкенд превращает работу с цифрами в общий процесс команды. Он определяет, какие данные доступны сотруднику, получает расчёт, сохраняет его основание и связывает результат с отчётом или разбором. Руководитель видит отклонение, адресует вопрос управляющему и фиксирует решение; аналитик задаёт смысл показателей; администратор обслуживает подключения. Эти действия сохраняются в БД и продолжают работать независимо от открытой вкладки.

Нейросеть участвует только в построении нового SQL по вопросу. Обзор, планы, доступ, отчёты, обсуждения и повторное измерение написаны обычным Python-кодом. API обслуживает интерфейс, отдельный worker выполняет долговечные задания и использует библиотеку [sql_agent](../packages/sql_agent/README.md).

## Как устроена часть приложения

```text
backend/
  app/
    main.py          сборка FastAPI и раздача интерфейса
    worker.py        последовательное выполнение SQL-заданий
    bootstrap.py     миграции и восстановление состояния после бэкапа
    access/          аккаунты, пространства, роли и область точек
    sources/         подключения, разрешённые данные и технические обращения
    analytics/       точки, показатели, планы, обзор и отчёты
    assistant/       личные диалоги и адаптация библиотеки SQL-агента
    collaboration/   разборы, измерения, адресные вопросы и уведомления
    jobs/            очередь, аренда и публикация результата
    infrastructure/  транзакции, конфигурация, HTTP и секреты
  migrations/        последовательные изменения прикладной БД
  tests/             проверки серверных сценариев и границ доступа
```

Внутри предметного модуля `api/` содержит HTTP-маршруты и входные схемы, `models.py` — хранимые сущности, `service.py` — общие правила и вычисления. Крупный самостоятельный сценарий получает отдельный файл. Дополнительная директория нужна, когда у неё есть собственная ответственность, а не для обёртки над одной функцией.

[Прикладная БД](migrations/README.md) хранит пользователей, настройки, версии показателей, историю вопросов и результаты. Подключённая PostgreSQL клиента хранит исходные бизнес-данные. Приложение читает её через отдельную роль и не создаёт в ней служебные таблицы или пользователей.

## Основные правила

- Доступ складывается из возможностей роли, области точек и списка читателей профиля источника. Сохранение результата не отменяет последующую проверку этих прав.
- Вопрос создаёт сообщение, запуск и задание одной транзакцией. Повтор с тем же ключом возвращает тот же запуск; изменение диалога из другой вкладки обнаруживается по версии.
- Worker повторно проверяет доступ перед исполнением и публикацией. Отмена, потеря аренды и отзыв прав не допускают позднего сохранения успешного ответа.
- Результат содержит таблицу, SQL расчёта и фактически исполненный SQL с параметрами ограничения области. Денежные значения передаются строками, чтобы браузер не терял точность.
- Определения показателей, планы и измерения версионируются. Обновление отчёта добавляет попытку в историю, сохраняя исходный результат.
- Техническое обращение направляется администратору источника без автоматического прикрепления финансового результата.

Пути данных и обязанности модулей разобраны в [app/README.md](app/README.md), HTTP-контракт — в [API.md](API.md). Возможности пользователя собраны в [описании продукта](../docs/PRODUCT.md).

## Разработка и запуск

Для разработки нужны Python 3.11+, зависимости из [requirements.txt](requirements.txt), базовый пакет `sql_agent` и прикладная БД. Рабочая конфигурация использует PostgreSQL; SQLite предназначена для локальных прикладных проверок. API не требует весов модели, но реальному worker нужны дополнительные зависимости и подготовленные модели.

Подготовка окружения, точки входа, правила изменения моделей и маршрутов находятся в [руководстве по бэкенду](../docs/development/backend.md). Общий запуск и ожидаемое состояние системы описаны в [эксплуатации](../docs/operations/README.md), контейнеры — в [Docker](../docs/operations/docker.md), выбор проверок — в [tests/README.md](tests/README.md).

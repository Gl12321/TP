# Приложение «Разбор»

Бэкенд связывает вопрос к данным с готовой таблицей и дальнейшей работой команды. Руководитель сохраняет расчёт, назначает вопрос управляющему точки, получает пояснение и фиксирует итог. Аналитик определяет, как считаются показатели; администратор подключает источники и участников. Один и тот же результат доступен только людям, которым разрешена вся его область.

Это самостоятельная часть SaaS: вход, пространства, роли, планы, отчёты и обсуждения работают обычным Python-кодом. Нейросеть нужна только при создании нового SQL-вопроса. API не загружает её веса и продолжает обслуживать страницы, пока отдельный worker строит запрос.

## Как связаны части

`FastAPI → предметные модули → PostgreSQL приложения` обслуживает действия пользователя. В этой БД хранятся участники, назначения, определения показателей, редакции планов, диалоги, задания и результаты. Внешний PostgreSQL клиента подключается отдельно: приложение читает согласованные таблицы, не создаёт в источнике пользователей или служебные таблицы.

[worker.py](app/worker.py) забирает сохранённое задание и вызывает [самостоятельный sql_agent](../packages/sql_agent/README.md). Пакет получает разрешённый каталог, определения показателей, выбранный контекст и интерфейс чтения. Обработчик сохраняет результат только после повторной проверки доступа и действующей аренды задания. Закрытие браузера не отменяет вычисление.

## Доступ и достоверность

Роль определяет действия, область — доступные точки. Администратор может обслуживать подключения без права читать финансовые данные. SQL проходит проверку грамматики и AST, затем каждая исходная таблица заменяется разрешённой проекцией полей и строк с параметризованным фильтром по внешним кодам точек. Условие `OR` в пользовательском SQL не снимает этот фильтр. Общие справочники разрешаются отдельно и явно. Дополнительно используется роль PostgreSQL без записи и транзакция `READ ONLY`.

Политика доступа отделена от версии метаданных. Обычное обновление каталога не уничтожает доступ к прежним снимкам результатов. Изменение политики, отключение источника или сужение области участника заново ограничивает чтение истории. Активное задание при изменении каталога прекращается: его запрос нельзя молча выполнить на другой структуре.

Обзор использует заданное аналитиком поле даты, ключ точки и операцию `sum`, `count` или `avg`. Полные месяцы сравниваются с предыдущими календарными месяцами, произвольные диапазоны — с предшествующими диапазонами той же длительности в днях. Сравнение рассчитывается по одинаковому составу точек; средние агрегируются с весами. Отсутствие строк отличается от нуля. Наличие строк не подтверждает полноту выгрузки, поэтому интерфейс показывает это ограничение. План за неполный месяц не распределяется по дням автоматически. Финансовая трактовка показателя остаётся явным определением, которое нужно сверить с учётной системой.

## Запуск и эксплуатация

Для обычного запуска используйте [общий запуск проекта](../README_RU.md). Для отдельной разработки бэкенда нужны Python 3.11+, PostgreSQL приложения и установленный пакет `sql_agent`; SQLite поддерживается для локальной проверки прикладных сценариев и не заменяет PostgreSQL аналитического источника.

```text
python -m pip install -r backend/requirements.txt
python -m pip install ./packages/sql_agent
python -m backend.app.bootstrap migrate
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Миграции применяются отдельной командой до API и worker. Входные переменные: `APP_DATABASE_URL`, `APP_SECRET_KEY`, `APP_BOOTSTRAP_TOKEN`; секреты не помещаются в YAML. `APP_SECURE_COOKIES=false` допускает локальный HTTP; для публичного сервиса нужен HTTPS и secure-cookie. Адреса разрешённых источников, origins и лимиты читаются из [config.yaml](../config.yaml), переменные `APP_*` могут их переопределить. Пустой список разрешённых адресов запрещает подключение к внешним БД.

После подготовки локальных моделей worker запускается `python -m backend.app.worker`. Команда `python -m backend.app.worker --healthcheck` проверяет свежую запись готовности в БД, не загружая веса. `/health` показывает жизнь API и доступность исполнителя; `/ready` проверяет прикладную схему БД. Недоступный worker блокирует новую отправку вопроса с понятной причиной, сохраняя доступ к истории и обсуждениям.

Собранный [фронтенд](../frontend/README.md) раздаётся из `frontend/dist` либо `APP_FRONTEND_DIST` с того же origin. Интерактивная спецификация `/api/docs` использует Swagger UI с CDN; JSON-схема `/api/openapi.json` доступна без CDN. Встроенного почтового транспорта нет: одноразовое приглашение копируется и передаётся адресату через выбранный организацией канал.

Проверки описаны в [tests](tests/README.md). Тесты HTTP и состояния заданий не оценивают качество реальной LLM; для этого нужен отдельный прогон выбранного GGUF на контрольных вопросах и измерение памяти всего процесса.

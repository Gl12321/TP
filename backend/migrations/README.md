# Изменения прикладной БД

Миграции переводят существующее пространство на новую структуру, сохраняя пользователей, результаты и обсуждения. Они относятся к БД приложения. Структура подключённой PostgreSQL клиента ими не меняется.

## Как устроено

Alembic применяет линейную цепочку из `versions/`. [env.py](env.py) загружает ORM-метаданные для сравнения схем и выполняет миграции через асинхронный драйвер. Команда [bootstrap](../app/bootstrap.py) передаёт URL из настроек, а не из сохранённого пароля в `alembic.ini`.

| Ревизия | Изменение |
| --- | --- |
| [0001_workspace](versions/0001_workspace.py) | Исходная схема приложения |
| [0002_workspace_references](versions/0002_workspace_references.py) | Составные ограничения принадлежности объектов одному пространству |
| [0003_measurements](versions/0003_measurements.py) | Неизменяемые измерения разборов и ключ повтора |
| [0004_source_readers](versions/0004_source_readers.py) | Явный список читателей профиля источника |
| [0005_source_issues](versions/0005_source_issues.py) | Технические обращения, комментарии и вторая цель уведомления |
| [0006_creation_requests](versions/0006_creation_requests.py) | Ключи создания и отпечатки запросов отчётов, разборов и обращений |

Уведомление имеет ровно одну цель: разбор или техническое обращение. Составные внешние ключи связывают автора, адресата, источник и объект с одним пространством. `creation_requests` добавляет защиту повтора без изменения ранее сохранённых объектов.

## Применение

Из корня проекта с заданным `APP_DATABASE_URL`:

```text
python -m backend.app.bootstrap migrate
```

Команда применяет все ревизии до `head`. Прямой Python-запуск не читает `.env` автоматически: переменные должны быть в окружении процесса. Общий запуск выполняет миграцию отдельно до API и worker. В продакшене этот шаг выполняется один раз для поставляемой версии; каждый HTTP-процесс не должен конкурировать за изменение схемы.

## Добавление ревизии

1. Изменить ORM-модель и создать новый файл с `revision`, `down_revision`, `upgrade` и `downgrade`. Применённые файлы не переписывать.
2. Явно определить перенос существующих данных, значение новых полей и ограничения. Изменение бизнес-истории нельзя сводить к удалению и повторному созданию таблицы.
3. Проверить обновление заполненной БД и соответствие конечной схемы ORM. Ограничения, использующие SQL-диалект, проверить на PostgreSQL.
4. Перед поставкой сохранить БД и ключ источников по [руководству резервного копирования](../../docs/operations/backup.md). Откат схемы, удаляющий данные, не заменяет восстановление бэкапа.

`Base.metadata.create_all()` допустим в изолированных тестах, но не обновляет существующую схему и не заменяет Alembic. Команда `restore-state` также не является миграцией: после восстановления она отзывает сессии, очищает heartbeat и завершает оставшиеся активными задания.

Проверки находятся в [tests](../tests/README.md), правила изменения модели и API — в [руководстве бэкенда](../../docs/development/backend.md), поставка — в [Docker](../../docs/operations/docker.md).

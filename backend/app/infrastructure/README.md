# Общие механизмы приложения

Предметные модули должны одинаково сохранять изменения, защищать секреты и возвращать ошибки. Эта директория содержит такие механизмы без понятий выручки, плана или управляющего точки. Она не вводит универсальную обёртку над каждой бизнес-операцией.

## Как устроено

| Файл | Что обеспечивает |
| --- | --- |
| [database.py](database.py) | Асинхронный SQLAlchemy engine, общая модель, идентификаторы, транзакция запроса |
| [config.py](config.py) | Несекретные настройки YAML и явные переменные окружения |
| [security.py](security.py) | scrypt, хеши токенов, CSRF и шифрование паролей источников |
| [schemas.py](schemas.py) | Базовые правила входных моделей |
| [http.py](http.py) | Предел фактического тела запроса |
| [errors.py](errors.py) | Публичная прикладная ошибка |
| [pagination.py](pagination.py) | Страницы истории, буквальный поиск и защищённый курсор |
| [idempotency.py](idempotency.py) | Атомарная защита создания объектов от дублей |

## Транзакции и данные

`get_db` фиксирует успешную операцию и откатывает исключение. Изменяющий запрос с известным участником добавляет запись аудита. HTTP-зависимость настроена на завершение до начала ответа: cookie не должна уйти браузеру до сохранения сессии. Для фоновой работы используются отдельные короткие транзакции.

SQLite включает внешние ключи, WAL и ожидание блокировки для локальных проверок. Рабочий сервис использует PostgreSQL. API не создаёт таблицы при старте: прикладная схема обновляется через [миграции](../../migrations/README.md).

Ключ идемпотентности создания уникален для пространства и автора. Отпечаток тела и операция запрещают повтор с другим содержимым. Резервирование и объект находятся в одной транзакции; после отката ключ свободен. Сам объект при повторе проверяется сервисом его предметного модуля.

## HTTP и секреты

Входные модели отклоняют неизвестные поля и очищают внешние пробелы строк. Пароли с значимыми пробелами переопределяют это правило. Предел тела — два МиБ, включая chunked-передачу; проверка происходит до разбора JSON.

`APP_SECRET_KEY` используется для защиты секретов источников и других подписанных данных. Его потеря делает сохранённые подключения нечитаемыми, поэтому [бэкап](../../../docs/operations/backup.md) должен сохранять и БД, и ключ. Это не пароль роли внешней PostgreSQL. Логи и публичная ошибка не должны раскрывать ни один из них.

Пагинация использует пару времени и id, ограничивает объём просмотра и шифрует курсор с привязкой к пользователю и условиям. Предметный модуль проверяет каждую запись; продвижение через недоступные объекты сохраняет достижимость старой разрешённой истории.

## Связи и изменение механизмов

[main.py](../main.py) собирает механизмы в API; [worker.py](../worker.py) использует ту же конфигурацию и БД отдельно от HTTP. Схемы конкретных операций остаются в `api/` соответствующего предметного модуля.

При изменении общего механизма следует проверять всех его потребителей: например, пагинацию используют четыре списка, а идемпотентное создание — три операции. Договор HTTP находится в [API](../../API.md), настройка окружения — в [конфигурации](../../../docs/operations/configuration.md), порядок разработки — в [руководстве бэкенда](../../../docs/development/backend.md).

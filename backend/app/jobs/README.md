# Долговечные задания

Длительный вопрос продолжает выполняться после закрытия вкладки и получает один определённый результат. Для этого API сохраняет задание в БД, а отдельный worker забирает его из очереди. Состояние не зависит от памяти HTTP-процесса.

## Как устроено

[models.py](models.py) содержит `Job`, последовательные `RunEvent` и `WorkerHeartbeat`. [service.py](service.py) управляет захватом, продлением аренды и завершением. [worker.py](../worker.py) загружает модели один раз, последовательно исполняет задания и передаёт библиотеке сигнал отмены.

PostgreSQL выдаёт самое старое доступное задание через `FOR UPDATE SKIP LOCKED`. Каждый захват получает случайный токен и срок аренды. Продление и публикация проверяют оба условия; старый процесс не может записать результат после утраты права на задание.

## Состояния и сбои

Очередь использует состояния `queued`, `running`, `cancel_requested`. Завершение — `succeeded`, `failed`, `cancelled`, `needs_input` или `rejected`. Поле `stage` уточняет текущий этап, но не заменяет состояние.

Отмена задания в очереди завершается сразу. Выполняющееся задание остаётся в `cancel_requested` до фактической остановки; поздний успешный результат не заменяет отмену. Просроченная аренда обнаруживается при следующем проходе очереди: потерянное выполнение становится `failed` с кодом `worker_lost`, запрос на отмену — `cancelled`. Автоматического повторного тяжёлого расчёта нет.

Перед публикацией блокируются и повторно проверяются членство, пользователь, источник и активные точки. Ревизия назначения, версия каталога и политика должны соответствовать запуску. Отзыв доступа возвращает конечное состояние без финансовой таблицы.

## Ресурсы и наблюдение

Один диалог допускает одно активное задание. Дополнительно действуют квоты приложения, пространства и пользователя из [конфигурации](../../../docs/operations/configuration.md). PostgreSQL advisory lock допускает один модельный worker на прикладную БД; масштабирование контейнера не создаёт параллельную генерацию автоматически.

Heartbeat свежестью до 30 секунд сообщает готовность. Отсутствие worker блокирует новые вопросы, сохраняя доступ к истории и обсуждениям. SSE читает события из БД, а актуальный GET запуска остаётся источником состояния. Логи и порядок перезапуска описаны в [эксплуатации](../../../docs/operations/README.md).

[Ассистент](../assistant/README.md) создаёт задания, [источник](../sources/README.md) исполняет SQL в разрешённой области, [библиотека агента](../../../packages/sql_agent/README.md) генерирует запрос и сообщает этапы.

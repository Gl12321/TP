# Задание переживает закрытие страницы

Длительный вопрос должен продолжать выполняться после закрытия вкладки и возвращать один определённый результат. Поэтому браузер создаёт запись задания, а отдельный worker забирает её из БД. Состояние не хранится только в памяти HTTP-процесса.

[service.py](service.py) управляет очередью, арендой и завершением. У каждого захвата есть случайный токен и срок. PostgreSQL выдаёт записи через `FOR UPDATE SKIP LOCKED`; просроченный исполнитель не может продлить аренду или опубликовать ответ. После потери worker задание становится ошибкой с предложением повторной отправки, без скрытого повторения тяжёлого расчёта.

[worker.py](../worker.py) загружает модели один раз и обрабатывает запросы последовательно. Монитор продлевает аренду, сохраняет этапы и передаёт сигнал отмены. Отмена очереди завершается сразу; активная работа остаётся в `cancel_requested` до фактической остановки. Поздний успешный ответ не заменяет отменённый результат.

Перед публикацией блокируются и проверяются актуальные членство, источник и область точек. Отдельный токен аренды защищает от устаревшего процесса. PostgreSQL дополнительно допускает один модельный worker на прикладную БД через advisory lock; локальные SQLite-тесты запускают одного исполнителя явно.

Свежий heartbeat позволяет [API](../main.py) различать готовый интерфейс и готовую генерацию. SSE читает сохранённые события, но источником истины остаётся GET запуска. Тестовый исполнитель подставляется только в проверках; рабочий процесс использует реальный пакет SQL-агента.

# Интерфейс вопросов к данным

Здесь пользователь загружает SQLite-базу, выбирает данные и описывает нужную выборку обычными словами. В ответ он получает готовую таблицу и SQL, по которому она рассчитана. Пока приложение работает, интерфейс показывает текущий этап и позволяет отменить вопрос.

Выбор данных и получение ответа находятся в одном окне: пользователю не нужно отдельно вызывать API или подключаться к PostgreSQL. При этом интерфейс не принимает решений о допустимости SQL — это задача серверной части.

## Как устроена работа

[app.py](app.py) отвечает за экран Streamlit и состояние браузерной сессии. В боковой панели находятся подключение, выбор схем и операции с данными. Основная область принимает вопрос и показывает последний результат. [client.py](client.py) обращается к [API](../src/api/README.md), отправляет файлы и читает поток событий в отдельном потоке Python; он не зависит от Streamlit.

Список схем приходит из `/schema_show`. Схема с неактуальным поисковым индексом недоступна для вопросов до переиндексации. После загрузки, переиндексации и удаления список перечитывается даже при ошибке операции. Если получить новый список не удалось, старый убирается из выбора, а пользователь видит обе причины ошибки.

Выбранные схемы, токен и ответ хранятся только в текущей сессии. Смена адреса API или токена очищает данные прежнего подключения. Во время вопроса изменение подключения и операций со схемами заблокировано.

Например, пользователь загружает базу заказов, выбирает её схему и пишет: «Покажи десять покупателей с самой большой суммой заказов». После выполнения он видит строки с покупателями и суммами. Если вопрос требует уточнить, что считать заказом или оплатой, вместо пустой таблицы интерфейс должен показать причину отказа; пустая выборка означает другое — запрос выполнен, но подходящих строк нет.

Основным ответом остаётся таблица. Под ней находится закрытый по умолчанию блок «SQL этого результата»: его можно раскрыть, изучить запрос с подсветкой синтаксиса и скопировать штатной кнопкой блока кода. SQL не занимает место перед результатом. Если выполнение не завершилось успешно, диагностический блок называется «Последний сформированный SQL» и явно не подтверждает успешное выполнение. При отказе без SQL такой блок не появляется.

Интерфейс не пересчитывает суммы и не исправляет запрос по собственным правилам: он сохраняет результат серверной обработки и делает его доступным для просмотра. Поэтому отображаемый SQL соответствует тому же ответу API, что и таблица, а не отдельно сгенерированному объяснению.

## Вопрос, прогресс и отмена

Объект задания хранится в `session_state`, поэтому обычное обновление скрипта Streamlit не отправляет вопрос повторно. Клиент читает `accepted`, `stage`, `heartbeat`, `result` и `error`, проверяя общий `request_id`. Фрагмент интерфейса обновляет прогресс каждые 0,5 секунды. После завершения один полный rerun включает элементы управления и прекращает периодическое обновление.

Кнопка отмены отправляет отдельный запрос `/queries/{request_id}/cancel`. Подтверждённая отмена останавливает чтение, а соединение закрывает сам читающий поток. Если сервер отвечает 404, вопрос уже мог закончиться: клиент дочитывает поток и сохраняет готовый ответ. Отсутствие конечного ответа считается ошибкой связи.

При пропавших heartbeat действует сетевой таймаут 15 секунд. Если браузерная сессия не обновляет задание 45 секунд, служебный поток запрашивает отмену; максимальное время задания — 30 минут. Освобождение серверных ресурсов может завершиться позже закрытия потока интерфейса.

## Как показываются данные

Таблица, пустая выборка, отказ генератора и техническая ошибка отображаются раздельно. Усечённый результат получает явное уведомление. Decimal и даты сохраняют представление API; одинаковые названия колонок получают номера только на экране.

Сессия хранит последний вопрос, последние 60 сообщений этапов и один конечный ответ. Heartbeat не заполняют историю, а результат не вытесняется прогрессом. Размер события ограничен 16 МиБ, сообщение этапа — 1000 символами; таблица в интерфейсе — 10 000 строками. Серверные ограничения обычно срабатывают раньше.

Хранение одного задания связано с текущим сценарием последовательных вопросов. Повторное отображение страницы читает уже существующее состояние, а отправка нового вопроса создаёт новое задание. Это не постоянный журнал запросов: история между сессиями отдельно не сохраняется.

SQLite передаётся в API по частям без второй полной копии multipart. Однако Streamlit [хранит выбранные файлы в RAM](https://docs.streamlit.io/knowledge-base/using-streamlit/where-file-uploader-store-when-deleted) ещё до отправки, поэтому большие базы лучше выбирать по одной. Лимит загрузки показывается перед импортом. Удаление всех схем требует отдельного подтверждения и затрагивает также схемы, созданные вне приложения; после операции подтверждение сбрасывается.

## Подключение и проверки

[Общий запуск](../README_RU.md) подготавливает API и интерфейс. `API_URL` задаёт адрес сервера, `API_TOKEN` — токен из окружения; вручную введённый токен заменяет его только в текущей сессии. Токен окружения не подставляется в браузерное поле.

Интерфейс использует публичный `st.fragment`; рабочая версия Streamlit закреплена в [requirements.txt](requirements.txt). [test_client.py](test_client.py) проверяет протокол, ограничения, multipart и отмену с подставным HTTP-транспортом. [test_app.py](test_app.py) запускает настоящий экран через Streamlit AppTest с подменённым API: проверяет порядок таблицы и SQL, свёрнутое состояние запроса, пустую выдачу и ошибки. Браузер и модели для этих проверок не нужны.

Разделение экрана и HTTP-клиента позволяет проверить сложные ситуации без браузера: ответ разбит посреди UTF-8-символа, отмена пришла одновременно с результатом или поток закончился без конечного события. AppTest подтверждает структуру элементов и их состояние, но не оценивает визуальное оформление, работу буфера обмена и полный путь от импорта до настоящего ответа модели. Для этого нужен отдельный прогон в браузере с работающим API.

# Рабочие файлы данных

Здесь приложение хранит промежуточные файлы импорта и поисковый индекс структуры базы. Основные таблицы с данными находятся в PostgreSQL. Такое разделение позволяет перестраивать поиск, не импортируя заново уже загруженные строки.

## Что хранится

Каталог временных SQLite-загрузок используется [API импорта](../src/api/routes/schemas.py). Загруженный файл получает случайное внутреннее имя, обрабатывается и удаляется. Имя исходного файла задаёт целевую схему PostgreSQL; временное имя на диске к ней не привязано.

Каталог Chroma содержит [поисковые описания таблиц](../src/rag/indexing/README.md). Рядом хранится `index-state-*.json` с перечнем неактуальных схем и состоянием прерванной очистки. Это позволяет после перезапуска обнаружить незавершённое обновление и не использовать старую структуру для нового SQL.

Здесь важно различать сами данные и способ их поиска. В PostgreSQL находятся строки заказов, клиентов или других импортированных таблиц. В индексе находятся сведения о том, какие таблицы существуют и чем они могут быть полезны для вопроса. Потеря индекса требует его восстановления, но не означает исчезновение строк из PostgreSQL.

Пути задаются [общей конфигурацией](../config.yaml). Порядок запуска и расположение сохраняемых данных описаны в [корневом руководстве](../README_RU.md).

## Жизненный цикл загрузки

Например, при импорте `sales.sqlite` API создаёт временный файл со случайным именем. [Импортёр](../src/database/migration/README.md) читает его и записывает таблицы в схему `sales` одной транзакцией. Затем каталог получает актуальную структуру новой схемы, после чего исходный временный файл удаляется.

Случайное имя файла отделяет пользовательское название от пути на диске. Оно также позволяет обрабатывать повторные загрузки без предположения, что файл с таким именем принадлежит именно текущему запросу. Целевая схема передаётся импортёру отдельным параметром.

Рабочий каталог не является архивом исходных SQLite-файлов. Если важно сохранить оригинал загрузки, он должен оставаться у пользователя отдельно: приложение использует временную копию только для переноса.

## Восстановление

Для исправления неактуального индекса используется переиндексация через интерфейс или API. Удаление файла состояния вручную скрывает признак сбоя, но не восстанавливает каталог.

Перестроение индекса сохраняет таблицы PostgreSQL. Удаление всех пользовательских схем — отдельная операция интерфейса; она удаляет сами данные, а не только поисковые файлы.

Например, после смены embedder прежние векторы больше не подходят новому поиску. Данные в БД могут оставаться полностью исправными: нужно заново прочитать структуру и построить её представления новой моделью. Для этого не требуется повторно загружать исходные SQLite-файлы.

Если импорт был прерван, сначала учитывается состояние транзакции PostgreSQL и отметка актуальности индекса. Наличие части файлов Chroma само по себе не подтверждает готовность схемы. Порядок восстановления определяет [каталог](../src/rag/indexing/README.md), а интерфейс показывает, какие схемы требуют переиндексации.

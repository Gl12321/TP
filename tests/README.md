# Проверки поведения приложения

Приложение должно возвращать таблицу из настоящих данных, сохранять прежнюю базу при неудачном импорте и корректно завершать отменённую работу. Тесты проверяют эти свойства по частям: правила SQL, сценарий агента, работу с данными и границы между компонентами.

Большинство проверок заменяет модели и внешние сервисы управляемыми зависимостями. Это позволяет воспроизводить ошибки, не загружая гигабайты весов. Отдельные проверки используют реальные библиотеки или PostgreSQL; отсутствие необходимых условий явно отмечается пропуском.

## Что проверяется

| Проверки | Поведение | Необходимые условия |
| --- | --- | --- |
| [test_agent.py](test_agent.py) | Исправления, обновление контекста, повторная отмена и завершение вопроса | Модели и граф заменены зависимостями |
| [test_graph_flow.py](test_graph_flow.py) | Переходы настоящего графа и число попыток | Установленный LangGraph |
| [test_prompts.py](test_prompts.py) | Полнота структуры, границы полей, сообщения исправления | Без модели |
| [test_llm_client.py](test_llm_client.py), [test_llm_template.py](test_llm_template.py) | Токенизация, шаблон, память, остановка и очистка | Подменённый движок; рендер требует Jinja2 |
| [test_rag.py](test_rag.py) | Изоляция схем, актуальность индекса, связи, ранжирование и отмена | Модели и Chroma заменены зависимостями |
| [test_sql_grammar.py](test_sql_grammar.py) | Допустимые и недопустимые запросы, экранирование GBNF | Без модели; нативная компиляция — при доступной локальной библиотеке |
| [test_sql_validation.py](test_sql_validation.py) | Имена, области видимости, агрегаты и запрещённые конструкции | Установленный SQLGlot |
| [test_results.py](test_results.py) | Представление Decimal, дат, UUID и бинарных значений, предел ответа | Стандартная библиотека |
| [test_database.py](test_database.py) | SQLite, типы, ограничения и метаданные импорта | Для части проверок нужен SQLAlchemy |
| [test_database_integration.py](test_database_integration.py) | Настоящие транзакции, откат импорта, курсоры, отмена и таймауты | Явное подключение к отдельной тестовой PostgreSQL |
| [test_api_logic.py](test_api_logic.py) | HTTP-операции, поток ответа и координация изменений | FastAPI и HTTP-клиент; без рабочей модели и внешней БД |
| [test_startup.py](test_startup.py) | Повторный запуск, секреты, порядок подготовки, прерывания и проверка файлов моделей | Docker и Hugging Face заменены зависимостями; без сети |
| [test_config.py](test_config.py) | Настройки YAML, выбор модели, пути, контрольные суммы и раннее отклонение неверной конфигурации | PyYAML и Pydantic Settings |

[gbnf_support.py](gbnf_support.py) содержит распознаватель для проверки языка грамматики. Если на Windows уже доступна `.tools/llama-*/llama.dll`, дополнительно проверяется компиляция настоящим движком без загрузки весов.

## Почему проверки разделены

Например, ошибка в сумме по покупателям может возникнуть на разных этапах: поиск не включил таблицу заказов, модель составила неверный JOIN или преобразование результата потеряло точность Decimal. Один большой запуск показал бы неправильную таблицу, но не объяснил причину. Проверки отдельных границ позволяют отличить эти ситуации.

При этом подмена зависимости имеет предел. Проверка агента может подтвердить, что исправимый SQL отправляется на новую попытку, но не может доказать, что настоящая модель его исправит. Поэтому сценарий графа, совместимость библиотек и качество ответа на предметных данных рассматриваются как разные уровни проверки.

## Запуск

Из корня проекта:

```text
python -m unittest discover -s tests -t . -v
python -m unittest discover -s frontend -p "test_*.py" -v
```

Вторая команда проверяет [клиент интерфейса](../frontend/test_client.py) с подставным HTTP-транспортом и [экран](../frontend/test_app.py) через Streamlit AppTest. Проверки экрана требуют зависимости из `frontend/requirements.txt`; при их отсутствии явно пропускаются. Браузер, работающий API и модели не нужны. Команды не устанавливают зависимости и не скачивают модели.

Проверки PostgreSQL включаются только при заданном `TEXT2SQL_TEST_DATABASE_URL`. Дополнительный `TEXT2SQL_TEST_READ_URL` включает сценарии выполнения под ролью чтения. Точные требования заданы в [интеграционном наборе](test_database_integration.py). Он создаёт и удаляет случайные схемы `text2sql_test_` в указанной БД; используйте отдельную тестовую базу. Сервисы тесты не запускают.

## Что означает результат

Пропущенная проверка не считается подтверждённой. Тест с подменой модели проверяет управление вызовом, но не качество её SQL. Тест HTTP-клиента не заменяет работу интерфейса в браузере. Поэтому после подготовки окружения нужен полный сценарий: импорт, вопрос, таблица, отмена и восстановление после ошибки.

При исправлении ошибки полезен сценарий, в котором прежнее поведение действительно даёт неверный результат. Например, существующий маркер модели не должен считаться готовностью после удаления файла, а ошибка конфигурации не должна останавливать уже работающие сервисы. Такие проверки сохраняют ожидаемое поведение при последующей переработке реализации.

Выполненные проверки и оставшиеся интеграционные прогоны перечислены в [VALIDATION.md](../docs/VALIDATION.md). Устройство проверяемых компонентов описано в [src](../src/README.md); сценарий запуска приложения — в [корневом руководстве](../README_RU.md).

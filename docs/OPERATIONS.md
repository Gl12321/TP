# Подключение и эксплуатация

Рабочая установка состоит из приложения, его собственной БД и подключённого источника данных компании. Подготовка моделей нужна только для свободных вопросов. Настроить пространство, участников, точки и источник можно заранее через обычный интерфейс.

Общая команда [run.py](../run.py) предназначена для Windows и Linux с работающим Docker Compose v2. Она сохраняет данные при остановке и повторной подготовке. Фактическая проверка каждой среды отражена в [VALIDATION.md](VALIDATION.md); наличие Compose-файла не означает, что все платформы уже испытаны.

## Первая настройка

1. Запустите `python run.py --without-ai`, если сначала хотите настроить приложение без скачивания моделей. Для полного запуска используйте `python run.py`.
2. Откройте `http://localhost:8000`. Введите код первоначальной настройки из терминала, создайте аккаунт и рабочее пространство. После этого повторное создание первого владельца закрывается.
3. Добавьте точки. Их внешние коды должны совпадать со значениями ключа точки в аналитическом источнике.
4. Добавьте адрес PostgreSQL клиента в `application.source_hosts` файла [config.yaml](../config.yaml) и перезапустите приложение той же командой. Пустой список запрещает любые подключения.
5. В разделе данных создайте подключение, проверьте его и обновите каталог. Разрешите нужные таблицы и столбцы. Для таблиц с операциями укажите ключ точки, для общих справочников явно выберите общий доступ.
6. Определите показатели по реальным таблицам и сравните их с контрольными расчётами из учётной системы. После этого задайте планы и пригласите участников с нужными ролями и областью.
7. Запустите `python run.py --model qwen3.5-9b`, чтобы подготовить модель и включить свободные вопросы.

Приглашение — одноразовая ссылка со сроком действия. Приложение создаёт её и позволяет скопировать; почтового транспорта сейчас нет. Ссылку передаёт администратор через принятый в организации канал.

## Подключение PostgreSQL клиента

Используйте отдельную роль чтения с `LOGIN`, доступом к нужной БД, `USAGE` разрешённых схем и `SELECT` нужных таблиц. Приложение отклоняет административную роль и обнаруженные права записи в выбранных таблицах, включая права изменения отдельных столбцов. Оно само не создаёт пользователя в клиентской БД и не меняет её схему.

Предпочтителен отдельный отчётный источник или представления с согласованными бизнес-полями. Это позволяет фиксировать смысл даты, суммы, статуса операции и внешнего кода точки. Типизированный показатель первой версии задаёт одну таблицу, агрегат `sum`, `count` или `avg`, поле даты и ключ точки. Сложные метрики с особыми правилами оплаты, возвратами и валютами следует подготовить в проверяемом представлении; произвольного конструктора формул пока нет.

Адрес разрешается по точному hostname или IP. Внутри Docker `localhost` обозначает контейнер, а не компьютер пользователя. Используйте достижимый из контейнеров адрес сервера; для PostgreSQL на Windows-хосте Docker Desktop обычно предоставляет `host.docker.internal`. Сетевой доступ и `pg_hba.conf` источника должны разрешать подключение.

Режим `verify-full` проверяет цепочку сертификата и имя сервера с системным хранилищем доверия. Режим `require` шифрует соединение, но не подтверждает личность сервера; `disable` предназначен для изолированного локального тестирования. Для удалённого источника настройте доверенный сертификат и используйте `verify-full`.

## Память и готовность

API, PostgreSQL и модельный worker разделены. Один worker обрабатывает один AI-запрос за раз; остальные задачи ожидают в ограниченной очереди. Настройки результата, SQL, генерации и свободной памяти находятся в YAML. Контейнеры API и PostgreSQL имеют отдельные ограничения памяти; worker проверяет доступную память перед загрузкой и во время генерации.

Для 24 ГБ RAM начните с профиля 9B или 4B и измерьте совместный расход всей установки. Проверка свободной памяти не гарантирует, что другая программа не займёт её во время работы. Размеры [GGUF](../models/README.md) не включают буферы, поиск и ОС. 27B не загружается одновременно с другой основной моделью.

`/health` сообщает о жизни API и готовности worker, `/ready` проверяет прикладную БД. Генерация без свежего heartbeat возвращает понятную ошибку до постановки новой задачи. Сохранённые материалы и обычные действия доступны независимо от модели. Техническая спецификация находится по `/api/docs`; её JSON — по `/api/openapi.json`.

## Секреты, хранение и обновление

`.runtime/compose.env` содержит сгенерированные пароли и ключ шифрования подключений. Файл исключён из Git. Не заменяйте `APP_SECRET_KEY` без отдельной процедуры перешифрования: существующие пароли источников перестанут расшифровываться. Пароль административной роли PostgreSQL используется при подготовке; API и worker работают под обычной прикладной ролью.

БД приложения хранится в томе `postgres_data`, кеш worker — в `agent_data`, веса — в `models`. `python run.py --stop` сохраняет все эти данные. Имя Compose-проекта зависит от абсолютного пути каталога. При переносе проекта в другую папку не считайте появившуюся пустую БД потерей прежней: прежний том принадлежит другому имени проекта.

Перед обновлением создавайте резервную копию командой ниже. Архив содержит согласованный снимок прикладной БД, YAML и ключ расшифровки подключений. Он содержит секреты: храните его в закрытом каталоге с резервированием на другом носителе. База клиента резервируется отдельно. Поисковый кеш можно построить заново; обсуждения и результаты требуют копии БД.

```text
python tools/backup.py create .runtime/backups/before-update.zip
```

Для восстановления используйте новое имя БД. Команда проверит состав и контрольные суммы архива, восстановит данные под обычной прикладной ролью и применит актуальные миграции. Исходная БД сохраняется; существующую БД с выбранным именем команда не перезаписывает. При ошибке удаляется только новая БД, созданная текущей попыткой.

```text
python tools/backup.py restore .runtime/backups/before-update.zip --database razbor_recovered --output-env .runtime/recovered.env
python run.py --env-file .runtime/recovered.env
```

В восстановленной копии отзываются все сессии, а незавершённые AI-задачи получают статус ошибки с причиной восстановления. Пользователь входит повторно и при необходимости заново отправляет вопрос. Старый worker не продолжает очередь восстановленного снимка. Ключ подключений переносится из архива, пароли прикладной роли берутся из текущего окружения.

YAML в архиве служит для сверки настроек; команда не заменяет актуальный `config.yaml` автоматически. После восстановления проверьте подключения, области участников и контрольный показатель. Последующие команды запуска, остановки и резервирования выполняйте с `--env-file .runtime/recovered.env`, пока эта копия используется как рабочая. Для остановки: `python run.py --env-file .runtime/recovered.env --stop`.

Обновление через общую команду собирает новые образы и выполняет Alembic-миграции до запуска нового API. Ошибка миграции останавливает последовательность. Это последовательное развёртывание одного экземпляра, без обещания обновления без простоя. Для публичной установки следует проводить обновление в согласованное окно.

## Размещение за HTTPS

По умолчанию порт доступен только на `127.0.0.1`. Для сервера поставьте перед приложением обратный прокси с HTTPS, задайте точные `application.allowed_origins` и `secure_cookies: true`. Нельзя оставлять локальную настройку cookie для публичного HTTP-доступа. Если порт меняется через `APP_PORT`, согласуйте origins с фактическим адресом браузера.

Сессии хранятся на сервере; cookie имеет `HttpOnly` и `SameSite=Lax`. Изменяющие запросы требуют CSRF-токен. Внешний доступ к БД контейнером Compose не публикуется. Source allowlist и роли участников должны соответствовать реальному развёртыванию, а не тестовым значениям.

## Разработка без контейнеров

Установите Python-зависимости через `python -m pip install -r requirements-dev.txt`. Укажите `APP_DATABASE_URL`, `APP_SECRET_KEY`, `APP_BOOTSTRAP_TOKEN` и для локального HTTP `APP_SECURE_COOKIES=false`. Для прикладных сценариев разрешена SQLite с URL `sqlite+aiosqlite:///./razbor.db`; внешний аналитический источник всё равно PostgreSQL. Локальную БД не следует добавлять в Git.

```text
python -m backend.app.bootstrap migrate
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

Сборка frontend: в каталоге `frontend` выполните `npm ci` и `npm run build`; API раздаёт `frontend/dist`. Для разработки с Vite смотрите [frontend/README.md](../frontend/README.md). Настройки процесса передаются переменными окружения; автоматического чтения произвольного `.env` здесь нет.

Отдельный запуск worker требует дополнительных зависимостей `python -m pip install './packages/sql_agent[local]'`, проверенных файлов моделей и затем `python -m backend.app.worker`. На Windows сборка `llama-cpp-python` может потребовать компилятор C++; для обычной эксплуатации этот шаг изолирован в Docker-образе. Автономные тесты и браузерная разработка весов не требуют.

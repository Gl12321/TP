# Резервное копирование и восстановление

Резервная копия сохраняет рабочие пространства, аккаунты, настройки источников, историю вопросов, отчёты и разборы. Она нужна для переноса приложения и восстановления после потери прикладной БД. Для чтения сохранённых паролей источников нужен также ключ приложения, поэтому один SQL-dump недостаточен.

Штатный инструмент — [tools/backup.py](../../tools/backup.py). Он создаёт архив прикладной PostgreSQL и восстанавливает его только в новую БД. Текущая база не перезаписывается, что позволяет проверить восстановление перед переключением пользователей.

## Что входит в копию

| Файл архива | Содержание |
| --- | --- |
| `database.dump` | `pg_dump` в custom-формате, без привязки к владельцам и ACL исходной установки |
| `config.yaml` | Корневой файл конфигурации проекта на момент копирования |
| `manifest.json` | Версия формата, время, имя исходной БД, ключ приложения и SHA-256 двух файлов |

Архив **не зашифрован** и содержит `APP_SECRET_KEY`, которым расшифровываются пароли источников из dump. Его нужно хранить с доступом только для ответственных за эксплуатацию. Контрольные суммы обнаруживают повреждение файлов; они не являются цифровой подписью автора архива. Восстанавливать следует копию из доверенного хранилища.

В архив не входят внешние бизнес-базы клиентов, модели, исходный код, Docker-образы, поисковый кеш и все пароли env-файла. Внешняя БД резервируется её владельцем отдельно. Модели воспроизводятся по закреплённым версиям YAML, кеш поиска перестраивается. Для развёртывания на другой машине отдельно сохраняются версия приложения и секреты подключения к целевой PostgreSQL.

Dump содержит согласованный снимок прикладной БД во время копирования. Он не фиксирует состояние внешних источников в тот же момент. Сохранённые ответы внутри приложения остаются частью копии, а новый расчёт после восстановления обращается к текущим данным источника.

## Требования

Для стандартного Compose-запуска нужны работающий сервис `db`, файл `.runtime/compose.env`, Python на хосте и доступ к Docker. Инструмент использует утилиты PostgreSQL внутри контейнера. Образы API должны быть собраны: при восстановлении они применяют миграции и очищают состояние незавершённых заданий.

Файл окружения должен содержать `DB_USER`, `DB_PASSWORD`, `DB_NAME`, `APP_DB_USER`, `APP_DB_PASSWORD`, `APP_DB_NAME`, `APP_SECRET_KEY`. Для восстановления через Compose и последующего запуска приложения нужен также `APP_BOOTSTRAP_TOKEN`: служебный запуск миграций использует конфигурацию контейнера API. При использовании другого файла он передаётся через `--env-file` перед действием `create` или `restore`.

Нужны свободное место для dump, архива и временных файлов, а при восстановлении — также место для новой БД. Служебная роль должна читать исходную БД, создавать целевую и выполнять `SET ROLE` в прикладную роль при `pg_restore`. В штатном Compose эти операции выполняет служебный пользователь PostgreSQL; для отдельного сервера права согласовываются отдельно. Прикладная роль на целевом сервере должна уже существовать; её подготавливает `bootstrap-db`.

## Создание

Из корня проекта:

```text
python tools/backup.py create .runtime/backups/razbor-2026-10-04.zip
```

Для отдельного env-файла:

```text
python tools/backup.py --env-file .runtime/production.env create .runtime/backups/razbor-2026-10-04.zip
```

Имя файла должно быть новым. Существующий архив не перезаписывается. Команда создаёт dump, рассчитывает контрольные суммы и публикует архив; при ошибке незавершённый итоговый файл удаляется. Временные файлы очищаются после завершения операции.

Создание копии не требует останавливать API и worker: `pg_dump` формирует согласованный снимок PostgreSQL. Если нужен момент переключения без потери последующих изменений, финальная копия делается в согласованное окно обслуживания, когда новые пользовательские записи уже прекращены.

Путь `.runtime/backups` удобен локально и исключён из Git. Для защиты от потери диска готовый архив переносится в отдельное защищённое хранилище. Планировщик ОС или система эксплуатации может вызывать ту же команду; встроенного расписания и автоматической ротации копий нет.

## Восстановление в новую БД

Сервис `db` должен работать. Для примера используется новая база `razbor_recovered` и новый env-файл:

```text
python tools/backup.py restore .runtime/backups/razbor-2026-10-04.zip --database razbor_recovered --output-env .runtime/recovered.env
```

Если текущие секреты находятся в другом файле:

```text
python tools/backup.py --env-file .runtime/production.env restore .runtime/backups/razbor-2026-10-04.zip --database razbor_recovered --output-env .runtime/recovered.env
```

Имя целевой БД состоит из строчных латинских букв, цифр и подчёркиваний, начинается с буквы либо подчёркивания и содержит не более 63 символов. Оно должно отличаться от служебной и текущей прикладной БД. Существующая БД не заменяется; новый env-файл также не должен существовать заранее.

Инструмент последовательно:

1. Проверяет состав архива, метаданные, место для распаковки временных файлов и контрольные суммы. Свободное место на диске самого PostgreSQL оператор проверяет отдельно.
2. Создаёт отдельную БД с прикладной ролью-владельцем и ограничивает публичный доступ.
3. Восстанавливает dump одной транзакцией, не применяя исходные владельцы и ACL.
4. Применяет миграции текущей версии приложения до `head`.
5. Отзывает восстановленные пользовательские сессии, удаляет старые heartbeat worker и помечает незавершённые задания и расчёты ошибкой восстановления.
6. Создаёт новый env-файл с именем восстановленной БД и `APP_SECRET_KEY` из архива.

Если восстановление не завершилось, инструмент удаляет незавершённый env-файл и пытается удалить созданную им целевую БД. При потере связи или недостаточных правах очистка БД тоже может завершиться ошибкой; тогда проверьте именно указанную целевую БД перед повтором. Исходная БД не удаляется и не исправляется на месте.

Для `config.yaml` из архива проверяется контрольная сумма; его настройки **не заменяют рабочий YAML автоматически**. Перед запуском сравните его с текущей конфигурацией: адреса источников, origins и ресурсы могут отличаться на новой машине. Архив всегда содержит корневой `config.yaml`; при специальном нативном запуске с другим `APP_CONFIG_PATH` этот альтернативный файл сохраняется отдельно.

Восстанавливать следует той же или совместимой более новой версией приложения. Автоматический downgrade схемы не выполняется. Мажорную версию PostgreSQL и совместимость dump нужно учитывать при переносе на другой сервер.

## Переключение приложения

После успешного восстановления остановите прежние сервисы, затем запустите приложение с новым окружением:

```text
python run.py --stop
python run.py --env-file .runtime/recovered.env
```

Если прежний запуск использовал нестандартный env-файл, при остановке передайте именно его:

```text
python run.py --env-file .runtime/production.env --stop
```

Модели и данные при штатной остановке сохраняются. При необходимости тот же запуск можно выполнить с `--without-ai`, чтобы проверить данные интерфейса без запуска модели. Это не удаляет историю расчётов.

После восстановления ожидается следующее:

- Пользователи входят заново прежними аккаунтами; существующий аккаунт не создаётся повторно через первоначальную настройку.
- Сохранённые пространства, определения, отчёты, разборы и результаты доступны в пределах прежних прав.
- Вопросы, которые были в очереди или выполнялись на момент копии, не запускаются незаметно повторно. Пользователь отправляет их заново.
- Подключения могут потребовать изменения адреса, разрешённого хоста или пароля на стороне внешнего источника. Сам факт восстановления не делает внешний сервер доступным.
- Worker создаёт новый heartbeat и при необходимости перестраивает поисковый кеш.

Проверьте `/ready`, вход, состав пространства, чтение сохранённого отчёта и подключение к источнику. После запуска worker проверьте `worker_ready` в `/health` и один обычный расчёт. Успешное создание ZIP без восстановления не доказывает пригодность копии.

Исходная БД сохраняется для обратного переключения. Если после перехода появились новые записи, простое возвращение старого env-файла их не переносит: это отдельная операция с согласованным моментом остановки. Удаление старой базы не входит в процедуру backup.

## Работа без Docker

Тот же инструмент умеет использовать установленные `pg_dump`, `pg_restore` и `psql`. Укажите каталог утилит через `--pg-bin`. В env-файле дополнительно задаются `DB_HOST` и `DB_PORT`; Python-окружение должно содержать зависимости бэкенда и SQL-пакет, поскольку миграции выполняются локально.

Пример Windows:

```text
python tools/backup.py --env-file .runtime/native.env --pg-bin "C:/Program Files/PostgreSQL/16/bin" create .runtime/backups/native.zip
```

Пример Linux:

```text
python tools/backup.py --env-file .runtime/native.env --pg-bin /usr/lib/postgresql/16/bin restore .runtime/backups/native.zip --database razbor_recovered --output-env .runtime/native-recovered.env
```

Пути в примерах заменяются на реальные каталоги установленного PostgreSQL. Для нативного запуска новый env-файл служит источником параметров; процесс приложения должен получить их через своё окружение. В восстановленном файле нет готового `APP_DATABASE_URL`: составьте его из `APP_DB_USER`, URL-кодированного `APP_DB_PASSWORD`, `DB_HOST`, `DB_PORT` и нового `APP_DB_NAME`. `run.py` остаётся launcher для Docker; нативный сервер запускается по [инструкции разработки](../development/README.md).

## Что хранить вместе с копией

Для воспроизводимого восстановления нужны архив, версия кода/образов, доступ к целевому PostgreSQL и параметры размещения. Внутри приложения ключ сохраняется в архиве; вне приложения остаются TLS, домен, правила сети и резервирование внешних бизнес-источников. Периодичность копий определяется допустимой потерей новых записей, а срок хранения — требованиями эксплуатации.

# Конфигурация и секреты

Настройки позволяют перенести один и тот же продукт с ноутбука на сервер, выбрать модель и задать доступ к источникам без изменения кода. Они разделены на обычную конфигурацию, секреты развёртывания и настройки данных внутри рабочего пространства. Это разные уровни: адрес разрешённого сервера не является правом пользователя читать его таблицы.

## Где хранится каждый уровень

| Место | Назначение |
| --- | --- |
| [config.yaml](../../config.yaml) | Модель, параметры генерации, лимиты, адреса источников, браузерные origins и поведение приложения |
| `.runtime/compose.env` или файл `--env-file` | Пароли служебной и прикладной БД, ключ приложения и код первоначальной настройки |
| Переменные процесса | Переопределения при нативном запуске и параметры, явно переданные контейнеру |
| Прикладная PostgreSQL | Организации, участники, подключения, разрешённые таблицы/поля/читатели, определения показателей и планы |
| `docker-compose.yml` | Состав сервисов, порты, тома, ресурсы и передача переменных контейнерам |

Обычная работа ведётся через YAML и интерфейс управления источниками. Секреты не записываются в YAML и не передаются фронтенду. Сгенерированные env-файлы исключены из Git.

## Разделы YAML

Точные значения по умолчанию находятся в `config.yaml`; таблица ниже объясняет назначение, а не дублирует каждое число.

| Раздел | Что меняет |
| --- | --- |
| `model` | Профиль основной модели по умолчанию |
| `application` | Разрешённые хосты источников, origins браузера, Secure-cookie, срок сессии и аренда задания |
| `settings` | Ограничения результата и SQL, общий бюджет вопроса, память, исправления, поиск, размер пакетов и вместимость очереди |
| `generation` | Параметры llama.cpp: контекст, длина ответа, потоки, пакеты, CPU/GPU и mmap |
| `models` | Доступные GGUF-профили с точными версиями файлов, размером и SHA-256 |
| `retrieval_models` | Encoder и reranker, их параметры и закреплённые файлы |

Ключи `application` и `settings` проверяются при загрузке: опечатка не превращается в молча проигнорированную настройку. Числовые лимиты должны быть положительными целыми, кроме `MAX_CORRECTIONS`, которому разрешён ноль. Связанные ограничения генерации проверяются отдельно: `n_ubatch <= n_batch <= n_ctx`, а контекст должен вмещать ответ и промпт.

### Доступ к источникам

`application.source_hosts` содержит точные имена хостов или IP, без схемы, пути и отдельного номера порта. Пустой список запрещает подключения к источникам. Маски и `*` не используются.

```yaml
application:
  source_hosts:
    - analytics-db.internal
  secure_cookies: true
  allowed_origins:
    - https://razbor.example.com
  session_ttl_seconds: 43200
  job_lease_seconds: 90
```

Фрагмент заменяет соответствующий раздел YAML; значения остальных разделов сохраняются. Имя хоста должно разрешаться из API и worker. Внутри контейнера `localhost` означает этот контейнер, а не компьютер пользователя. Для внешнего источника нужен доступный контейнерам адрес и разрешение подключения на стороне PostgreSQL.

Allowlist сервера только разрешает попытку сетевого подключения. В интерфейсе отдельно задаются учётная запись PostgreSQL для чтения, TLS, видимые таблицы/поля, область строк и читатели профиля. После изменения этих правил бэкенд обновляет версию каталога и заново проверяет доступ к расчётам.

### Браузер и сессии

`allowed_origins` — точные HTTP/HTTPS origins вида `https://razbor.example.com`, без пути и завершающего `/`. Они определяют, с каких браузерных адресов разрешены запросы. Для локальной разработки с отдельным Vite-сервером добавляется его origin. `*` не допускается.

`secure_cookies: false` подходит для локального HTTP. При размещении через HTTPS используется `true`; внешний URL, настройки reverse proxy и origins должны согласовываться. Изменение опубликованного порта требует проверить адреса интерфейса и origins. CSRF-защита остаётся обязательной независимо от этого флага.

### Лимиты и ресурсы

- `MAX_RESULT_ROWS` и `MAX_RESULT_BYTES` ограничивают накопленный результат. При достижении лимита ответ отмечается как ограниченный, а не как полный набор строк.
- `SQL_TIMEOUT_MS` и `SQL_LOCK_TIMEOUT_MS` ограничивают работу источника. Увеличение времени генерации не увеличивает автоматически время SQL.
- `LLM_TIMEOUT_SECONDS` задаёт общий бюджет вопроса и предел генерации. Исправления расходуют тот же общий бюджет.
- `MAX_CORRECTIONS` управляет исправлениями после первой генерации. Ноль оставляет только первую попытку.
- `RETRIEVAL_TOP_K` и `CONTEXT_MAX_TABLES` ограничивают кандидатов и итоговый набор таблиц с учётом связей. Увеличение числа таблиц может привести к нехватке контекста.
- `EMBEDDING_BATCH_SIZE` и `RERANKER_BATCH_SIZE` влияют на память и скорость CPU-моделей поиска.
- `MAX_QUEUED_JOBS`, лимит рабочего пространства и лимит пользователя ограничивают число активных заданий. Они не добавляют вычислительные worker.
- `MIN_FREE_MEMORY_MB` задаёт запас доступной памяти для приложения. Это проверяемый порог, а не резервирование RAM операционной системой.

Уменьшение `n_ctx` сокращает доступный контекст; увеличение требует дополнительной памяти. `max_tokens` должен позволять завершить SQL, но также отнимает место у входного контекста. При `n_threads: null` и `n_threads_batch: null` запуск выбирает ограниченное число потоков по доступным CPU, максимум восемь.

Штатный профиль использует CPU. Изменение `n_gpu_layers` работает только с соответствующей сборкой llama.cpp и настройкой GPU в контейнере. Оно само по себе не устанавливает CUDA и не открывает доступ к видеокарте.

## Приоритеты и применение настроек

Для бэкенда порядок такой: значения класса `Settings` → разделы YAML → явно поддерживаемые переменные окружения процесса. Загрузчик находится в [infrastructure/config.py](../../backend/app/infrastructure/config.py).

Для моделей: `--model` при запуске задаёт `MODEL_PRESET`; иначе используется значение из env-файла, если оно явно задано, затем `model` из YAML. Общие параметры `generation` дополняются и переопределяются `models.<профиль>.params`. Путь к GGUF определяется выбранным профилем и каталогом `models/`.

`run.py` очищает у дочернего Compose часть одноимённых переменных текущего терминала: пароли, имена прикладной БД, ключи и `MODEL_PRESET`. Поэтому уже открытый терминал не должен случайно заменить секреты другого запуска. Для смены модели используется флаг, для смены прикладной БД и ключей — `--env-file`.

Важное различие: **Compose env-файл задаёт значения подстановки, а не все переменные контейнера**. Стандартный `docker-compose.yml` передаёт приложению только явно перечисленные поля `environment`. Добавление произвольного `APP_MAX_RESULT_ROWS` в `.runtime/compose.env` не изменит лимит внутри контейнера. Для обычного Compose-развёртывания такие значения меняются в YAML; для специального развёртывания переменная должна быть явно передана сервисам API и worker.

Настройки читаются при создании процесса. После изменения YAML перезапускаются API и worker: `python run.py --stop`, затем `python run.py` с нужными флагами. Одного изменения смонтированного файла недостаточно, а повторный Compose `up` может сохранить уже работающий API. Изменение модели требует перезапуска worker и подготовки выбранных файлов. Статическая сборка фронтенда для изменений YAML не нужна.

## Переменные процесса

Эти параметры используются при нативном запуске либо при явной передаче окружения контейнеру.

| Переменная | Назначение |
| --- | --- |
| `APP_DATABASE_URL` | Прикладная БД, обычно `postgresql+asyncpg://…`. SQLite предусмотрена для изолированных проверок, а рабочая очередь использует PostgreSQL |
| `APP_SECRET_KEY` | Общий ключ API и worker длиной не менее 32 символов |
| `APP_BOOTSTRAP_TOKEN` | Код первоначального создания аккаунта; должен присутствовать в окружении приложения |
| `APP_CONFIG_PATH` | YAML для бэкенда и его локального движка; в контейнере `/app/config.yaml` |
| `APP_FRONTEND_DIST` | Каталог готовой сборки интерфейса |
| `APP_INDEX_DIR` | Восстановимый дисковый кеш поиска worker |
| `MODEL_PRESET` | Профиль основной модели для worker и подготовки |
| `APP_ALLOWED_ORIGINS`, `APP_SOURCE_HOSTS` | Списки через запятую; заменяют соответствующие списки YAML |
| `APP_SECURE_COOKIES` | Строго `true` либо `false` |
| `APP_SESSION_TTL_SECONDS`, `APP_JOB_LEASE_SECONDS` | Срок сессии и аренда задания |
| `APP_MAX_RESULT_ROWS`, `APP_MAX_RESULT_BYTES` | Предел выдачи |
| `APP_SQL_TIMEOUT_MS`, `APP_SQL_LOCK_TIMEOUT_MS` | Ограничения SQL |
| `APP_MAX_QUEUED_JOBS`, `APP_MAX_QUEUED_JOBS_PER_WORKSPACE`, `APP_MAX_QUEUED_JOBS_PER_USER` | Вместимость очереди |

LLM, retrieval и generation не имеют общего автоматического механизма переопределения через `APP_*`: они берутся из YAML. `SQL_AGENT_CONFIG` используется загрузчиком подготовки, если путь не передан явно; внутри штатного Compose оба процесса используют смонтированный корневой YAML.

Для Compose также существуют `APP_PORT` и `APP_BIND_ADDRESS`: они управляют публикацией порта API на хосте. `HF_TOKEN` передаётся только подготовке моделей при необходимости доступа к репозиторию. Настройки offline-режима worker уже заданы в Compose.

Для другого порта задайте `APP_PORT` в env-файле либо окружении команды: в PowerShell — `$env:APP_PORT = "8001"`, затем `python run.py`; в Bash — `APP_PORT=8001 python run.py`. Переменная процесса имеет приоритет над env-файлом; пустое выбранное значение использует стандартный порт 8000. Launcher выводит выбранный порт в адресе интерфейса. При нестандартном `APP_BIND_ADDRESS` используйте фактически опубликованный адрес хоста.

Приложение не загружает корневой `.env` автоматически. При нативном запуске нужные значения должны присутствовать в окружении процесса. Файл секретов launcher имеет простой формат `NAME=value`, без shell-команд и без необходимости оборачивать значение в кавычки.

## Секреты и сохранность данных

[run.py](../../run.py) создаёт отсутствующие пароли и ключи в `.runtime/compose.env`. В Unix файл получает права `0600`; в Windows доступ определяется ACL каталога. Существующие значения переиспользуются при повторном запуске.

| Секреты и имена | Роль |
| --- | --- |
| `DB_USER`, `DB_PASSWORD`, `DB_NAME` | Служебная учётная запись и начальная БД контейнера PostgreSQL, используемые подготовкой и резервированием |
| `APP_DB_USER`, `APP_DB_PASSWORD`, `APP_DB_NAME` | Отдельная роль и БД приложения; runtime запрещает совпадение прикладной и служебной роли |
| `APP_SECRET_KEY` | Шифрование паролей внешних источников, CSRF и защищённые курсоры списков |
| `APP_BOOTSTRAP_TOKEN` | Подтверждение первоначальной настройки; это не пароль пользователя и не ключ GitHub |

Удаление env-файла при сохранённом томе PostgreSQL не является сбросом приложения: новые сгенерированные значения могут перестать соответствовать существующей БД, а новый ключ не расшифрует сохранённые подключения. Секреты резервируются вместе с данными согласно [инструкции backup](backup.md).

Нельзя менять `APP_SECRET_KEY` как обычный пароль: текущая версия не выполняет автоматическое перешифрование всех источников. Для переноса используется прежний ключ из копии. `DB_PASSWORD` существующего PostgreSQL также не меняется от редактирования переменной контейнера: изменение должно быть согласовано с самой ролью БД. Прикладной пароль настраивает `bootstrap-db` при запуске.

Штатный launcher генерирует URL-safe пароли. В Compose `APP_DB_PASSWORD` вставляется в `APP_DATABASE_URL` напрямую: если задаёте свой пароль для этого режима, используйте URL-safe символы. Не подставляйте в эту переменную URL-кодированный пароль вместо реального — он одновременно передаётся в PostgreSQL как значение пароля. При нативном запуске пароль в отдельно составленном `APP_DATABASE_URL`, наоборот, нужно URL-кодировать, сохранив исходное значение в самой роли БД.

Подключения к клиентским базам хранятся в прикладной БД с зашифрованными паролями. Они не равны служебным ролям контейнера. Выдачу прав на внешней стороне PostgreSQL выполняет администратор этой базы.

## Что проверить после изменения

Изменённая настройка должна попасть в оба процесса, если влияет на авторизацию, источник или результат. Доступность API проверяется через `/ready`, присутствие готового worker — через `/health` и поле `worker_ready`. Затем проверяется именно изменённое поведение: подключение нового разрешённого хоста, вход по HTTPS, ограничение выдачи или выбранная модель.

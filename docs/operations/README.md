# Запуск и эксплуатация

Это руководство описывает установку «Разбора»: как получить рабочий интерфейс, подключить данные компании и поддерживать приложение после обновлений. Одинаковый способ запуска на Windows и Linux — Python-команда, управляющая Docker Compose. База приложения, API и обработчик SQL работают отдельными процессами; закрытие браузера не останавливает их.

Для знакомства с интерфейсом предусмотрены отдельные [демонстрационные сценарии](../demo/README.md): готовая сеть и первоначальная настройка. Им нужны обычные зависимости приложения, собранный frontend и отдельный PostgreSQL с `RAZBOR_DEMO_DATABASE_URL` для первой подготовки. Они создают собственные базы и аккаунты, сохраняют изменения и не запускают модели. Рабочая установка демонстрационными продажами не заполняется.

[Автоматические проверки](../development/testing.md) запускаются отдельно и используют свои временные данные. Для PostgreSQL-проверок предназначен `RAZBOR_TEST_DATABASE_URL`; он не настраивает demo. Браузерный сценарий получает `APP_UI_CREDENTIALS` отдельной тестовой установки.

Устройство контейнеров описано в [docker.md](docker.md), настройки — в [configuration.md](configuration.md), сохранение и восстановление данных — в [backup.md](backup.md). Для изменения кода и запуска компонентов по отдельности есть [руководство разработчика](../development/README.md).

## Что требуется

Если машина ещё не подготовлена, сначала выполните [установку с нуля](install.md). Там есть команды установки для Windows и Ubuntu, права, перезагрузка, проверка PATH и запуск Engine. Приведённые ниже команды проекта предполагают, что этот этап завершён.

| Компонент | Для чего нужен |
| --- | --- |
| Python 3.11 или новее на компьютере | Выполняет `run.py`; устанавливать Python-зависимости приложения на хост для этого режима не требуется |
| Работающий Docker с Compose v2 | Собирает образы, запускает PostgreSQL, API и worker |
| Linux-контейнеры | На Windows используется Docker Desktop с Linux backend; на Linux — Docker Engine с Compose |
| Свободное место на диске | Для образов, выбранной GGUF-модели, двух поисковых моделей и данных PostgreSQL |
| Достаточная оперативная память | Для выбранной модели, её контекста, поиска, PostgreSQL, API и операционной системы одновременно |
| PostgreSQL компании после первоначальной настройки | Нужен для расчётов по своим бизнес-данным; приложение можно запустить и открыть без него, собственная БД создаётся автоматически |

Node.js, компилятор C++, PostgreSQL CLI и ML-библиотеки находятся внутри соответствующих образов. При нативной разработке устанавливаются только зависимости изменяемого компонента: API не требует компилятора и весов, frontend требует Node.js, настоящий worker — локальные ML-зависимости. PostgreSQL CLI нужен для нативного резервирования. Подробности: [backend](../development/backend.md), [агент](../development/sql-agent.md), [frontend](../development/frontend.md).

Если образы, зависимости или веса отсутствуют, первый запуск получает их из сети. Повторный запуск использует подготовленные файлы и слои сборки. Наличие модели само по себе не означает, что на другом компьютере уже есть Docker-образы. Для закрытой сети нужны модели и подготовленное окружение сборки: launcher каждый раз вызывает `docker compose build`, поэтому перенос только конечных образов без нужных базовых образов и кеша не гарантирует офлайн-запуск. Такой режим проверяется на целевой машине до отключения сети.

## Одна команда

Перед первым запуском убедитесь, что выбранный интерпретатор реально запускается, а Docker Engine работает с Linux-контейнерами. Windows, в корне проекта:

```powershell
py -3.12 --version
py -3.12 run.py --check
py -3.12 run.py --model qwen3.5-9b
```

Linux:

```bash
python3 --version
python3 run.py --check
python3 run.py --model qwen3.5-9b
```

Продолжайте после кода `0` от проверки. `--check` ничего не устанавливает и не изменяет данные: проверяет Python 3.11+, Compose и доступный Linux Engine. В остальных примерах этого руководства `python` — сокращение выбранного рабочего интерпретатора: `py -3.12`, `python3` или явный путь к Python окружения. Заглушка Windows Store этим условием не является.

Доступны профили `qwen3.5-4b`, `qwen3.5-9b` и `qwen3.5-27b`. Без `--model` используется поле `model` в [config.yaml](../../config.yaml). Флаг выбирает модель этого запуска и не переписывает YAML. Размеры файлов, квантование и назначение вспомогательных моделей приведены в [документации агента](../development/sql-agent.md).

```text
python run.py --list-models
python run.py --without-ai
python run.py --stop
```

`--list-models` показывает каталог без скачивания весов; для команды также нужен Docker, а служебный образ при необходимости собирается. `--without-ai` запускает интерфейс и API без подготовки моделей и останавливает уже запущенный worker. `--stop` останавливает контейнеры, сохраняя PostgreSQL, модели и секреты.

Режим без AI позволяет управлять пространствами, участниками, источниками, метриками, планами, разборами и читать сохранённые результаты. Обзор с уже настроенным источником рассчитывается обычным SQL через API. Новые вопросы ассистенту и обновление сохранённых отчётов требуют worker: последнее не использует генерацию, но выполняется через его очередь.

## Что происходит при запуске

1. Проверяется Docker и блокируется второй одновременный запуск из этой папки. Создаётся или читается постоянный файл секретов `.runtime/compose.env`.
2. Проверяется конфигурация и собираются нужные образы. На этом шаге веса модели ещё не загружаются.
3. Запускается PostgreSQL, создаётся отдельная прикладная роль и БД, применяются миграции.
4. Поднимается API со встроенной сборкой frontend. После успешной проверки готовности терминал выводит адрес интерфейса и код первоначальной настройки.
5. В обычном режиме проверяются и при необходимости скачиваются выбранная GGUF-модель, embedder и reranker. Затем запускается worker. Интерфейс уже можно открыть, пока этот шаг продолжается.

Стандартный адрес — `http://localhost:8000`. Код из терминала нужен только для создания первого владельца. Это не пароль от PostgreSQL и не токен модели. В браузере задаются собственные данные входа и название первого пространства; после настройки первого пользователя повторное создание через этот сценарий закрывается.

Не ожидайте готовой выручки сразу после запуска. Новая установка содержит пустое рабочее пространство. В интерфейсе будут шаги настройки, а не демонстрационные продажи. Состояние «worker не готов» означает, что API работает, но обработчик ещё не загрузился или остановлен; оно не равнозначно готовности ассистента.

## От первого входа к реальным данным

1. Владелец добавляет точки сети: названия, города и внешние идентификаторы, соответствующие значениям в базе компании.
2. Оператор сервера разрешает точный hostname или IP источника в `application.source_hosts` в YAML и перезапускает приложение. Пустой список не разрешает подключать произвольные адреса.
3. Администратор создаёт подключение PostgreSQL через интерфейс. Нужна отдельная роль источника с правом чтения согласованных таблиц; приложение не выдаёт ей права автоматически. Проверка подключения показывает результат отдельно от сохранения настроек.
4. Администратор загружает каталог и разрешает нужные таблицы и столбцы. Для таблиц с фактами указывает поле точки. Общие справочники отмечает явно. Затем задаёт, какие участники могут читать источник.
5. Аналитик создаёт показатель, связывая бизнес-название с таблицей, датой, полем точки и агрегацией. Руководитель при необходимости вводит месячные планы. Обзор начинает считать реальные данные.
6. Владелец или администратор приглашает сотрудников, задаёт роли и области точек. Ссылка приглашения передаётся пользователю вручную. При готовом worker участники с правом чтения задают вопросы ассистенту.

Адрес источника должен быть доступен **из контейнеров API и worker**. `localhost` внутри контейнера обозначает его самого. В Docker Desktop база на хосте обычно доступна через `host.docker.internal`; это же точное имя надо разрешить в YAML. На Linux используйте доступный сетевой адрес сервера или явно настройте связь с хостом. Само разрешение hostname в приложении не меняет сетевые правила, `pg_hba.conf` и права PostgreSQL.

Представления и таблицы должны иметь понятную структуру и связи. Агенту нужны корректные названия полей и определения показателей: синтаксически допустимый SQL не исправит неверное бизнес-определение выручки. Сначала проверьте несколько характерных вопросов по известным контрольным итогам.

## Память и модели

Одновременно работает один выбранный генератор и две небольшие модели поиска. Профиль 27B существенно тяжелее 4B и 9B. Размер GGUF на диске не равен общему расходу RAM: добавляются KV-кеш, рабочие буферы, библиотеки и данные приложения. На ноутбуке с 24 ГБ нужно учитывать и память Windows/Linux, и ограничение памяти Docker. Количество ядер процессора не заменяет этот расчёт.

`MIN_FREE_MEMORY_MB` задаёт резерв для проверок агента; это не жёсткая изоляция памяти процесса. Контекст, batch и число потоков меняются в YAML. Рабочий профиль выбирается по доступной памяти и допустимой задержке, а не только по числу параметров модели. CPU-сборка является стандартной; включение GPU требует отдельной сборки и настройки worker.

## Изменения, обновления и остановка

Перед обновлением кода или схемы БД создайте [резервную копию](backup.md). Для применения изменённого YAML остановите и заново запустите приложение: настройки API читаются при старте процесса, а простой повтор `up` может оставить существующий процесс.

```text
python run.py --stop
python run.py --model qwen3.5-9b
```

Повторный запуск пересобирает изменившиеся слои и применяет миграции. Для другой модели достаточно очередного запуска с `--model`: launcher останавливает прежний worker перед подготовкой нового. API не загружает веса и продолжает обслуживать собственные функции независимо от длительности подготовки генератора.

Если используется `--env-file`, передавайте один и тот же путь запуску, остановке и резервированию. Не удаляйте секреты для «сброса ошибки»: смена ключа нарушит расшифровку сохранённых подключений. Не удаляйте PostgreSQL volume ради пересборки образа.

Имя Compose-проекта вычисляется из абсолютного пути репозитория. Перемещение или переименование папки меняет имя проекта и используемых томов. Для переноса установки применяйте резервирование и восстановление; запуск из новой папки сам по себе не переносит существующую БД.

## Как понять, что работает

| Проверка | Что она показывает |
| --- | --- |
| Главная страница | API отдаёт собранный frontend |
| `GET /ready` | Приложение может прочитать таблицу первоначальной настройки в своей БД; это не проверка всех возможных миграций и клиентских источников |
| `GET /api/v1/health` | Жив API и присутствует ли свежий heartbeat worker в поле `worker_ready` |
| Проверка источника в интерфейсе | Доступен конкретный PostgreSQL и подходит ли учётная запись подключения |
| Контрольный вопрос с ожидаемым ответом | Работает полный путь от каталога и модели до SQL и результата |

Спецификация API доступна в `/api/openapi.json`, интерактивная документация — в `/api/docs`. Страница Swagger использует внешние статические ресурсы; JSON-спецификация доступна непосредственно с сервера.

## Типичные ситуации

| Наблюдение | Что проверить |
| --- | --- |
| `python` предлагает Microsoft Store | Реальный интерпретатор не выбран: установите Python по [инструкции](install.md), откройте новый терминал и проверьте `py -3.12 --version` |
| Launcher не находит Docker | Docker установлен, запущен и доступен в `PATH`; на Windows выбран режим Linux-контейнеров |
| Интерфейс открылся, ассистент недоступен | Подготовка весов и загрузка worker ещё идут; проверьте завершение команды и логи worker |
| Процесс worker завершается | Свободную память, выбранный профиль и настройки контекста; логи могут указывать на отсутствующие файлы или несовместимость библиотеки |
| Источник нельзя сохранить | Поля подключения и право `sources:manage`; сохранение профиля само по себе не проверяет сеть |
| Проверка источника вернула ошибку | Точное имя в `application.source_hosts`, сетевую доступность, TLS и права роли PostgreSQL |
| База подключается, таблиц нет в вопросе | Разрешения каталога и столбцов, поле точки, аудиторию источника и область участника |
| Ошибка доступа после смены порта или домена | `allowed_origins`, режим cookies и адрес, через который открыт браузер |
| Есть таблица, но нет плана или сравнения | Определение/версию показателя, период, покрытие данных и наличие сопоставимого месячного плана |
| Обновление отчёта ожидает выполнения | Готовность worker и очередь; повторный SQL выполняется асинхронно |
| После переноса папки появилась пустая установка | Имя Compose-проекта и тома; восстановите нужную БД из копии вместо повторной настройки другой установки |

Состав контейнеров, логи и требования к публикации через HTTPS — в [руководстве Docker](docker.md).

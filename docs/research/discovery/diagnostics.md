# Помощь, когда результат не совпал с ожиданием

Человек часто замечает проблему раньше, чем может правильно сформулировать новый запрос: «здесь должен быть этот заказ», «почему пусто», «а если считать по дате оплаты?». Приложение может помогать исследовать такое расхождение, опираясь на данные и фактически выполненный расчёт. Это делает его полезным и после получения первой таблицы.

Ниже новая диагностическая функция и развитие ранее предложенного сравнения определений, рассмотренные 1 октября 2026 года. Они не реализованы. Примеры придуманы для обсуждения; их числа не являются результатами измерений или проверок проекта. [Общий отбор](README.md) сопоставляет их с другими сценариями.

## Почему запись не попала в результат

Пользователь получил оплаченные заказы за июнь и пишет: «Почему здесь нет заказа 1042?». Приложение находит запись по известному ключу в доступных пользователю данных и сопоставляет её с условиями выполненного запроса. Ответ выглядит как небольшая карточка:

| Проверка | Что обнаружено |
| --- | --- |
| Заказ существует в выбранных данных | Да, номер 1042 |
| Статус — оплачен | Да |
| Дата оплаты входит в июнь | Нет: 2 июля |
| Регион — Москва | Да |

Следующее действие — «Посмотреть июль с теми же условиями». Оно создаёт новый расчёт. Июньский результат и исходное определение остаются доступны для сравнения. Если пользователь ожидал отбор по дате создания, он может явно изменить именно это условие.

Полезный момент здесь — переход от «модель ошиблась» к конкретной проверяемой причине. Исследование [Why Not?](https://dbgroup.eecs.umich.edu/files/ChapmanSIGMOD09.pdf) рассматривает объяснение отсутствующих записей через операции, которые их исключили. Оно подтверждает самостоятельность такой задачи; универсальный алгоритм из статьи не предполагается переносить в TP целиком.

### Как вести себя при пустом результате

У пустой таблицы появляется действие «Проверить условия». Приложение показывает границы дат в источнике, доступные значения выбранной категории и результат нескольких ограниченных проверок. Например: «В данных есть июнь, но у заказов этого региона дата оплаты не заполнена». Это должно следовать из выполненных проверок, а не из свободного объяснения модели.

Нужно различать пять ситуаций:

1. Записи нет в выбранном источнике или его версии.
2. Запись есть, но условие отбора не выполняется либо его значение неизвестно.
3. Запись теряется при соединении или её группа не проходит условие после агрегирования.
4. Запись подходит, но находится за пределами запрошенного top-N или страницы.
5. Результат запроса шире показанной выдачи: ограничение приложения остановило получение строк.

Первые две ситуации подходят для начальной версии. Если запись прошла фильтры, но запрос содержит LIMIT, OFFSET или приложение усекло выдачу, начальная версия сообщает: «Фильтры пройдены; причину отсутствия среди показанных строк этот режим не определяет». Само наличие лимита не доказывает, что именно он скрыл конкретную запись. Если запрос содержит неподдержанный для диагностики JOIN, HAVING или сложную группировку, интерфейс называет эту границу и открывает условия запроса. Уверенная догадка о причине хуже честного ограничения функции.

### Реалистичная первая версия

Поддержать одну таблицу, известный уникальный ключ и набор явных фильтров: период, равенство, диапазон, принадлежность списку, отсутствие значения. Проверка выполняется отдельными ограниченными SELECT в том же разрешённом источнике. Для сохранённого результата нужна доступная версия данных либо явная пометка, что проверяются текущие данные и они могли измениться.

Предикаты нужно вычислять PostgreSQL, а не повторять приблизительно на Python. SQL различает истину, ложь и неизвестное значение; например, отсутствие даты не означает, что она находится вне периода. Порядок вычисления AND/OR тоже не следует выводить из порядка записи условий. Это следует из [документации логических операций PostgreSQL](https://www.postgresql.org/docs/current/functions-logical.html).

Для составного условия нельзя объявлять каждую ложную часть причиной исключения: в выражении с OR запись может пройти по другой ветке. Счётчики «осталось после первого фильтра, затем после второго» допустимы как иллюстрация выбранного порядка, но не как единственное объяснение влияния каждого условия. Начальную диагностику разумно ограничить понятными конъюнкциями и показывать неизвестные значения отдельно.

Небольшая модель нужна для понимания «заказ 1042» и выбора ключа при неоднозначности. После этого проверка и представление фактов выполняются без генерации нового объясняющего SQL. Поиск произвольного значения во всех таблицах не входит в минимальную версию.

### Связь с текущим кодом

В [QueryResult](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/domain/query.py) уже есть SQL и признак усечения, но нет описания предикатов, ключей сущностей или версии данных. [SQLExecutor](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/database/executor.py) ограничивает выдачу: это отдельная причина отсутствия строки на экране, отличная от SQL LIMIT. [Грамматика](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/sql/grammar/select.gbnf) разрешает JOIN и HAVING, поэтому обещание диагностики любого принятого запроса было бы слишком широким.

Не нужен второй агент, который сочиняет оправдание первого. Нужны описание поддержанных условий, небольшой исполнитель проверок и карточка их результатов. Для каждого поддержанного типа условия заранее известен способ проверки. Ограничения роли чтения, источников, времени и объёма результатов сохраняются.

**Проверка полезности до разработки:** показать человеку результат и известную отсутствующую запись. Он должен самостоятельно отличить «нет в источнике», «не прошла фильтр» и «фильтры пройдены, дальнейшая причина не установлена». В проверенных случаях он может изменить нужное условие; в неподдержанных понимает границу ответа. Если для этого приходится читать SQL, пользовательская задача пока не решена.

## Насколько вывод зависит от определения

Сравнение двух определений уже описано как F14 в [каталоге](../../FEATURES.md). Поэтому ниже предложено развитие представления такого сравнения, а не ещё одна независимая функция в подсчёте новых идей.

Вопрос «какой регион продаёт больше?» может дать разные ответы по созданным заказам, оплаченным заказам и оплатам за вычетом возвратов. Вместо скрытого выбора одного значения приложение может предложить сравнить два-три осмысленных определения на одном периоде и одной версии данных.

Например, в придуманном наборе Москва имеет 120 тысяч по созданным заказам и 80 тысяч по оплаченным; Петербург — 100 и 90 тысяч соответственно. По одному определению лидирует Москва, по другому — Петербург. Полезный ответ: «Лидер зависит от того, какие заказы учитывать», с таблицей обоих вариантов и видимыми правилами. Ни один вариант не объявляется правильным лишь потому, что он даёт большую сумму.

Такой подход родственен исследованию [Boba: Authoring and Visualizing Multiverse Analyses](https://arxiv.org/abs/2007.05551), где рассматриваются варианты аналитических решений и устойчивость результатов. Предложение для TP намного уже: несколько явно выбранных определений, без собственного языка программирования, автоматического перебора всех гипотез и статистических обещаний.

### Что получает пользователь

Действие «Проверить другое определение» появляется рядом с определением показателя. Пользователь выбирает один спорный аспект: статус заказа, событие даты, учёт возвратов или заранее заданный порог. Приложение показывает варианты, их значения, разницу и то, сохранился ли конкретный вывод — например, лидер среди регионов.

Этот сценарий отличается от сравнения периодов: меняются правила расчёта, а не дата наблюдения. Он отличается и от «что если»: фактические данные не подменяются предполагаемыми продажами или ценами. Пользователь исследует последствия определения.

### Как не раздувать функцию

Первая версия — два определения одной меры в совместимых единицах, один разрез и один период. Программа сравнивает значения и порядок категорий; словесный вывод собирается из этих фактов. Если варианты используют разную временную привязку, это видно рядом с каждым результатом. Равные значения должны оставаться равными, без произвольного объявления победителя.

Альтернативы берутся из утверждённых определений или явного выбора пользователя. Модель может предложить вопрос об определении, но не создаёт десятки вариантов в поиске красивого вывода. Сравнение всех сочетаний фильтров и всех полей быстро становится дорогим и провоцирует выбор удобного результата.

Для простых сумм по двум статусам достаточно условных агрегатов; текущий язык уже имеет CASE. Сложные альтернативы с разными связями, валютами или распределением возврата по позициям требуют отдельных проверенных расчётов. Поддержка CASE сама по себе не подтверждает правильность этой логики.

**Ограничение:** устойчивость среди двух выбранных вариантов не означает устойчивость при любых определениях. Это не вероятность истинности вывода и не статистическая значимость. Изменённое определение нужно подписывать явно; иначе функция лишь создаст две разные цифры с одинаковым названием.

**Приоритет:** полезное расширение после появления сохранённых определений. Для первой демонстрации продукта диагностика отсутствующей записи даёт более самостоятельную пользу и требует меньше предварительно согласованных бизнес-правил.

# Какой продукт имеет смысл строить вокруг SQL Agent

Срез исследования до замены интерфейса. 3 октября 2026 года прежний Streamlit удалён; упоминания его поведения ниже исторические. Актуальное проектирование — [Python-бэкенд, React и sql_agent](../franchise/architecture.md); [статус frontend](../../../frontend/README.md).

Исследование от 1 октября 2026 года. Рассматривается один пользователь на ноутбуке с 24 ГБ RAM, CPU Intel, Windows или Linux. Это выбор направления и размера следующей версии, а не описание уже реализованных возможностей. Производственный код в ходе этой работы не менялся. Общий каталог идей находится в [FEATURES.md](../../FEATURES.md); здесь отобраны решения, которые оправдывают свою стоимость.

**Самое сильное направление — помощник, который превращает обычный вопрос в проверяемый расчёт, а удачный расчёт позволяет сохранить и повторять без нового обращения к модели.** Рабочее пространство нужно вокруг этих расчётов: таблица, график, условия, SQL, параметры и предыдущие запуски. Для первого полезного результата человек не должен заранее описывать всю предметную область.

Пример законченного сценария: загрузить продажи, спросить «Сколько принесли оплаченные заказы по городам?», увидеть таблицу и условия расчёта, проверить SQL, сохранить анализ. Затем выбрать другой месяц обычным контролом и получить новый результат, сохранив прежний для сравнения. Модель участвует в понимании нового вопроса; изменение уже предусмотренного параметра выполняется непосредственно кодом.

Это не доказательство свободной рыночной ниши: похожие части сценария уже есть у других продуктов. Выбор обоснован сочетанием условий конкретного проекта — русский язык, свои локальные данные, небольшой компьютер, отсутствие обязательного облачного сервиса и возможность понять происхождение результата.

## Что уже есть и чего пока нет

В текущем [интерфейсе](../../../frontend/README.md) уже показываются таблица и раскрываемый SQL; есть отмена, этапы обработки и сообщение об усечении выдачи. Поэтому «показывать SQL» нельзя записывать как новую возможность. Новый смысл появляется, когда результат становится сохраняемым объектом, а его условия можно менять предсказуемым способом.

[Граф агента](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/agent/graph.py) начинает каждый новый вопрос с поиска контекста и затем генерирует SQL. Путь выполнения сохранённого рецепта отсутствует. [QueryResult](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/domain/query.py) содержит SQL, названия колонок, строки и признак усечения, но не типы результата, идентификатор запуска, версию источника или определения показателей. [Клиент](../../../frontend/README.md) привязывает работу к живой UI-сессии, а [маршрут запроса](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/routes/queries.py) хранит задания в памяти.

API начинает обслуживать запросы только после [создания всех сервисов](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/dependencies.py#L61): подключения к PostgreSQL, загрузки embedder, reranker и LLM. Обещание «можно открыть историю без модели» требует менять этот порядок; одного нового экрана недостаточно. [Launcher](../../../run.py#L95) также выполняет подготовку до запуска API и UI.

## Три возможных направления и их настоящая цена

### A. Помощник с проверенными расчётами и повторяемыми рецептами

Пользователь приходит за ответом и регулярно возвращается к похожим вопросам. Ценность возникает от того, что «выручка» сохраняет определение, период меняется явно, а новое число можно сопоставить с предыдущим. Для CPU это также способ не генерировать похожий SQL повторно.

Подобная идея существует в зрелых системах: MetricFlow умеет локально запрашивать определённые показатели и разрезы командами `mf query`, а Rill компилирует обращения к именованным мерам в SQL. Это подтверждает применимость детерминированного пути, но не необходимость переносить их полный стек в этот проект. [MetricFlow](https://docs.getdbt.com/docs/build/metricflow-commands), [Rill Metrics SQL](https://www.rilldata.com/blog/introducing-metrics-sql-a-sql-based-semantic-layer-for-humans-and-agents).

Главная цена — подготовка определений. Если перед первым вопросом требовать заполнить словарь, кардинальности всех связей и формулы, помощник превращается в инструмент для инженера данных. Поэтому вход должен оставаться свободным, а проверенные рецепты появляться постепенно: сначала полезный ответ, затем явное сохранение и настройка разрешённых изменений.

Риск — создать видимость гарантии. Успешное выполнение SQL не подтверждает бизнес-смысл, а отметка пользователя не доказывает корректность всех будущих параметров. Проверка относится к конкретной версии рецепта, допустимым параметрам и источнику. При изменении структуры источника рецепт может потребовать повторной проверки.

**Выбор:** основное направление. Начинать с нескольких узких рецептов, а не с универсальной семантической платформы.

### B. Рабочее пространство для исследования данных

Пользователь задаёт цепочку вопросов, сопоставляет результаты, возвращается к предыдущему шагу, меняет представление таблицы и иногда редактирует SQL. Главный объект здесь — исследование с результатами, а не одна переписка.

Hex уже связывает разговор с проектом, который можно открыть как notebook или app; агент также ищет подходящие существующие приложения. Это полезный ориентир: повторное использование найденного расчёта часто ценнее очередной генерации. Однако повторять всю многооконную среду Hex для одного локального пользователя неоправданно. [Hex Threads](https://learn.hex.tech/docs/explore-data/threads).

Исследование Microsoft Data Formulator показывает другой полезный принцип: естественный язык можно сочетать с прямым управлением полями и визуализацией, а историю использовать для возврата к предыдущему результату. Для нашего проекта это аргумент за понятные контролы периода, разреза и графика. Это не доказательство того, что всякий пользователь предпочитает сложный canvas: результаты исследовательского прототипа нельзя переносить на наш интерфейс без проверки. [Microsoft Research](https://www.microsoft.com/en-us/research/blog/data-formulator-exploring-how-ai-can-help-analysts-create-rich-data-visualizations/).

Главная цена — количество независимых состояний: активный анализ, выбранный запуск, несохранённые изменения параметров, выполняющееся задание, фильтр представления, условия SQL, выбранная строка и вид графика. Если разработчик не различает их, интерфейс показывает старые числа под новыми фильтрами или теряет работу при переходе между экранами.

**Выбор:** тонкое рабочее пространство как оболочка направления A. В первой версии достаточно списка анализов, одного открытого результата и истории его запусков. Разветвлённые notebook-проекты и произвольные панели можно добавить после подтверждённой потребности.

### C. Лёгкая аналитика файлов с DuckDB

Пользователь получает CSV или Parquet и хочет быстро посмотреть данные, сгруппировать их и задать вопрос, не поднимая PostgreSQL и не проходя миграцию SQLite. Это меняет прежде всего вход в продукт и способ хранения данных.

DuckDB уже предлагает локальный UI, а Tad — просмотр и агрегацию файлов. Следовательно, «умеет открыть CSV локально» полезно, но само по себе не делает проект особенным. Возможное отличие — понятный вопрос на русском, проверяемый расчёт и дальнейшая работа без ожидания LLM. [DuckDB UI](https://duckdb.org/docs/current/core_extensions/ui), [Tad](https://www.tadviewer.com/).

Замена PostgreSQL требует пересмотреть SQL-диалект, типы и даты, режим чтения, доступ к файлам, отмену, импорт, бэкап и совместимость существующих тестов. В DuckDB `SELECT` может вызывать функции чтения файлов; текущая отдельная PostgreSQL-роль не переносится автоматически в embedded engine. Ограничения доступа должны задаваться на уровне встраивания и разрешённых операций. [Securing DuckDB](https://duckdb.org/docs/current/operations_manual/securing_duckdb/overview).

Также embedded не означает гарантированно малое потребление памяти. DuckDB умеет выгружать часть промежуточных данных на диск, но не все операции одинаково ограничиваются `memory_limit`; тяжёлая аналитика конкурирует за RAM с моделью. Проверять надо весь сценарий на ноутбуке, а не только скорость одного SQL. [DuckDB: tuning workloads](https://duckdb.org/docs/current/guides/performance/how_to_tune_workloads).

**Выбор:** простой импорт файлов нужен раньше смены движка. DuckDB стоит отдельно проверить как вариант облегчённого запуска, если обязательный Docker/PostgreSQL действительно мешает целевому пользователю. Не держать одновременно два аналитических движка без сценария, который оправдывает оба.

## Пять решений, которые стоит принять

### 1. Сохранять расчёт и его результаты как разные вещи

Сохранённый анализ отвечает на вопрос «что и как считать», запуск — «что получилось на этих данных в это время». У анализа есть имя, рецепт или проверенный SQL, параметры по умолчанию и настройки представления. У запуска — фактические параметры, версия определения, сведения об источнике, SQL, ограниченный результат, статус и продолжительность.

Это сразу даёт полезные функции: вернуться к вчерашнему ответу, пересчитать сегодняшний, сравнить два периода, повторить анализ после обновления данных. Не требуется с первого дня хранить все полные копии исходных баз. Если старый источник не сохранён, приложение честно позволяет открыть сохранённый результат, но не обещает пересчитать его на прежних данных.

Для одного API-процесса достаточно небольшого SQLite-хранилища метаданных и ограниченных файлов результатов. Его следует держать отдельно от анализируемого PostgreSQL. Текущий [drop_all_schemas](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/database/metadata.py#L65) удаляет все пользовательские схемы кроме `public`, а пользователь ранее отказался ограничивать действие только схемами, созданными приложением. Служебная история не должна случайно попадать ни в этот список, ни в SQL-контекст. Предлагаемое хранение не меняет согласованную область удаления данных.

Отдельный SQLite не даёт общей транзакции с PostgreSQL. Поэтому импорт записывает намерение и итог, а восстановление после сбоя сверяет состояние источника; оно не повторяет разрушительный импорт вслепую. Первая версия резервной копии должна блокировать изменения на время согласованного сохранения метаданных и локальных данных. Копирование открытого SQLite-файла заменяется штатным backup API. [SQLite backup](https://www.sqlite.org/backup.html).

**Граница первой версии:** история и сохранённый анализ, без системы веток, общих папок команды и полного версионирования всех входных файлов. Сложность M–L. Готово, когда перезапуск сохраняет результаты и повторный расчёт создаёт новый запуск, не переписывая предыдущий.

### 2. Разделить поиск контекста, смысл показателя и повтор исполнения

Сейчас [retriever](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/rag/retrieval/retriever.py) ищет подходящие описания таблиц, а [ContextBuilder](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/rag/retrieval/context.py) добавляет связанные таблицы. Это полезный поиск кандидатов. Векторная близость не определяет, что считать оплаченным заказом, какое поле даты использовать и можно ли суммировать показатель после соединения.

Определение проверенного расчёта должно жить отдельно: название, формула или сохранённый SQL, единица, обязательные условия, допустимые разрезы и параметры, связанные таблицы, версия. Retrieval может помочь найти это определение, но не должен незаметно его изменять. Такой разрыв между физической схемой и явным смыслом также отражён в Wren MDL; нам полезен принцип, а не необходимость реализовать весь его язык. [Wren: MDL](https://docs.getwren.ai/oss/concepts/what_is_mdl).

В интерфейсе нужны три разных пути выполнения:

| Действие пользователя | Что выполняется | Почему это важно |
| --- | --- | --- |
| Сменить вид графика или отсортировать уже полученные строки | Представление сохранённого результата | Не нужны SQL, retrieval и LLM; нельзя выдавать это за пересчёт всей базы |
| Изменить разрешённый период или значение фильтра в рецепте | Типизированные параметры → построение SQL → проверка → БД | Нужен новый запуск, но не генерация модели |
| Задать принципиально новый вопрос | Разрешение неоднозначности, поиск контекста, генерация и проверка | Здесь LLM действительно приносит пользу |

Для русского языка полезнее проверять реальные затруднения: «оборот» и «выручка», `paid` и «оплачено», разные поля даты, падежи названий и значения с апострофами. В RedSQL показаны 409 русскоязычных пар вопросов и SQL в девяти предметных областях; результаты авторов подтверждают, что успех на общих академических задачах нельзя считать доказательством работы с новой областью. Это аргумент за собственный маленький набор проверок на пользовательских данных, а не обещание перенести опубликованную точность в наш стек. [RedSQL](https://aclanthology.org/2025.bsnlp-1.9/).

Неоднозначность нужно разрешать конкретным вопросом: «Дата создания заказа или дата оплаты?» вместо общего отказа «недостаточно контекста». Наличие двух правдоподобных SQL-интерпретаций — известная отдельная проблема; AmbiQT исследует именно её. При этом нельзя показывать произвольный процент уверенности, который никто не калибровал. [AmbiQT](https://arxiv.org/abs/2310.13659).

**Граница первой версии:** несколько сохранённых рецептов с явными параметрами; одна таблица либо заранее проверенный неизменяемый путь соединения. Сложность M для узкого каталога. Готово, когда изменение разрешённых параметров не вызывает LLM и сохраняет обязательные условия расчёта.

### 3. Разрешить приложению быть полезным без загруженной модели

Просмотр результатов, сортировка, экспорт, работа с уже подготовленными рецептами и просмотр структуры данных не должны требовать наличия GGUF в памяти. Сейчас это невозможно из-за общего [построения сервисов](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/dependencies.py#L93). Первое изменение — разделить готовность приложения, доступность БД и состояние модели.

У модели достаточно состояний `unloaded`, `loading`, `ready`, `unloading`, `failed`. Загрузка выполняется один раз при первом необходимом обращении; второй запрос ожидает тот же процесс загрузки. Отмена одного ожидающего запроса не должна разрушать общую загрузку. Одновременная загрузка двух больших моделей для переключения на 24 ГБ RAM не подходит.

Не стоит выгружать LLM, embedder и reranker после каждого вопроса: можно снизить RAM в покое ценой повторного чтения весов и длинной паузы на каждое действие. Сначала имеет смысл проверить более дешёвую альтернативу: на маленькой выбранной схеме, если весь необходимый контекст действительно помещается в токены, обходить тяжёлый retrieval и reranker. Это гипотеза для измерения, а не готовое правило по одному числу таблиц: две очень широкие таблицы могут быть дороже двадцати маленьких.

Одна тяжёлая операция одновременно остаётся разумной для такого ноутбука. Существующий [OperationGate](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/dependencies.py#L14) и [ожидание фактической очистки](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/core/concurrency.py) стоит сохранить для генерации, импорта, реиндексации, удаления и переключения модели. Просмотр истории, состояния и отмена не должны ждать этой блокировки.

Долговечные задания можно реализовать без Redis: SQLite хранит очередь и итог, один worker выполняет тяжёлую работу. HTTP-подключение становится подпиской на уже существующее задание. После перезапуска незавершённое вычисление помечается прерванным; продолжения с последнего токена обещать не надо. Клиентский [таймер сессии](../../../frontend/README.md) тоже нужно пересмотреть, иначе он отменит работу даже после изменения серверного маршрута.

При измерении фиксировать холодный запуск, время подготовки контекста, prefill, генерацию, SQL и пиковую память всего сценария. `llama-bench` помогает раздельно измерить prompt processing и token generation, но не заменяет замер приложения. Снижение `n_ctx` и перебор числа CPU-потоков требуют измерений на конкретной машине; «14 ядер» недостаточно для правильного фиксированного значения. [llama-bench](https://github.com/ggml-org/llama.cpp/blob/master/tools/llama-bench/README.md).

**Граница первой версии:** открыть историю и повторить рецепт без LLM; одно тяжёлое задание, корректная отмена и восстановление статуса. Сложность M–L. Полный интерфейс ещё до запуска PostgreSQL и до скачивания весов — отдельное изменение launcher, а не автоматическое следствие lazy loading.

### 4. Улучшить вход через файлы раньше смены PostgreSQL

Сейчас [upload](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/routes/schemas.py#L17) принимает SQLite. Для обычного пользователя файл продаж чаще начинается с таблицы в CSV или Excel. Даже небольшой импорт CSV с понятным предпросмотром расширяет реальную аудиторию сильнее, чем ещё один способ выбора модели.

Нужен не только новый suffix в списке расширений. Пользователь должен увидеть разделитель, заголовок, типы и несколько исходных значений; `00123` нельзя незаметно превратить в число, а `01.02.2026` — интерпретировать без выбранного формата даты. Импорт сохраняет выбранные правила и отчёт об ошибочных строках. Пропуск строк по умолчанию создаёт скрытое расхождение итогов.

Начать стоит с CSV; Parquet удобен, когда нужны заранее типизированные данные. XLSX добавляет выбор листа, пустые и объединённые области, формулы и их сохранённые значения, поэтому его следует делать после подтверждения пользовательского сценария. Для всех форматов нужен потоковый или ограниченный по памяти путь; загрузка нескольких полных копий таблицы в pandas конкурирует с моделью.

DuckDB-пилот оправдан, если на одинаковом наборе вопросов и файлов он заметно сокращает путь от чистой установки до первой таблицы, потребление памяти и время импорта, не ухудшая корректность типов и отмены. Проверять нужно Windows и Linux, отсутствие сети после подготовки, перезапуск, замену файла, запрет обращения к произвольным файлам и пиковую память при агрегации вместе с LLM. Решение по движку принимается после этого пилота.

Наличие локального UI у технологии нельзя автоматически считать гарантией офлайн-работы: документация DuckDB UI прямо указывает загрузку файлов интерфейса с удалённого сервера, хотя сами запросы по умолчанию выполняются локально. Для обещания «после подготовки работает без сети» ресурсы собственного UI должны поставляться вместе с приложением. [DuckDB UI](https://duckdb.org/docs/current/core_extensions/ui).

**Граница первой версии:** предпросмотр и контролируемый CSV-импорт в существующий путь данных, без одновременной замены БД. Сложность M–L. Готово, когда повторный импорт с сохранёнными настройками даёт те же типы и явный отчёт обо всех непринятых строках.

### 5. Менять фронтенд ради рабочего процесса, а не ради списка технологий

История, ссылки на результаты, график и формы сами по себе не требуют React. Streamlit поддерживает URL-параметры, а фрагменты позволяют обновлять часть интерфейса; в текущем приложении фрагмент уже используется. Серверное хранение устраняет потерю результатов независимо от UI-фреймворка. При этом Session State сам по себе связан с WebSocket и не заменяет такое хранение. [URL-параметры](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.query_params), [фрагменты](https://docs.streamlit.io/develop/api-reference/execution-flow/st.fragment), [Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state).

React с TypeScript становится оправданным, когда главным ежедневным сценарием будут несколько открытых результатов и локальные взаимодействия между таблицей, графиком и контролами. Он позволяет явно моделировать это состояние в клиенте. Но таблица, доступность с клавиатуры, маршрутизация, загрузки, ошибки и сохранение состояния потребуют реализации — React не предоставляет готовую аналитическую среду.

До решения о миграции стоит проверить три сквозных сценария на небольшом прототипе:

1. Выделить категорию на графике, увидеть согласованное выделение или фильтр таблицы, вернуть исходное представление; ни один шаг не запускает LLM и не меняет незаметно условия SQL.
2. Открыть другой сохранённый анализ, вернуться назад, увидеть прежние фильтры представления и выполняющееся задание; переключение экрана не отменяет расчёт.
3. Изменить период, явно запустить пересчёт, до готовности видеть подпись старого результата, затем сопоставить новый запуск с предыдущим.

Если эти сценарии требуют на Streamlit множества отдельных JS-компонентов и обходов его модели состояния, React — разумный выбор. Если следующая версия по-прежнему состоит из одной формы и одного результата, перенос создаст больше работы, чем пользовательской пользы. Граница определяется сценариями, а не количеством строк `app.py`.

Для выбранного рабочего пространства достаточно статического клиентского приложения и существующего Python API; SSR и новый Node-сервис не следуют из этих требований. Сборка фронта должна оставаться частью одной команды запуска. Отдельно нужно решить доступ браузера к API: текущий Python-клиент хранит доступ на серверной стороне, и этот секрет нельзя просто перенести в статический JS-бандл.

marimo — содержательная альтернатива, если продукт переориентируется на аналитика, который хочет редактировать Python/SQL notebook. Он поддерживает SQL, зависимости между ячейками и связанные контролы. Для человека, ожидающего «спросил — получил таблицу», такое изменение вводит новую модель работы и не даёт очевидного выигрыша. [marimo SQL](https://docs.marimo.io/guides/working_with_data/sql/).

**Выбор:** не связывать историю и рецепты с обязательной миграцией. Сначала контракт и хранение результатов, затем небольшой React-прототип перечисленных взаимодействий. Миграция оправдана при выборе полноценного рабочего пространства; её нельзя продавать как оптимизацию RAM модели. Сложность L для законченной замены.

## Проверка самой дешёвой сильной идеи: рецепт без LLM

[recipe_probe.py](recipe_probe.py) — изолированный исследовательский скрипт. Он создаёт 50 000 синтетических заказов в SQLite в памяти, строит SQL через SQLGlot AST и пропускает его через существующий `SQLValidator`. Производственный executor не используется; SQL для проверки результата переводится из PostgreSQL в SQLite. Проверяемая формула — сумма сумм оплаченных заказов в копейках по городу или каналу, с полуоткрытым периодом `[начало, конец)` и необязательным городом.

Результат сравнивается с независимо написанным Python-расчётом, который проходит по исходным строкам и суммирует подходящие значения. В данных есть неоплаченные заказы и NULL-суммы. Проверены другой период, смена разрешённого разреза, пустые результаты, значение с апострофом и текст, похожий на SQL-инъекцию, который остаётся обычным значением города. Неверная дата, пустой период, неизвестный разрез и неканоническая запись даты отклоняются.

| Проверка | Первый процесс | Повтор в новом процессе |
| --- | --- | --- |
| Результаты совпали с Python-эталоном | 9 из 9 | 9 из 9 |
| Неверные параметры отклонены | 4 из 4 | 4 из 4 |
| Вызовы LLM | 0 | 0 |
| Медиана построения AST и текущей SQL-проверки, 30 повторов | 2,586 мс | 2,547 мс |
| Медиана SQLite-выполнения, 30 повторов | 15,309 мс | 14,677 мс |

Исходные результаты: [первый запуск](recipe_probe.json), [повтор](recipe_probe_repeat.json). Среда: Python 3.12.10, SQLGlot 28.10.1, SQLite 3.49.1. Данные детерминированы; временные значения зависят от нагрузки машины. Эти числа не измеряют PostgreSQL, память модели, UI, JOIN, многопользовательскую нагрузку или скорость ноутбука пользователя. Эксперимент подтверждает узкое свойство: полезный повтор с параметрами можно выразить небольшим кодом без генерации и без изменения существующего валидатора.

Есть конкретная интеграционная граница: [список разрешённых AST-узлов](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/sql/validation.py#L9) сейчас не допускает placeholders; probe подтвердил отказ для `:city`. [SQLExecutor](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/database/executor.py#L79) принимает проверенную SQL-строку, а не пару statement/parameters. В probe используются AST-литералы и повторная проверка. Для bind-параметров в будущем потребуется согласованное расширение контракта executor и validator. Строковая замена значений в сохранённом SQL для этого не подходит.

Обычный запуск в Python-окружении проекта, где установлены зависимости:

```text
python -m docs.research.platform.recipe_probe
```

В использованной здесь служебной среде выполнялась команда из корня репозитория:

```text
.tools\python\python.exe -c "import sys,runpy; sys.path[:0]=['.','.tools/test-packages']; runpy.run_path('docs/research/platform/recipe_probe.py',run_name='__main__')"
```

## Каталог рецептов или собственная семантическая платформа

Для ближайшей версии выбирать **каталог рецептов**. Различие не сводится к тому, хранить определения в YAML или SQLite. Универсальная платформа обязана решать произвольные композиции мер, разрезов и связей: grain, fan-out, несколько фактов, distinct, средние, отношения, временные окна, разное качество ключей и несколько SQL-диалектов. Это самостоятельный аналитический движок с собственными ограничениями и большим набором тестов.

Компактный рецепт фиксирует форму расчёта. Например, `paid_order_revenue_by_city_v1` хранит известное выражение, обязательное `status = 'paid'`, поле даты, допустимые параметры периода и города, единицу, схему результата и контрольный пример. Пользователь меняет предусмотренные параметры. Выбор нового произвольного пути JOIN или новой формулы создаёт другой расчёт и требует проверки.

Даже Rill в опубликованной модели Metrics SQL намеренно ограничивает один запрос одним metrics view и не поддерживает JOIN между такими views. Это полезный прецедент ограничения области применимости, а не недостаток, который нужно немедленно «исправить» в нашем проекте. [Ограничения Metrics SQL](https://www.rilldata.com/blog/introducing-metrics-sql-a-sql-based-semantic-layer-for-humans-and-agents).

Не надо автоматически превращать каждый литерал успешного SQL в редактируемый параметр. Дата может быть пользовательским периодом, а `paid` — обязательной частью определения; их роли различаются. Рецепт явно объявляет разрешённые изменения и проверяет их до SQL. Сохранение произвольного запроса полезно само по себе, но не делает его управляемой бизнес-метрикой.

Минимальный состав без преждевременных абстракций:

- данные рецепта: идентификатор, версия, имя, проверенный SQL или ограниченная структура, явные параметры и зависимости от таблиц;
- функция проверки параметров и построения SQL, использующая текущую SQL-проверку;
- выполнение через существующий read-only executor и OperationGate;
- запись нового запуска в историю; хранение результата отдельно от определения;
- экран разрешённых параметров и просмотра условий расчёта.

В первую версию не входят собственный язык выражений, автоматический поиск безопасного grain, универсальная оптимизация мер, граф зависимостей семантических объектов и совместимость со всеми существующими semantic-layer форматами. Позже можно выделить общую формулу показателя из нескольких реальных рецептов, когда такое повторение появится в данных проекта. Не стоит строить всю иерархию заранее.

**Условие пересмотра решения:** реальные пользователи регулярно запрашивают комбинации проверенных показателей и разрезов, которые невозможно разумно покрыть каталогом, а ручное сопровождение рецептов создаёт дублирование и ошибки. Тогда нужно отдельно сравнивать интеграцию существующего движка с собственным ограниченным компилятором, а не расширять незаметно несколько helper-функций до новой платформы.

## Пять идей, которые сейчас стоит отвергнуть или отложить

1. **Универсальная семантическая платформа с произвольными JOIN.** Её цена определяется корректностью расчёта при разных уровнях детализации, а не количеством классов. Начальный каталог даёт большую часть практической пользы для повторяемых вопросов с существенно меньшей областью ответственности.
2. **Одновременная замена фронта, PostgreSQL, inference runtime и формата метаданных.** Не останется стабильного эталона поведения; сбои трудно будет связать с конкретным решением. Контракт результата и история полезны в любом из вариантов и должны появиться раньше крупных миграций.
3. **Несколько LLM-агентов, постоянный critic и переход на 27B как главный способ улучшения продукта.** Каждый дополнительный вызов расходует CPU-время, а модели конкурируют за память. Сначала нужен набор ошибок, который не исправляется определениями, контекстом и детерминированным исполнением. Если сложный вопрос всё же требует большего бюджета, это отдельный измеренный режим.
4. **Универсальный агент, выполняющий произвольный Python над пользовательскими файлами.** Это меняет модель доверия и ресурсные ограничения, вводит исполнение кода и непредсказуемое копирование данных. Для выбранных задач достаточно контролируемых SQL-операций и заранее реализованных аналитических приёмов.
5. **Многопользовательская облачная платформа, совместное редактирование и desktop-обёртка в первом релизе.** Они решают другие задачи и увеличивают требования к сессиям, синхронизации, обновлениям и упаковке. Для одного человека сначала важнее рабочий локальный сценарий, восстановление после перезапуска и одна понятная команда запуска.

## Что подтвердит, что направление выбрано правильно

Проверять следует не количество новых кнопок, а законченный повторяемый сценарий. Человек получает первую полезную таблицу без подготовки полного словаря; видит, что посчитано; сохраняет анализ; меняет месяц без нового ожидания LLM; после перезапуска находит оба результата и понимает различие между ними. Ни график, ни экспорт не превращают усечённую выборку в видимость полного набора данных.

Для решения о следующем усложнении собирать небольшое число наблюдений: сколько уточнений потребовалось, где менялся смысл показателя, сколько времени занял первый ответ и повтор с параметрами, какие действия действительно использовались, какой был пик RAM и удалось ли восстановить состояние после закрытия вкладки. Выбор React, DuckDB и более крупной модели затем опирается на конкретный неудачный участок этого сценария.

# Три улучшения, которые делают локального помощника надёжнее

Исследование от 1 октября 2026 года. Цель — получать понятные расчёты на ноутбуке с 24 ГБ RAM, сохранив небольшое приложение. Здесь рассматриваются три связанные возможности: управляемый расчёт, содержательное уточнение и проверяемое объяснение результата. Это уточнение направления из [FEATURES.md](../../FEATURES.md), а не новый список десятков функций.

Главная идея: **модель помогает выбрать смысл вопроса, а согласованный расчёт выполняется по небольшому проверенному правилу**. Для неподготовленных данных остаётся существующая генерация SQL. Пользователь видит, применялось ли конкретное определение показателя; приложение не приписывает свободному SQL гарантии, которых у него нет.

Рабочий пример: «Выручка за январь по странам» → при необходимости выбрать дату оплаты или создания → увидеть сумму, условия и неизвестные данные → заменить период без повторного изобретения SQL. Если следующий вопрос требует распределить заказ между товарными категориями, приложение объясняет отсутствующее правило распределения, а не просто присоединяет позиции заказа.

## Что действительно проверено

[experiments.py](experiments.py) запускает SQLite в памяти и небольшие вычисления Python. Все таблицы созданы синтетически. Проверки не запускают PostgreSQL, LLM, API или Docker, не измеряют качество русского языка и не сравнивают модели. Никакой production-код не изменён. Числа ниже нельзя использовать как оценку точности Text-to-SQL.

Зафиксированный результат находится в [results.json](results.json). Среда первого прогона: Python 3.12.10, SQLite 3.49.1. Деньги представлены целым количеством копеек; деление выполняется Decimal. Это позволяет отделить ошибки смысла от округления SQLite, но не проверяет денежные типы PostgreSQL.

| Опыт | Наблюдение | Практическое следствие |
| --- | --- | --- |
| Четыре ошибочных SQL на одной обычной БД | Все четыре дают правильные 300 рублей | Одной успешной таблицы недостаточно для подтверждения правила |
| Добавление неоплаченного заказа | SQL без обязательного фильтра выдаёт 350 вместо 300 | Условия метрики должен сохранять исполнитель, а не только промпт |
| Вторая позиция существующего заказа | JOIN с позициями выдаёт 400 вместо 300 | Существующие GBNF и AST принимают этот запрос; нужна семантика сущности |
| Два разных заказа с одинаковой суммой | SUM DISTINCT даёт 100 вместо 200 | Уникальность значения не заменяет уникальность заказа |
| Заказ без назначенного клиента | INNER JOIN теряет 50 рублей | Даже связь без размножения может уменьшить исходную совокупность |
| Заказ относится к двум категориям | Сумма категорий — 1200, общий итог — 1100 | Устранение дублей внутри категории не задаёт правило распределения |
| Один заказ попал в две категории, другой потерян | Сумма категорий совпала с правильным итогом 200 | Сверка общего числа необходима, но сама по себе не доказывает правильный состав строк |
| Месячные средние 100 и 900 рублей при 2 и 1 заказе | Среднее этих средних — 500; общий средний чек — 366,66… | Для повторного расчёта среднего нужны исходная сумма и число заказов |
| Пустая выборка, неизвестная сумма и известный ноль | Все состояния различимы по SUM, COUNT(*) и COUNT(amount) | NULL нельзя оформлять как нулевую выручку без определения |
| Создание и оплата сначала происходят в одном месяце | Два разных смысла вопроса дают одинаковые 300 рублей | Совпадение текущих результатов не устраняет неоднозначность |
| Поздняя оплата пересекает границу месяца | Те же интерпретации дают 350 и 300 рублей | Уточнение выбирает смысл, а не наиболее удобное число |
| Одинаковый момент времени: 1 марта 00:30 UTC+3 | «Прошлый месяц» в UTC — январь, в UTC+3 — февраль | Временная интерпретация входит в план, а не берётся неявно от сервера |
| 60 воспроизводимых случайных наборов | 360 сравнений результатов трёх метрик с независимым Python-расчётом прошли | Малое поддержанное подмножество можно проверять предметно |

Опыты с неправильным SQL намеренно включают SUM DISTINCT: текущий язык проекта такую форму SUM не допускает. Она показывает ошибочность распространённого исправления, а не новую уязвимость приложения. Отдельный опыт `current_validator` проверяет именно принимаемый сейчас JOIN/SUM через настоящий SQLValidator и тестовый распознаватель GBNF. Это не нативный прогон генерации llama.cpp.

## 1. Управляемый расчёт вместо повторного написания одной формулы

### Пользовательский сценарий и эффект

Пользователь сохраняет «Оплаченная выручка по странам», затем меняет январь на февраль. Показатель, обязательный статус и способ соединения таблиц сохраняются. Изменение периода не требует нового ответа LLM. На CPU это полезно и для скорости, и для предсказуемости.

Для обычных группировок модель выбирает известный показатель, измерение, фильтр и период. Она не придумывает JOIN и повторно не выводит формулу. SQL собирается кодом из небольшого набора разрешённых форм. Это адаптация принципа, применяемого в Looker: модель выбирает поля и условия, а семантический слой формирует запрос. Это не перенос измерений качества Looker на местную модель. [Устройство Conversational Analytics](https://docs.cloud.google.com/looker/docs/conversational-analytics-overview).

### Минимальный план

```json
{
  "metric": "paid_revenue",
  "group_by": "country",
  "country": "RU",
  "start": "2026-01-01",
  "end": "2026-02-01",
  "date_basis": "paid_on",
  "catalog_version": 1
}
```

В прототипе существуют только три показателя: сумма оплаченных заказов, число оплаченных заказов и их средний чек. Для первых двух денежных показателей неполные суммы не считаются полной выручкой. Допустимые разрезы — страна и месяц. Основа — orders; единственная связь с customers требует подтверждённого уникального ключа на стороне клиента. Для отображения неизвестного клиента используется LEFT JOIN. Фильтр страны намеренно исключает записи без этой страны.

Статус `paid` принадлежит определению показателя и не может быть заменён отдельным значением модели. Названия SQL-источников выбираются из кода, значения фильтров передаются параметрами. Период имеет полуоткрытые границы: начало включено, конец исключён. Выбранное поле даты управляет и фильтром периода, и месячной группировкой.

Это исследовательский шаблон SQLite. Он не вставлен в приложение и не совместим с текущим API исполнителя без доработки. В рабочей реализации потребуются PostgreSQL-выражения времени, передача параметров и согласованная проверка SQL. Созданный кодом SQL тоже не должен обходить ограничения источников, роли чтения и таймаутов.

### Что поместится в маленький план

| Семейство | Пример | Достаточная форма | Граница |
| --- | --- | --- | --- |
| Один показатель | Сколько оплаченных заказов? | Metric | Определение существует в каталоге |
| Сумма или среднее | Выручка и средний чек | Известная сумма либо отношение компонентов | Нельзя автоматически усреднять готовые средние |
| Разрез | Выручка по странам | Metric + одно измерение | Измерение сохраняет смысл и зерно показателя |
| Динамика | Выручка по месяцам | Metric + календарная группировка | Известны роль даты, зона и границы |
| Отбор | За январь, только Россия | Типизированные фильтры и период | Не произвольный логический язык |
| Рейтинг | Пять стран с наибольшей выручкой | Предыдущая форма + сортировка + top-N | Малое продолжение прототипа; точный порядок должен вычисляться в БД |
| Два периода | Этот месяц относительно прошлого | Два запуска одного плана + проверка совместимости | Сравнение не меняет определение и единицы |
| Смена параметра | Теперь Казахстан | Изменение одного слота существующего плана | Остальные условия сохраняются |

Рейтинг и сравнение описаны как граница следующего шага, а не реализованные возможности прототипа. Первую реализацию разумно ограничить одной таблицей фактов, одним-двумя измерениями и простыми AND-фильтрами. Для усложнения фильтров сначала нужен пользовательский сценарий, а не универсальный язык выражений.

**Нет основания утверждать, что это покрывает 70–80% реальных запросов.** Такой процент — проверяемая продуктовая гипотеза. Нужно собрать независимые вопросы хотя бы для двух разных предметных наборов, разметить требуемый смысл до проектирования шаблонов и посчитать полное покрытие без потери условий. Десять перефразировок одной группировки не должны изображать десять разных аналитических возможностей.

Не входят: свободные формулы, автоматическое распределение суммы заказа по категориям, независимые таблицы фактов, retention, воронки, произвольные окна, нетиповые коррелированные подзапросы и иерархии. Для частого сложного расчёта можно позже добавить один явно описанный рецепт. Добавлять универсальное дерево всех SQL-конструкций сейчас не стоит: это превратит маленький план во второй SQL-компилятор.

### Минимальная архитектура и связь с кодом

Достаточно структур `MetricDefinition`, `AnalysisPlan` и `CalculationReceipt`, небольшой проверки плана и сборщика нескольких SQL-форм. Нового сервиса, второй LLM или отдельного semantic engine не требуется. [Текущий агент](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/agent/graph.py) может выбирать между существующей генерацией SQL и новым поддержанным расчётом; общий исполнитель и ограничения сохраняются. Физическая [TableSchema](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/domain/schema.py) и предметное определение остаются разными сущностями.

Сначала — 5–10 определений демонстрационного набора. Для произвольной загруженной БД модель может предложить черновик определения, но название `amount` не доказывает его смысл. Нельзя объявить автоматически созданный черновик проверенной выручкой. Работа с незнакомыми данными остаётся доступной через текущий SQL-сценарий и понятное описание использованного способа расчёта.

Кардинальности и ключи как основа допустимых соединений используются и в MetricFlow. Это подтверждает полезность подхода, но не гарантирует правильность наших определений. [Логика соединений MetricFlow](https://docs.getdbt.com/docs/build/join-logic).

### Сильная альтернатива и критерий остановки

Альтернатива — сохранить свободную генерацию SQL, обогатить промпт определениями и добавить анализатор подозрительных JOIN. Она дешевле на старте и охватывает больше форм. Её недостаток: для каждой повторной просьбы модель снова может изменить смысл, а универсальная проверка соответствия произвольного SQL бизнес-определению сложна.

Малый план имеет смысл, если повторяемые семейства действительно занимают большую долю вопросов и не требуют ручной разработки нового шаблона почти каждый раз. Если независимый корпус показывает низкое полное покрытие, каталог быстро разрастается или пользователи не могут задать понятные определения, следует оставить план для избранных отчётов. Не нужно расширять его до универсальной аналитической платформы ради достижения заранее названного процента.

## 2. Уточнение, которое меняет ровно нужную часть расчёта

### Пользовательский сценарий и эффект

«Выручка в январе» → «Период по дате оплаты или создания заказа?» → «По оплате» → таблица. Затем «Только Россия» изменяет фильтр страны, сохраняя показатель и временную основу. Принятые решения отображаются рядом с вопросом и доступны для изменения.

Полезное отличие — приложение работает с конечным числом известных смысловых вариантов, а не начинает длинную беседу ради беседы. Если определение уже закреплено, вопрос не задаётся. Если пользователь просит показать две интерпретации рядом и они обе допустимы, это может быть полезнее дополнительного выбора.

### Логика

Нерешённые слоты описываются отдельно: показатель, временная роль, путь связи, соответствие значения, правило распределения. Уточнение имеет идентификатор, альтернативы и связь с версией плана. Ответ применяет ограниченное изменение; остальные слоты не генерируются заново. Новый неизвестный фильтр не должен исчезать при преобразовании структуры.

Эксперимент проверяет, что неизвестный структурный слот `category` отклоняется, а не удаляется. Также отклоняются неизвестная метрика, изменение версии определения, неизвестная кардинальность и неполный период. Это проверка структурированного ввода. Она **не доказывает**, что LLM правильно перенесла каждое условие естественного языка в структуру.

Например, исходный текст «по странам без возвратов» может ошибочно превратиться в корректный план без условия возвратов. Валидатор структуры этого не обнаружит. Поэтому интерфейс показывает интерпретацию, а стенд качества отдельно проверяет сохранение существенных условий вопроса. Второй LLM-критик не делает это доказуемым автоматически.

### Что отвергнуто после опыта

Идея «не спрашивать, если обе трактовки сейчас дают одно число» выглядит удобной, но небезопасна. На исходной синтетике сумма по созданию и по оплате совпала — 300 рублей. После заказа с оплатой в следующем месяце получились 350 и 300. Совпадение одного результата не является эквивалентностью правил, особенно для сохранённого анализа.

Уточнять надо существенное различие смысла, а не любое различие формулировки. Если вопросы отличаются только известным синонимом одной утверждённой метрики, нового диалога не требуется.

### Минимальная архитектура и границы

Добавить `PendingClarification` и операции изменения плана; существующий граф получает состояние ожидания. LLM вызывается для первоначального разбора и сложных новых реплик, но не для применения нажатой кнопки. При ожидании пользователя не удерживаются модель, транзакция и общий gate. Не нужны отдельные агенты «аналитик», «критик» и «уточнитель» с постоянными проходами.

Работы PRACTIQ и CLARITY подтверждают, что неоднозначность бывает многочастной, а ответ пользователя не обязательно разрешает её полностью. Они не доказывают качество предложенного локального протокола. [PRACTIQ, NAACL 2025](https://aclanthology.org/2025.naacl-long.13/), [CLARITY, ACL Industry 2026](https://aclanthology.org/2026.acl-industry.86/).

Отказ от этой идеи в широком виде оправдан, если лишние уточнения заметно ухудшают прохождение простых вопросов, а разрешённые неоднозначности редко улучшают конечный результат. Тогда оставить только выбор известных метрик, даты и неоднозначных справочников. Измерять нужно не количество диалогов, а правильность ответа после уточнения и число необоснованных прерываний ответимых вопросов.

## 3. Результат, показывающий границы расчёта

### Пользовательский сценарий и эффект

Вместо непонятного «Выручка: NULL» пользователь видит один из разных случаев:

- заказов в выбранном периоде нет;
- два заказа есть, но у них не заполнены суммы;
- суммы двух заказов известны и действительно равны нулю;
- сумма рассчитана по известным значениям, но полная выручка не определена.

Вывод привязывается к явной политике показателя. Можно показать известную часть отдельно, но нельзя назвать её полным итогом без изменения определения. Число заказов при неизвестных суммах по-прежнему может быть достоверно вычислено.

### Логика и минимальный состав

Для поддержанных метрик вместе с результатом получать несколько контрольных агрегатов: число исходных сущностей, число известных значений и при необходимости число неизвестных дат. Это не ещё одна модель; часто нужны лишь дополнительные COUNT в том же запросе. Статусы формируются кодом и привязаны к версии определения.

В карточке показывается короткая запись: правило, единица, временные границы, исходные сущности, неполные данные и ограничение выдачи. Сведения о соединении и SQL раскрываются по запросу. Это проверяемое объяснение фактического расчёта, а не свободное рассуждение модели о том, почему её ответ верен.

Для средних и долей сохранять числитель и знаменатель, чтобы повторное объединение не усредняло средние. Для пересекающихся категорий показывать неаддитивность. Сумма заказа, присутствующего в двух категориях, может законно учитываться в обеих для определённого показателя; тогда общий итог нельзя получать суммой видимых категорий.

Поведение агрегатов с NULL и пустыми наборами описано в документации PostgreSQL: AVG использует ненулевые входы, COUNT(*) и COUNT(column) различаются, SUM пустого набора не превращается в ноль автоматически. Эксперименты демонстрируют эти ситуации в SQLite, а будущая реализация потребует отдельных PG-тестов. [PostgreSQL 16: агрегаты](https://www.postgresql.org/docs/16/functions-aggregate.html).

### Повторная критическая проверка прототипа

В эксперимент `counter_review` намеренно включены три ограничения собственного прототипа:

1. **Неизвестная дата скрывается фильтром периода.** Есть оплаченный заказ без paid_on. Диапазон WHERE исключает его, и прототип сообщает `complete` для оставшихся сумм. Этот статус означает лишь полноту суммы внутри выбранных строк. Он не доказывает полноту исходной совокупности. Для продукта нужны раздельные статусы и проверка неизвестных дат до временного фильтра в соответствующей области данных. Нельзя утверждать, что такой заказ определённо относится к выбранному месяцу; его принадлежность неизвестна.
2. **Правильная структура не доказывает понимание вопроса.** План без условия возвратов может быть структурно корректен. Это остаётся задачей оценки NL→plan и видимой интерпретации.
3. **Хеш плана не является снимком результата.** В прототипе plan_id зависит от структуры, но не содержит версии данных. Для сохранённого запуска нужны отдельный ID, ревизия данных, версия определения и зафиксированное время. Совпадение plan_id не доказывает совпадение чисел.

Таким образом, проверяемыми могут быть конкретные свойства: использована нужная формула, обязательный фильтр сохранён, известные ключи не размножают заказ, суммы не пропущены молча. Ни один такой факт не доказывает правильность всех данных или верность исходного бизнес-определения. На экране не нужен общий зелёный знак «ответ доказан».

### Контрпримеры как способ проверять правило

Для утверждённых рецептов полезен маленький набор изменяемых предметных данных. Добавить неоплаченный заказ, вторую позицию, одинаковую сумму другого заказа или NULL в допустимом поле — и проверить ожидаемое свойство. В стенде четыре неверных запроса совпадают с правильным на исходной базе, затем каждый выявляется отдельным изменением.

Это не предложение изменять пользовательскую БД при каждом вопросе. Контрпримеры живут в тестовых данных при разработке/редактировании рецепта. Инварианты должны соответствовать определению: добавление позиции не меняет сумму самого заказа, но может законно менять сумму позиций. Универсальная автоматическая генерация правильных инвариантов для любой таблицы не входит в первый вариант.

Отдельный опыт показывает предел обычной сверки итогов: один заказ на 100 попадает в две категории, второй заказ на 100 теряется. Категории всё равно складываются в правильные 200. Поэтому совпадение суммы детализации и итога — полезная проверка, но не замена правила происхождения и контроля ключей сущностей.

Исполнение на нескольких специально подобранных БД как приближение семантической проверки исследовано в Test Suite Accuracy. Такой набор усиливает проверку, но не становится полным доказательством эквивалентности произвольных SQL. [Semantic Evaluation with Distilled Test Suites](https://aclanthology.org/2020.emnlp-main.29/).

### Альтернатива и критерий остановки

Альтернатива — только текстовое описание SQL. Это проще и полезно для прозрачности, но не отличает неизвестную выручку от известного нуля и не обнаруживает размножение сущностей.

Если для каждого простого результата требуются многочисленные полные сканирования, подробные проверки следует делать при подготовке данных или по запросу. Профиль должен иметь версию и признак полноты. Выборочные сведения не могут обосновывать «пропусков нет». Первым выпуском достаточно покрыть SUM/COUNT/среднее на одном факте, сохраняя честное «не проверено» для остальных свойств.

## Как проверить решение на настоящей модели

Сначала выбрать вопросы до обучения промпта: повседневные суммы, разрезы, периоды и примеры за границей плана. Для одного и того же локального GGUF сравнить текущую генерацию SQL и выбор плана с одинаковыми каталогом, примерами и бюджетом повторов. Прототип не заменяет этот опыт.

Отдельно измерять полное покрытие вопроса, правильный конечный результат, пропущенные условия, необоснованные отказы, успешность уточнения, число вызовов модели, токены, время и общий расход RAM. Экономия на повторном изменении параметра логична по устройству: LLM не вызывается. Насколько это уменьшит задержку всего приложения, ещё не измерено.

Последовательность для небольшого первого выпуска:

1. Три–пять утверждённых расчётов одного набора данных, параметризованный SQL и контрольные примеры.
2. Выбор даты/метрики с сохранением решения, видимые параметры и явная граница неподдержанного вопроса.
3. Различение пустоты, нуля и неизвестных значений; запись фактически проверенных условий.
4. Сравнение с исходным SQL-сценарием на независимых вопросах. Расширение плана только после обнаружения частых неподдержанных семейств.

Это даёт заметную возможность: пользователь продолжает уже понятный расчёт, а приложение сохраняет его смысл. Главное ограничение остаётся явным: маленький план уменьшает свободу ошибиться внутри поддержанного расчёта, но не читает мысли человека и не создаёт отсутствующие бизнес-определения.

## Повторить эксперименты

Из корня репозитория обычным Python 3.12:

```text
python docs/research/quality/experiments.py --output docs/research/quality/results.json
```

В текущем рабочем окружении:

```text
.\.tools\python\python.exe docs/research/quality/experiments.py --output docs/research/quality/results.json
```

Основные опыты используют стандартную библиотеку. Проверка действующего AST дополнительно ищет SQLGlot в окружении и локальной `.tools/test-packages`; если библиотека недоступна, это фиксируется отдельно. Файл вывода разрешено записать только рядом со скриптом. Скрипт не запускает сервисы и не меняет исходные БД.

Исходный код прототипа не содержит комментариев и docstring; назначение и ограничения описаны здесь. Прототип — исследовательский артефакт, не готовый модуль для подключения к API.

# Ассистент: разговор, результат и продолжение расчёта

Статус на 4 октября 2026 года: документ сохраняет обсуждение на этапе проектирования. Новый backend, frontend и самостоятельный SQL-пакет уже реализованы; текущее поведение и проверки описаны в [руководстве продукта](../../../README_RU.md). Утверждения о ещё не реализованных компонентах ниже относятся к первоначальной дате исследования.

Ассистент нужен, когда готового отчёта недостаточно: пользователь описывает нужную таблицу обычными словами, получает результат и уточняет следующий расчёт. Каждая таблица сохраняет собственные условия и SQL. Разговор не заменяет обсуждение с сотрудником и не превращает модель в автора управленческих решений.

Это проектирование для [«Разбора»](README.md), согласованное с [архитектурой backend и frontend](architecture.md). Сейчас ядро обрабатывает отдельные вопросы, а HTML-макет показывает подготовленный ответ. История диалога, продолжения и постоянные задания ещё не реализованы.

## Где находится и кому доступен

В навигации есть «Ассистент». В обзоре, карточке точки и отчёте — «Спросить по этим данным». Контекстная кнопка открывает панель с тем же интерфейсом; «Развернуть» переносит на страницу диалога без потери текста и результата. На телефоне сразу открывается полная страница.

Доступ определяется полномочием `ask_data`. Его получают руководитель, региональный менеджер, франчайзи, управляющий и аналитик в пределах выданных источников и данных. Администратору это право отдельно выдаётся при необходимости. Для всех одна механика чата; меняются область, примеры вопросов и разрешённые операции.

Диалог принадлежит одному пользователю и одному пространству/источнику. Совместная работа начинается с передачи выбранного результата в разбор. История всего личного диалога не раскрывается адресату вместе с одной таблицей. Смена источника создаёт новый диалог; период и точки можно менять внутри текущего с явным указанием условий.

## Состав экрана

| Часть | Содержимое и поведение |
| --- | --- |
| История | Личные диалоги с названием, датой и состоянием последнего запроса. Название берётся из первого вопроса и редактируется человеком; отдельной генерации названия нет |
| Контекст | Источник, доступная область и выбранные условия. Права вычислены сервером; элементы выбора позволяют запросить только разрешённое |
| Лента | Сообщение пользователя, этапы его задания и карточка результата или понятная причина отказа |
| Карточка результата | Таблица, число показанных строк, усечение, время, основание продолжения; отдельно SQL и достоверно известные условия |
| Поле вопроса | Ввод, явная кнопка отправки, видимое основание уточнения и «Новый вопрос», сбрасывающий наследование предыдущего расчёта |
| Действия результата | Развернуть таблицу, сохранить отчёт, создать разбор, уточнить этот результат; график только для поддержанного набора колонок |

Таблица — основное содержимое ответа. Ассистент не дописывает отдельным LLM-вызовом «Как видно из данных…». Подписи состояний и числовые сводки формируются кодом по известным полям. SQL раскрывается по запросу пользователя; поток токенов модели не подменяет этапы выполнения.

Выбранный период и область — условия запроса, а не автоматически доказанная интерпретация произвольного SQL. Проверенные шаблоны показывают точные параметры. Для свободного SQL дополнительные условия извлекаются только из распознанных конструкций; иначе остаются формулировка, заданный контекст и сам SQL. Приложение не выдумывает подпись, которую не смогло проверить.

## Три пользовательских сценария

**Новый вопрос.** Франчайзи выбирает свои точки и сентябрь, пишет «Покажи продажи и возвраты по неделям» и нажимает «Получить таблицу». Backend сохраняет сообщение и задание; worker вызывает `sql_agent`. Полученный результат можно открыть после ухода со страницы.

**Продолжение.** Под результатом пользователь нажимает «Уточнить» и пишет «А теперь за август». Над полем видно, какой результат взят за основу. Создаётся новый запуск: предыдущая таблица сентября остаётся прежней, новая таблица относится к августу. Следующее «только Арбат» относится к явно выбранному последнему результату, а не к случайной таблице в соседней вкладке.

Унаследованные условия являются исходными значениями. Явное изменение в новой реплике, например «за август», заменяет унаследованный сентябрь. Контракт различает унаследованный контекст и параметры, которые человек изменил в форме для текущей отправки. Если новая реплика противоречит именно этим явно заданным параметрам, агент возвращает запрос уточнения периода до исполнения. В интерфейсе показываются запрошенные условия; применённые условия результата подписываются только при возможности их проверить по SQL. Ограничения доступа текстом вопроса не переопределяются.

**Передача человеку.** Пользователь выделяет поддержанный факт одной точки и выбирает «Создать разбор». Далее — «Задать вопрос участнику», адресат и предпросмотр. Если свободная таблица не позволяет надёжно выделить разрешённую точку, нельзя просто скрыть соседние строки: нужен отдельный расчёт по точке или отказ в передаче. Комментарии управляющего остаются в разборе и не подмешиваются в историю SQL-генерации.

Для «только эти точки» требуется явный выбор точек. Ссылку на строки можно использовать только при проверенной связи с идентификаторами точек; название произвольной колонки не доказывает такую связь. При неоднозначности пользователь выбирает точки из разрешённого справочника.

## Как диалог использует прежнее ядро

Backend хранит всю историю, но передаёт в агент компактное основание: новое сообщение, вопрос выбранного предыдущего запуска, его проверенный SQL при наличии, известные условия и версии определений. Для ответа на уточнение дополнительно передаётся исходный незавершённый вопрос. Строки результатов, сообщения сотрудников и цепочка всех старых ошибок исключены.

Поиск таблиц получает новый вопрос вместе с основанием. Искать только слова «а за август» бессмысленно. Тот же контекст получает существующий генератор; отдельного LLM-перефразировщика нет. История и SQL обозначаются как данные, не как системные инструкции. Успешный предыдущий SQL — ориентир, а не разрешение повторить его без проверки.

Перед продолжением backend заново проверяет доступ к источнику, предыдущему результату и используемым полям. Изменение выданных прав или профиля чтения требует повторной проверки основания; если оно теперь недоступно, старый контекст не передаётся модели и предлагается новый вопрос. Обычное сужение выбранных точек внутри разрешённой области, например «только Арбат», сохраняет `base_run_id` и создаёт новый результат. Изменившаяся схема требует свежего каталога и новой проверки. Версия каталога не гарантирует неизменность строк БД.

Контекст ограничивается токенизатором с резервом для ответа. При превышении бюджета интерфейс предлагает новый вопрос или более узкую область. Молчаливого удаления значимых условий или сжатия истории ещё одной моделью нет.

## Уточнение и отказ

Текущая грамматика возвращает SELECT либо `INSUFFICIENT_CONTEXT` / `UNSUPPORTED_QUERY`. Поэтому свободный разговор с вопросами модели уже сейчас не обещается.

Для диалогового выпуска добавляется небольшое расширение протокола: закрытые коды `CLARIFY_PERIOD` и `CLARIFY_METRIC`. Backend показывает фиксированную форму выбора периода или разрешённого определения. SQL-ветка грамматики сохраняется, новые ответы проходят отдельные тесты и не исполняются в БД. Для других недостатков контекста остаётся понятное сообщение с просьбой переформулировать вопрос.

| Ситуация | Действие интерфейса |
| --- | --- |
| Не указан необходимый период | Выбор периода; при наличии однозначно заданного контекста повторный вопрос не нужен |
| «Доход» имеет несколько согласованных значений | Выбор определения из серверного списка, а не придуманная моделью формула |
| Нет данных о себестоимости | Сообщение о недоступной метрике; продажи не выдаются за прибыль |
| Нужна неподдерживаемая SQL-конструкция | Сообщение об ограничении и возможность изменить вопрос |
| Запрос требует чужих точек | Ограничение доступа; результат своей точки не подписывается как итог всей сети |
| Вопрос «почему?» требует причины | Предложение запросить измеримую детализацию или обратиться к ответственному; причинный рассказ не генерируется |

При уточнении задание завершается как `needs_input` и освобождает worker. Ответ пользователя создаёт новое задание, связанное с исходным вопросом. Повторы исправления SQL остаются внутренними попытками одного запуска, а не сообщениями «ассистента» в чате.

У формы уточнения есть собственный идентификатор и версия диалога. «Новый вопрос» закрывает ожидание ответа у прежней формы, сохраняя её в истории; продолжить её можно позже только явным действием. Устаревший ответ из другой вкладки отклоняется как конфликт версии, введённый текст сохраняется. Он не подставляется в новый вопрос автоматически.

## Отправка, отмена и несколько вкладок

1. Клиент отправляет текст, контекст, `base_run_id` при уточнении, версию диалога и ключ идемпотентности. Права и SQL предыдущего запуска берутся сервером, а не из доверенных полей браузера.
2. Backend атомарно сохраняет сообщение, запуск и задание. Возвращает идентификаторы; клиент подписывается на события. Повтор HTTP-запроса с тем же ключом не создаёт вторую генерацию.
3. На диалог допускается одно активное задание. Второй запрос из другой вкладки получает текущее состояние, а набранный текст сохраняется. Изменение контекста не переписывает уже принятое задание.
4. При обрыве подписки клиент переподключается или получает состояние через GET. Закрытие панели/вкладки не равно отмене.
5. «Остановить» отправляет отдельную команду. Состояние «Останавливается» остаётся до подтверждённой остановки. Поздний ответ отменённой попытки не подменяет текущую таблицу.
6. Повтор после ошибки создаёт новую попытку со своим идентификатором; предыдущий запуск и причина сохраняются. Повторение сохранённого SQL без генерации — отдельная операция отчёта, не скрытая отправка нового вопроса.

Новая API-схема отделяет POST создания от GET событий и результата. Текущий [маршрут](https://github.com/Gl12321/TP/blob/7b1c7a44285fcc88279942596c824239e442b9d1/src/api/routes/queries.py) использует POST с NDJSON и отменяет работу при закрытии потока; подключить к нему EventSource без переработки нельзя. Существующее поведение сохраняется до реализации постоянных заданий и нового контракта.

## Что проверяет готовность

- «Продажи за сентябрь → за август → только Арбат»: каждый результат имеет правильный период, область и отдельный SQL; прежние числа не изменились.
- «Только эти точки» без выбора не приводит к угадыванию идентификаторов.
- Новый диалог не наследует фильтры другого источника. Отзыв доступа закрывает историю и основание продолжения, которое стало недоступным.
- Двойная отправка, два окна, разрыв SSE и повторное открытие страницы не создают дубликат вычисления.
- Отмена освобождает ресурсы; готовность нового запроса не объявляется раньше фактического завершения предыдущего.
- Сохранение и передача результата не раскрывают чужие строки, поля, SQL или сообщения личного диалога.
- Ошибка и уточнение не требуют дополнительной модели; обычный просмотр истории вообще не запускает генерацию.

Изменения ядра ограничены контрактом основания, учётом его в retrieval и промпте, небольшим протоколом уточнения и проверками диалоговых сценариев. Хранение чата, уведомления, роли, рендеринг таблиц и управление заданиями реализуются обычным кодом backend/frontend.

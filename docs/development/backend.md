# Разработка бэкенда

Бэкенд отвечает за доверие к данным и согласованную работу команды: у каждого результата есть область доступа, использованный источник и история действий. Его можно менять и проверять без загрузки языковой модели. Генератор нужен отдельному worker; обзор, настройки и обсуждения выполняются обычным Python-кодом.

Здесь описаны устройство серверной части и порядок изменений. Общая схема находится в [архитектуре](../ARCHITECTURE.md), пользовательские сценарии — в [описании продукта](../PRODUCT.md), точные HTTP-пути — в [backend/API.md](../../backend/API.md).

## Процессы и границы

| Процесс | Точка входа | Что выполняет |
| --- | --- | --- |
| API | [backend/app/main.py](../../backend/app/main.py) | Авторизация, настройки, обычная аналитика, история, обсуждения, выдача собранного фронтенда |
| Worker | [backend/app/worker.py](../../backend/app/worker.py) | Загрузка моделей, обработка очереди, генерация и исполнение SQL, публикация результата |
| Подготовка схемы | [backend/app/bootstrap.py](../../backend/app/bootstrap.py) | Alembic-миграции; отдельная операция `restore-state` после восстановления БД |

Все процессы используют одну прикладную БД. Для рабочего запуска это PostgreSQL с драйвером `asyncpg`. Подключения к PostgreSQL клиента создаются отдельно через `sources`; клиентская БД не хранит пользователей или задания приложения. Redis и Celery не требуются: очередь и события находятся в прикладной БД.

API импортирует контракты и проверку SQL из `sql_agent`, но не загружает LLM. Адаптер [assistant/engine.py](../../backend/app/assistant/engine.py) создаёт локальные модели только при запуске worker. Интерфейс и история поэтому доступны, когда генератор загружается или остановлен.

Новую операцию размещают у владельца данных; универсальный репозиторий или сервисный класс для каждой таблицы не является обязательным слоем.

## Модель данных

| Владелец | Основные таблицы | Назначение |
| --- | --- | --- |
| `access` | `app_setup`, `app_users`, `workspaces`, `memberships` | Первоначальная настройка, аккаунт и назначения в пространствах |
| `access` | `user_sessions`, `login_attempts`, `invitations`, `audit_events` | Сессии, ограничение входа, одноразовые приглашения, журнал успешных изменений |
| `sources` | `sources`, `source_issues`, `source_issue_comments` | Зашифрованные подключения, каталог, политики и история технических проблем |
| `analytics` | `stores`, `metrics`, `plans`, `reports` | Точки, редакции расчётов и планов, ссылки на опубликованные результаты |
| `assistant` | `conversations`, `conversation_messages`, `query_runs` | Личные диалоги, сообщения и результаты запусков |
| `jobs` | `jobs`, `run_events`, `worker_heartbeats` | Состояние выполнения, события и готовность исполнителя |
| `collaboration` | `cases`, `case_measurements`, `case_comments`, `assigned_questions`, `notifications` | Совместный разбор и его история |
| `infrastructure` | `creation_requests` | Защита создания отчёта, разбора и технического обращения от дублей |

Идентификаторы — строковые UUID, серверное время — UTC. Большинство объектов принадлежит `workspace_id`; составные внешние ключи запрещают связывать результаты, источники и участников разных пространств. Массивы областей, контексты и результаты хранятся в JSON и дополнительно проверяются прикладным кодом. Внешний ключ не заменяет проверку текущего доступа.

`Store.code` — внешний код точки в исходных таблицах. Он уникален в пространстве и не изменяется через текущий PATCH точки. Название и город можно менять; для чтения строк используется код, а не отображаемое имя.

Новая редакция показателя с тем же `key` получает новый `id` и увеличенную `version`. План относится к конкретным `metric_id`, точке и месяцу; повторное сохранение создаёт редакцию. Отчёт хранит ссылку на исходный запуск, обновления — отдельные запуски с `context.report_id`. Измерение разбора сохраняет определение показателя, период, значения и план, чтобы последующие изменения не переписали основание решения.

## Доступ: четыре независимые проверки

1. **Аккаунт и членство.** Сессия действующая, пользователь и назначение активны, объект принадлежит указанному пространству.
2. **Возможность.** `Access.require(...)` проверяет действие, например `plans:write` или `sources:manage`.
3. **Область точек.** `all_stores` либо `store_ids` определяют разрешённые точки. Для общего результата необходим доступ ко всей сохранённой области.
4. **Профиль источника.** Нужны `analytics:read` и разрешение `Source.reader_ids`: `null` означает всех аналитических читателей пространства, пустой список — отсутствие читателей, непустой — перечисленные `user_id`.

Роли описаны в [access/policy.py](../../backend/app/access/policy.py). Базовый аналитический набор — чтение аналитики, ассистент, создание отчётов и разборов.

| Роль | Базовый аналитический набор | Дополнительно |
| --- | --- | --- |
| `director` | Да | `plans:write` |
| `regional_manager` | Да | `plans:write` |
| `franchise_owner` | Да | Область задаётся назначением |
| `store_manager` | Да | Область задаётся назначением |
| `analyst` | Да | `metrics:write` |
| `admin` | Только при `data_access=true` | `sources:manage`, `members:manage` |

Признак владельца добавляет управление источниками, участниками, показателями и планами. `data_access=false` удаляет все аналитические возможности, в том числе у владельца. Приглашение администратора по умолчанию создаётся без финансового доступа. Владение пространством и техническое управление источником не обходят `reader_ids`.

Изменение назначения увеличивает `Membership.revision`. Worker проверяет ревизию во время работы и перед публикацией. Изменение политики источника увеличивает `policy_revision`: старый результат с другой ревизией скрывается. Обычная перепроверка каталога меняет `catalog_version`, сохраняя чтение ранее полученных результатов, но прерывает активный расчёт на устаревшей структуре.

Новый маршрут должен проверять идентификатор объекта, пространство, действие, область и источник. Это относится также к спискам, уведомлениям, названию диалога, повтору идемпотентного запроса и SSE: метаданные могут раскрыть недоступный результат.

## Чтение внешней БД

[sources/service.py](../../backend/app/sources/service.py) проверяет адрес по разрешённому серверному списку, расшифровывает пароль только при подключении и устанавливает PostgreSQL-соединение с режимом чтения. Проверка источника отклоняет административные полномочия и права записи в доступные таблицы выбранных схем. Политика приложения дополнительно выбирает колонки и ключ точки для каждой таблицы.

Порядок исполнения: проверка AST по разрешённому каталогу → замена каждой таблицы проекцией разрешённых колонок и строк → привязка внешних кодов точек параметрами → транзакция `READ ONLY` → ограниченная выдача. Внешний `OR`, JOIN или агрегат не убирает фильтр внутри проекции. Общие справочники доступны только с явным `shared=true`; это не настройка RLS самого PostgreSQL.

API ограничивает соединения с источниками общим семафором на восемь и двумя на профиль, worker — двумя и одним соответственно. Это лимиты **процесса**: добавление процессов API увеличивает суммарное число соединений. Ожидание слота ограничено пятью секундами. Таймауты, строки и размер значений задаются в [конфигурации](../operations/configuration.md).

Обычная аналитика и ассистент используют `ScopedExecutor`. Прямой вызов `asyncpg` из нового бизнес-маршрута обойдёт проверки области, каталога и лимитов. Интеграцию с другим типом БД нужно проектировать в `sources`, сохранив этот договор чтения; текущий продукт поддерживает PostgreSQL-источники.

## Жизненный цикл вопроса

1. Клиент передаёт вопрос, источник, точки, выбранные условия, `version` диалога и `idempotency_key`.
2. `assistant.service.create_run` проверяет готовность worker, права и квоты. Сообщение, `QueryRun`, `Job` и первое событие записываются одной транзакцией.
3. Worker захватывает самое старое доступное задание. PostgreSQL использует `FOR UPDATE SKIP LOCKED`; захват получает случайный токен и срок аренды.
4. `assistant.engine` передаёт библиотеке разрешённый каталог, определения показателей, условия и выбранное основание продолжения. Строки результата, пароли и обсуждения коллег в промпт не включаются.
5. Монитор сохраняет этапы, продлевает аренду и передаёт отмену. Периодически проверяются права, версия каталога и активность точек.
6. `jobs.finish_job` блокирует актуальные записи, проверяет аренду и права, затем публикует таблицу либо конечное состояние. Просроченный исполнитель не может сохранить поздний ответ.

Активные состояния: `queued`, `running`, `cancel_requested`. Конечные: `succeeded`, `failed`, `cancelled`, `needs_input`, `rejected`. `stage` уточняет этап, но не заменяет состояние. Отмена очереди завершается сразу; выполняющийся запрос остаётся в `cancel_requested` до остановки. При потере worker просроченное задание получает `worker_lost` при следующем проходе очереди, а не запускается повторно незаметно для пользователя.

Один диалог допускает одно активное задание. Дополнительно действуют общая квота, квота пространства и пользователя. Worker исполняет задания последовательно; PostgreSQL advisory lock допускает один модельный worker на прикладную БД. Простое масштабирование контейнера не включит параллельную генерацию: для этого нужно отдельно изменить управление моделями и ресурсами.

SSE читает сохранённые `run_events`; `Last-Event-ID` и `after` позволяют продолжить чтение. Закрытие SSE не отменяет задание. После переподключения клиент получает актуальный запуск через GET. При отзыве доступа поток отправляет `access_revoked` и завершается.

## HTTP и транзакции

[dependencies.py](../../backend/app/access/dependencies.py) выдаёт `Db`, `CurrentUser` и `WorkspaceAccess`. Зависимость с `scope="function"` фиксирует транзакцию до начала ответа, включая отправку сессионной cookie. Сервис использует `flush`, когда нужен созданный идентификатор; обычную фиксацию и откат выполняет [get_db](../../backend/app/infrastructure/database.py).

Сессия находится в HttpOnly cookie `razbor_session`, в БД хранится хеш токена. Изменяющие запросы аутентифицированного пользователя требуют `X-CSRF-Token`. Сервер отдельно проверяет Origin, ограничивает тело запроса двумя МиБ и запрещает неизвестные поля входных моделей. Пароли сохраняются через scrypt, секреты источников шифруются ключом, производным от `APP_SECRET_KEY`.

Публичная ошибка имеет вид `{"error":{"code":"...","message":"..."}}`; ошибка валидации добавляет `fields`. Для ожидаемой ошибки используется `AppError` со стабильным `code`. Нельзя возвращать текст исключения драйвера, DSN или пароль. `audit_events` фиксирует успешный изменяющий маршрут и участника; это журнал действий, а не полная история предыдущих и новых значений каждого поля.

Создание отчёта, разбора и технического обращения использует [reserve_creation](../../backend/app/infrastructure/idempotency.py): пространство + автор + ключ уникальны, отпечаток тела и вид операции проверяются при повторе. Резервирование и объект сохраняются одной транзакцией; ошибка освобождает ключ. Повтор возвращает актуальный объект после новой проверки доступа. Вопрос, обновление отчёта и повторное измерение имеют свои обязательные ключи.

Списки диалогов, отчётов, разборов и технических обращений используют [paginate](../../backend/app/infrastructure/pagination.py). JSON содержит массив, продолжение передаётся через `X-Next-Cursor`. Курсор привязан к пользователю, пространству, маршруту и фильтрам. Возможен пустой массив с продолжением после просмотра недоступных объектов; клиент не должен считать его концом истории. Уведомления имеют отдельный предел последних 100 записей и пока не используют эту пагинацию.

## Правила расчётов и истории

- Период включает обе даты; SQL использует полуинтервал до начала следующего дня. Календарная группировка `timestamptz` опирается на часовой пояс сессии внешнего PostgreSQL; отдельной настройки бизнес-часового пояса нет.
- Полные месяцы сравниваются с предыдущим блоком календарных месяцев, произвольный диапазон — с предшествующим диапазоном той же длины. Оба периода читаются одним SQL.
- Средние агрегируются с весами. Отсутствие строки, `null` и ноль не взаимозаменяемы. Наличие строк не доказывает полноту загрузки источника.
- Месячный план показывается для полных месяцев; приложение не распределяет его по дням автоматически. Факт и план сравниваются по общей области.
- Обновление отчёта повторяет сохранённый SQL через очередь и текущие проверки доступа. Модель новый SQL не генерирует; исходный снимок не заменяется.
- Закрытие разбора сохраняет обязательный итог и прекращает обычное обсуждение. Автор может добавить повторное измерение по исходному определению, чтобы проверить результат действия.

## Локальная работа

Команды выполняются из корня репозитория с активированным Python-окружением. Зависимости объявлены в [requirements-dev.txt](../../requirements-dev.txt); набор устанавливает базовый агент в editable-режиме и инструменты проверок, но не веса моделей.

```text
python -m pip install -r requirements-dev.txt
python -m backend.app.bootstrap migrate
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
```

Перед миграцией и запуском в окружении процесса должны быть `APP_DATABASE_URL`, `APP_SECRET_KEY`, `APP_BOOTSTRAP_TOKEN`; для локального HTTP — `APP_SECURE_COOKIES=false`. Примеры Windows/Linux находятся в [общем руководстве разработки](README.md) и [конфигурации](../operations/configuration.md). Прямые команды `python -m ...` не читают `.env` автоматически. Изменение Python-кода подхватывает `--reload`; миграции, зависимости и новые переменные окружения применяются отдельно.

API без worker позволяет войти, настроить организацию, читать обычную аналитику и историю. Новый вопрос вернёт `worker_unavailable`. Для реальной генерации нужны подготовленные модели, дополнительные зависимости пакета и отдельная команда:

```text
python -m backend.app.worker
```

Выбор моделей и работа библиотеки разобраны в [sql-agent.md](sql-agent.md). Worker при изменении своего кода перезапускается отдельно. Для разработки интерфейса используется Vite из [руководства фронтенда](frontend.md); для раздачи API нужна собранная `frontend/dist`.

`GET /health` подтверждает работу API и сообщает `worker_ready`; это не проверка БД клиента. `GET /ready` проверяет доступность прикладной таблицы `app_setup`, а не каждую миграцию или источник. `python -m backend.app.worker --healthcheck` проверяет свежий heartbeat, не загружая модели. Порядок общего запуска находится в [эксплуатации](../operations/README.md).

## Как вносить изменения

### Новое поле или сущность

1. Добавить ORM-поле у владельца сущности и новую Alembic-ревизию после текущей `head`; применённые версии не переписывать.
2. Задать поведение для существующих записей: значение по умолчанию, перенос данных и допустимость `null`. Для связей предметных объектов сохранить границу пространства составным ключом.
3. Обновить входную схему, публичный payload и тип фронтенда. Не выдавать ORM-объект целиком: секреты и служебные поля не входят в API автоматически.
4. Проверить переход с предыдущей схемы на новой и заполненной БД. Обновить [документацию миграций](../../backend/migrations/README.md) и контракт, если меняется HTTP.

### Новый маршрут

1. Разместить его в `api/` предметного модуля. Новый router зарегистрировать в `main.py`.
2. Для входа использовать `Input`, для доступа — `WorkspaceAccess` и нужную capability. Связанные идентификаторы проверять в том же пространстве.
3. Определить транзакционную границу, повторную отправку и поведение при конфликте. Если действие создаёт долгий расчёт, сохранить задание вместо удержания HTTP-запроса на генерации.
4. Для списка использовать общую пагинацию и проверку доступа каждой записи. Для события или уведомления проверять доступ к целевому объекту.
5. Проверить пользовательский сценарий: успешный вызов, чужую область, существенные повтор и конфликт. Обновить [API.md](../../backend/API.md) и клиентские типы.

### Новое право или роль

Изменить `CAPABILITIES` и схему роли, проверить сочетания `owner`, `data_access`, области точек и `reader_ids`. Обновить интерфейс настройки участников и доступность действий, сохранив обязательную серверную проверку. Для изменений назначения оставить увеличение `revision`: фоновые задания не должны продолжить работу со старыми правами.

### Изменение SQL-поведения

Определение обычного показателя меняется в `analytics`; генерация и поддерживаемый язык — в библиотеке агента. Общая граница исполнения остаётся в `sources`. Расширение языка требует согласованной проверки грамматики, AST, ограничения строк/колонок и реальных значений PostgreSQL. Успешный парсинг не подтверждает правильность бизнес-метрики.

## Проверки и поставка

Для прикладного изменения достаточно относящегося к нему набора. Команды полного серверного набора:

```text
python -m pytest backend/tests -q
python -m ruff check backend
python -m ruff format --check backend
```

SQL-ограничения, блокировки, отмена и миграции PostgreSQL проверяются отдельно с `RAZBOR_TEST_DATABASE_URL`, направленным на изолированный тестовый кластер. Требования к роли и создаваемым ресурсам описаны в [backend/tests/README.md](../../backend/tests/README.md). SQLite проверяет прикладные сценарии, но не заменяет PostgreSQL. Тестовый engine проверяет интеграцию, а не качество настоящей модели.

Поставка включает совместимые API, worker, собранный фронтенд и миграции одной версии. Перед сменой схемы нужна [резервная копия](../operations/backup.md) БД и ключа источников; миграция выполняется один раз до рабочих процессов. `Base.metadata.create_all()` предназначен для тестовых сценариев и не заменяет миграции при деплое. Порядок обновления и конфигурация сервисов описаны в [Docker](../operations/docker.md).

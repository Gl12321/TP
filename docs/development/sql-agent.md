# Разработка SQL-агента

Агент отвечает за один сценарий: получить аналитический вопрос и вернуть рассчитанную таблицу с SQL либо объяснить, каких условий не хватает. Его можно менять и использовать как библиотеку без переноса веб-приложения. При этом продуктовый бэкенд продолжает управлять пользователями, подключениями, заданиями и сохранёнными результатами.

Руководство описывает границы ядра, его контракт и порядок изменений. Для общего устройства продукта см. [архитектуру](../ARCHITECTURE.md), для настройки машины и контейнеров — [запуск](../operations/README.md) и [Docker](../operations/docker.md).

Изменение UI, HTTP-схемы, модели пользователя или очереди не должно добавлять зависимость на FastAPI, SQLAlchemy либо код `backend` внутрь пакета. Направление зависимости одно: бэкенд использует библиотеку.

## 2. Как библиотека встроена в продукт

| Компонент | Что делает |
| --- | --- |
| [API помощника](../../backend/app/assistant/api/routes.py) | Принимает вопрос, проверяет возможность запуска и создаёт задание |
| [Worker](../../backend/app/worker.py) | Забирает задание, поддерживает аренду и сохраняет итог |
| [LocalEngine](../../backend/app/assistant/engine.py) | Собирает модели, каталог, определения показателей и исполнитель для конкретного запроса |
| `SQLAgent` | Подбирает контекст, генерирует и проверяет SELECT, управляет исправлениями |
| [ScopedExecutor](../../backend/app/sources/service.py) | Повторно проверяет доступ, ограничивает строки, выполняет SQL и сохраняет фактические параметры |

В worker загружается один экземпляр основной модели, embedder и reranker. Для каждого задания создаётся агент с каталогом и исполнителем, привязанными к этому пользователю и источнику. Общие поисковые модели можно переиспользовать; состояние доступа к разным запросам смешивать нельзя.

API не загружает веса. Поэтому пользователь может работать с точками, отчётами и обсуждениями, пока worker занят генерацией. Агент не является самостоятельным контейнером или HTTP-сервисом: пакет установлен в образ worker, а базовое SQL-ядро также используется бэкендом для проверки и выполнения сохранённых запросов.

Обновление отчёта выполняет сохранённый SQL через исполнитель. Оно не требует новой генерации и не меняет первоначальный результат отчёта.

## 3. Вход, результат и порты

### Запрос

`AgentRequest` из [contracts.py](../../packages/sql_agent/src/sql_agent/contracts.py) содержит:

| Поле | Назначение |
| --- | --- |
| `question` | Текущий текст пользователя |
| `filters` | Явно выбранные условия: период, точки, показатель и другие данные контекста |
| `metrics` | Согласованные определения доступных показателей: ключ, смысл, единица, версия, таблицы и расчёт |
| `conversation` | Выбранный предыдущий успешный расчёт: вопрос, SQL и условия |

`conversation` — конкретное основание нового вопроса, а не полная история чата. Неудачный SQL передаётся механизмом исправления, а не в качестве успешного основания. Ответ пользователя на запрос уточнения собирает бэкенд перед вызовом библиотеки.

`filters.metric_key` связывает выбранный показатель с `MetricDefinition.key`. Таблицы выбранного определения становятся обязательными для контекста. Если определения нет либо оно ссылается на недоступную таблицу, библиотека возвращает ошибку до генерации.

Фильтры не предоставляют права на строки. Даже если пользователь напишет в вопросе другой город или передаст иной код точки, исполнитель обязан сохранить серверную область доступа.

### Обязательные порты

Контракты заданы структурными `Protocol` в [ports.py](../../packages/sql_agent/src/sql_agent/ports.py).

| Порт | Методы и требования |
| --- | --- |
| `AllowedCatalog` | `async snapshot(context) -> CatalogSnapshot`: проверить актуальный доступ и вернуть только разрешённые таблицы и поля |
| `SQLGenerator` | `context_size`, `max_tokens`, `count_tokens(messages)` и `async generate(messages, grammar, context) -> str`: считать и генерировать с одним шаблоном и токенизатором, соблюдать грамматику и остановку |
| `ReadOnlyExecutor` | `async execute(sql, context) -> QueryResult`: проверить права заново, ограничить данные, выполнить чтение с таймаутом и ограниченной выдачей |

Дополнительные `TableRetriever.retrieve(question, snapshot, context)` и `TableRanker.rerank(question, documents, context)` возвращают `RetrievedTable`. Каждый найденный объект должен точно соответствовать таблице из переданного снимка. Нельзя подмешивать таблицу из общего индекса, даже если её имя совпадает.

Базовый вариант подключения:

```python
from sql_agent import AgentRequest, AgentSettings, QueryContext, SQLAgent

async def calculate(question, catalog, generator, executor, on_event):
    context = QueryContext(on_event=on_event)
    agent = SQLAgent(
        catalog,
        generator,
        executor,
        settings=AgentSettings(max_corrections=3, timeout_seconds=600),
    )
    return await agent.run(AgentRequest(question), context)
```

Это функция интеграции: `catalog`, `generator` и `executor` предоставляет вызывающее приложение. Готовая реализация сборки с локальными моделями находится в `LocalEngine`.

### Результат

`AgentResult.status` принимает `success`, `clarification`, `not_found`, `cancelled` или `error`. Успех определяется статусом, а не наличием SQL или строк. `result` содержит `QueryResult` с колонками, типами, строками и признаком `truncated`. Дополнительные поля результата — `attempts`, `sql`, `catalog_version`, `tables`, `error_code`, `error`, `clarification`.

В библиотеке `sql` — нормализованный аналитический запрос. Бэкенд отдельно добавляет `execution` с фактически исполненным запросом и параметрами после ограничения строк. Эти два представления нужны для проверки происхождения чисел. Нельзя показывать исходный текст модели как доказательство того, что именно он исполнялся.

Ожидаемые ошибки интеграции передаются как `QueryError(code, message, retryable=False)`. Только явно исправимая SQL-ошибка получает `retryable=True`. Запрет доступа, отмена, нехватка памяти и сетевой сбой не должны запускать попытку «починить SQL». Неожиданное исключение программирования не превращается библиотекой в успешный ответ; его обрабатывает и журналирует вызывающее приложение.

## 4. Каталог, поиск и бюджет контекста

`CatalogSnapshot(namespace, version, tables)` — снимок разрешённых метаданных. `namespace` должен различать организацию, источник и область данных. `version` меняется при изменении структуры или правил доступа. Описание таблицы включает только разрешённые колонки, их типы, комментарии и допустимые связи.

Перед исполнением агент снова вызывает `snapshot` и сравнивает весь снимок. При различии возвращается `catalog_changed`; текущий запрос не выполняется. Это дополняет, но не заменяет повторную авторизацию внутри исполнителя и при чтении сохранённого ответа.

Семантический поиск в [semantic.py](../../packages/sql_agent/src/sql_agent/retrieval/semantic.py) устроен так:

1. Описание широкой таблицы делится на группы колонок. Это позволяет искать поле, которое не поместилось бы в один вход encoder.
2. Embedder строит векторы фрагментов и вопроса. Таблица получает максимальное сходство среди своих фрагментов.
3. Reranker оценивает пары «вопрос — описание» и меняет порядок кандидатов.
4. [context.py](../../packages/sql_agent/src/sql_agent/retrieval/context.py) добавляет кратчайшие пути по внешним ключам. Таблица и необходимые для неё связи включаются вместе.
5. Кандидаты проверяются по фактическому токенизатору генератора с резервом ответа и исправления.

Ключ векторного кеша включает namespace, версию, содержимое таблиц и fingerprint embedder. В памяти действует ограничение числа каталогов. На диске хранится JSON с векторами; повреждённая запись пересоздаётся, запись нового файла атомарная. Дисковый кеш можно удалить при остановленном worker: он восстановится из разрешённых метаданных. Кеш содержит производную информацию о схеме и не должен публиковаться как статический файл.

Обязательные таблицы предыдущего расчёта и выбранного показателя нельзя молча отбросить ради размера промпта. Если они не помещаются, возвращается `context_limit`. Увеличение `n_ctx` потребляет дополнительную память; сначала стоит проверить ненужные поля и описания в профиле источника.

Без собственного retriever используется поиск пересечения слов. Он подходит для небольших каталогов и изолированных проверок; штатный SaaS передаёт семантический retriever.

## 5. Генерация, уточнение и исправление

[prompts.py](../../packages/sql_agent/src/sql_agent/generation/prompts.py) разделяет системные инструкции и JSON с данными вопроса. Каталог, определения показателей, пользовательский текст, предыдущий SQL и ошибки считаются данными. Из них нельзя создавать новые системные сообщения.

Модель возвращает SELECT либо один из четырёх полных ответов протокола:

| Ответ модели | Результат библиотеки |
| --- | --- |
| `CLARIFY_PERIOD` | `clarification`: нужен период либо конфликтуют текст вопроса и выбранные даты |
| `CLARIFY_METRIC` | `clarification`: неоднозначен смысл показателя |
| `INSUFFICIENT_CONTEXT` | `not_found`: недостаточно данных или определения |
| `UNSUPPORTED_QUERY` | `not_found`: операция не выражается поддерживаемым SQL |

Коды не исполняются в БД. Они преобразуются в фиксированное сообщение приложения. При уточнении новый запрос пользователя проходит обычный цикл авторизации и запуска.

Исправление сохраняет исходную аналитическую задачу и добавляет предыдущий SQL, код и текст ошибки. При `MAX_CORRECTIONS: 3` возможно четыре генерации: первая и три исправления. Повтор того же неудачного SQL при неизменном контексте прекращает цикл. По ошибке `missing_context` поиск расширяется не более одного раза. Весь цикл остаётся внутри общего дедлайна.

При изменении промпта нужно сохранять правила кратности JOIN, согласованные формулы, полуоткрытые календарные периоды, десятичное деление и защиту от деления на ноль. Просьба «сделай более подробный ответ» не должна менять контракт SELECT/код отказа. Текстовые объяснения результатов не являются частью текущего ядра.

## 6. Грамматика и AST

[Грамматика](../../packages/sql_agent/src/sql_agent/sql/grammar/README.md) создаётся для текущего набора таблиц. Источники получают канонические псевдонимы `t0`, `t1` по отсортированным именам; имена и колонки корректно экранируются. Файлы `.gbnf` входят в wheel и доступны независимо от рабочего каталога процесса.

Поддерживается один SELECT с INNER/LEFT JOIN, фильтрами, группировками, HAVING, сортировкой, LIMIT/OFFSET, агрегатами, арифметикой, CASE и базовыми операциями с датами. CTE, подзапросы, UNION, окна, self-join, произвольные функции и запись не поддерживаются.

[SQLValidator](../../packages/sql_agent/src/sql_agent/sql/validation.py) разбирает SQL через sqlglot и проверяет разрешённые узлы, источники, область видимости JOIN, колонки, агрегаты, группировки и пределы выражений. `SELECT *` раскрывается в явный список видимых колонок. Грамматика не способна выразить все эти семантические ограничения, поэтому AST-проверка обязательна и после ограниченной генерации.

Пример порядка добавления операции, например новой функции даты:

1. Описать точные аргументы, типы результата и допустимые позиции выражения.
2. Добавить только нужную форму в GBNF.
3. Добавить соответствующее разрешение и ограничения в AST-валидатор; не разрешать произвольные функции целиком.
4. Обновить правила промпта и документацию языка.
5. Проверить разрешённые и запрещённые варианты, затем значение результата в PostgreSQL и применение строковых ограничений бэкенда.

Для CTE, подзапросов или self-join требуется пересмотреть и переписывание SQL в `ScopedExecutor`: текущее ограничение источников спроектировано под один уровень SELECT. Изменения только GBNF недостаточно.

## 7. Модели, отмена и память

Основная модель работает через [LLMClient](../../packages/sql_agent/src/sql_agent/adapters/llama.py) и `llama-cpp-python`. Адаптер использует шаблон диалога из GGUF, отключает thinking, проверяет служебные токены в данных и считает токены тем же способом, которым собирает запрос. Замена модели требует совместимости архитектуры, шаблона и версии движка.

Три закреплённых профиля Qwen3.5, их размер и назначение описаны в [models/README.md](../../models/README.md); точные revision, имена и контрольные суммы находятся в [config.yaml](../../config.yaml). Одновременно используется один профиль основной модели. Автоматической подмены на меньшую модель при ошибке нет.

Embedder `multilingual-e5-small` и reranker `mmarco-mMiniLMv2-L12-H384-v1` работают через CPU PyTorch и Transformers. E5 усредняет только настоящие токены по attention mask и нормализует вектор; префиксы `query: ` и `passage: ` различаются. Reranker возвращает один скаляр на пару. Его оценка определяет порядок кандидатов и не является вероятностью правильности SQL.

Модели открываются только из локального кеша с `local_files_only=True` и `trust_remote_code=False`. Их предварительной подготовкой занимается [runtime/models.py](../../runtime/models.py), а не библиотека и не обработчик пользовательского вопроса.

### События и остановка

`QueryContext` содержит общий `threading.Event`, синхронный `on_event`, идентификатор запроса и дедлайн по `time.monotonic()`. Агент выбирает более ранний из переданного дедлайна и собственного лимита. Нельзя передавать Unix timestamp вместо монотонного времени.

Событие имеет `event="stage"`, `request_id` и `content` с `stage`, `message` и дополнительными полями. Этапы: `retrieve`, `index`, `context`, `generate`, `validate`, `execute`, `correct`. `index` появляется при построении векторов, `correct` — при исправлении. Терминальный статус возвращается в `AgentResult`; очередь и доставка событий браузеру находятся в бэкенде.

Обработчик `on_event` не должен выполнять долгие сетевые операции. Он должен быстро передать событие в очередь приложения. При пользовательской отмене следует выставить `context.cancelled.set()`. Прямое снятие asyncio-задачи может распространять `CancelledError` вызывающему коду; это не равно доменному ответу `status="cancelled"`.

Нативная генерация llama.cpp выполняется в потоке. Callback проверяет отмену, время и запас RAM, включая обработку входного промпта. Адаптер дожидается завершения нативного вызова и очищает прерванное состояние до следующего вопроса. Encoder и reranker проверяют остановку между пакетами. Не следует освобождать модель, пока её нативный вызов ещё выполняется.

Перед загрузкой учитываются размер файла, рабочий резерв и `MIN_FREE_MEMORY_MB`; во время генерации контролируется остаток памяти. На Linux учитываются cgroup, на Windows — доступная память ОС. Это предохранитель, а не гарантированное резервирование RAM. Размер GGUF нельзя выдавать за полный расход worker.

## 8. Установка и проверки при изменении

Пакет требует Python 3.11+, проектное окружение использует Python 3.12. Базовая зависимость — `sqlglot`; группа `local` добавляет llama-cpp-python, Jinja2, psutil, PyTorch и Transformers. Точные версии зафиксированы в [pyproject.toml](../../packages/sql_agent/pyproject.toml).

В настроенном окружении для правок ядра используется editable-установка:

```text
python -m pip install -e ./packages/sql_agent
python -m unittest discover -s packages/sql_agent/tests
```

Для окружения worker с локальными моделями:

```text
python -m pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -e "./packages/sql_agent[local]"
```

Если для выбранной платформы нет совместимого wheel llama-cpp-python, pip собирает нативную библиотеку. Тогда требуются CMake и C++ toolchain: на Linux компилятор и `libgomp`, на Windows средства сборки Visual C++. Docker-образ worker содержит необходимые инструменты сборки. CUDA не требуется для штатного CPU-профиля; один лишь `n_gpu_layers` не добавляет поддержку GPU в CPU-сборку.

Команды установки нужны при создании либо обновлении окружения. Обычный запуск готового окружения не требует переустановки зависимостей. Перед релизом проверяются установленные wheel и ресурсы грамматики, а не только импорт из дерева исходников.

Проверки выбираются по смыслу изменения:

| Изменение | Что проверить |
| --- | --- |
| Промпт, условия или продолжение | `test_pipeline.py`: разделение правил и данных, права продолжения, контрольные вопросы с ожидаемыми таблицами |
| SQL-язык | `test_sql_grammar.py`, `test_sql_validation.py`, PostgreSQL-исполнение и строки вне области доступа |
| Поиск и кеш | `test_retrieval.py`: namespace, смена версии, смена модели, широкая таблица, обязательные связи |
| Адаптер модели | Реальный запуск с подготовленными весами: шаблон, токенизация, отмена и последующий запрос |
| Сериализация | API-ответ реального расчёта: точность Decimal, даты, ограничение размера и представление во frontend |
| Профиль либо нативная зависимость | Реальная генерация, корректный результат, первый и повторный вопрос, пиковая память всего процесса |

Весь компактный набор библиотеки выполняется без весов, PyTorch и llama.cpp. Он проверяет конвейер с заданными ответами генератора и распознавание SQL по собранной грамматике. Нативная совместимость, качество генерации и расход памяти проверяются отдельно на настоящей модели; успешный автономный набор этого не подтверждает. Команды и границы — в [README проверок](../../packages/sql_agent/tests/README.md).

## 9. Типовые изменения и диагностика

| Задача или симптом | Где действовать |
| --- | --- |
| Изменить формулировку уточнения | `_SIGNALS` в `pipeline/agent.py`; код протокола сохраняется |
| Агент не находит нужное поле | Сначала профиль источника и комментарии, затем сериализация/поиск; не расширять права ради поиска |
| Показатель считается иначе, чем на обзоре | Определение и `MetricDefinition.calculation`, кратность JOIN, единицы, период; сравнивать результаты, а не похожесть SQL |
| `context_limit` | Размер выбранного профиля, обязательные таблицы, длина описаний и фактический бюджет токенов |
| `catalog_changed` или `context_not_allowed` | Изменились метаданные либо права; нужен новый расчёт по актуальному каталогу |
| `memory_limit` | Свободная память, cgroup, выбранная модель и `n_ctx`; не отключать резерв как первое решение |
| `model_missing` или `model_unavailable` | Путь, права чтения и подготовленные файлы моделей |
| Ошибка шаблона или управляющих токенов | Метаданные GGUF, совместимость шаблона, специальные последовательности в вопросе/описаниях |
| Нужен другой генератор | Реализовать `SQLGenerator` с фактическим подсчётом токенов, грамматикой, отменой и дедлайном |
| Нужен другой источник данных | Реализовать каталог и исполнитель с теми же гарантиями; текущий язык ориентирован на PostgreSQL |

После изменения библиотеки перезапускается worker. После изменения зависимостей или package data пересобирается его образ. Изменение только текстов фронтенда не требует изменения пакета или перезагрузки моделей.

# Разработка «Разбора»

Задача разработки — сохранять связь между вопросом, достоверным расчётом и действием пользователя. Даже небольшая правка может затронуть эту связь: новый фильтр меняет область расчёта, новое поле — HTTP-контракт, новая функция SQL — проверку и ограничение источников. Поэтому изменение начинается с конкретного сценария и владельца его данных.

Это общий вход для разработчика: карта документации, рабочее окружение и порядок внесения изменений. Подробные механизмы каждого слоя вынесены отдельно, чтобы не смешивать создание формы с устройством нативной генерации.

## 2. Окружение Windows и Linux

Для разработки используются Python 3.12 и Node.js 24. Пакет агента декларирует Python 3.11+, но единая проектная версия уменьшает расхождения с CI и контейнерами. Рабочая прикладная БД — PostgreSQL 16. Docker нужен для стандартного общего запуска; для изменения Python и React можно использовать уже подготовленную нативную БД.

На новой машине сначала установите Python и Docker по [инструкции](../operations/install.md); Node и нативный PostgreSQL можно подготовить по [рецепту demo](../demo/README.md#подготовка-demo-с-нуля). Команды далее предполагают рабочий интерпретатор и Node в PATH. В Windows `python` может быть заглушкой Store: для создания venv используйте проверенный `py -3.12`, после создания — явный Python окружения.

### Python

Создайте виртуальное окружение из корня репозитория:

```text
python -m venv .venv
```

Если Python в Linux доступен только как `python3`, используйте `python3 -m venv .venv`. В Windows допустим установленный launcher `py -3.12 -m venv .venv`.

PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
```

Bash:

```bash
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
```

Активация — удобство терминала, а не обязательное условие. Если PowerShell не позволяет выполнить `Activate.ps1`, вызывайте `.\.venv\Scripts\python.exe` вместо `python`; в Linux — `.venv/bin/python`. Для этого не требуется менять системную политику выполнения скриптов.

[requirements-dev.txt](../../requirements-dev.txt) устанавливает зависимости API, подготовки, SQL-пакет в editable-режиме и инструменты проверок. Веса и тяжёлые библиотеки локального inference этим набором не загружаются. Если окружение уже подготовлено, установку повторяют только после изменения зависимостей.

Для настоящего worker нужны дополнительные зависимости `sql_agent[local]` и подготовленные модели; это отдельная операция из [руководства агента](sql-agent.md). Обычная работа над формой, маршрутом, правами или документацией не требует скачивать GGUF.

### Frontend

Из каталога `frontend`:

```text
npm ci
npm run dev
```

`npm ci` устанавливает версии из lock-файла и нужен при создании окружения или изменении зависимостей. Для уже подготовленного каталога достаточно `npm run dev`.

Vite работает на `http://127.0.0.1:5173` и проксирует `/api` в Python API на порту 8000. Для этого API должен быть запущен отдельно. `npm run preview` показывает сборку, но не заменяет полный сервер приложения. Подробнее — [frontend.md](frontend.md).

### Настройки нативного API

Прямые Python-команды читают окружение процесса, а не корневой `.env`. Для существующей БД используются её реальные параметры и прежний ключ приложения. Значения в примерах ниже — места для подстановки, их нужно заменить до запуска.

PowerShell:

```powershell
$env:APP_DATABASE_URL = "postgresql+asyncpg://razbor_app:URL_ENCODED_PASSWORD@127.0.0.1:5432/razbor"
$env:APP_SECRET_KEY = "EXISTING_APPLICATION_SECRET_AT_LEAST_32_CHARACTERS"
$env:APP_BOOTSTRAP_TOKEN = "EXISTING_INITIAL_SETUP_TOKEN"
$env:APP_SECURE_COOKIES = "false"
$env:APP_ALLOWED_ORIGINS = "http://127.0.0.1:5173,http://localhost:8000,http://127.0.0.1:8000"
```

Bash:

```bash
export APP_DATABASE_URL='postgresql+asyncpg://razbor_app:URL_ENCODED_PASSWORD@127.0.0.1:5432/razbor'
export APP_SECRET_KEY='EXISTING_APPLICATION_SECRET_AT_LEAST_32_CHARACTERS'
export APP_BOOTSTRAP_TOKEN='EXISTING_INITIAL_SETUP_TOKEN'
export APP_SECURE_COOKIES=false
export APP_ALLOWED_ORIGINS='http://127.0.0.1:5173,http://localhost:8000,http://127.0.0.1:8000'
```

Пароль внутри URL должен быть URL-кодирован. Ключи API и worker должны совпадать. Новый случайный `APP_SECRET_KEY` подходит только новому пустому окружению: он не сможет расшифровать подключения существующего приложения. Для двух терминалов используйте один и тот же набор значений.

Список origins в примере разрешает локальный Vite и прямое открытие API. Если меняете адрес или порт frontend, замените его точным origin. Для подключения аналитического источника также настройте `application.source_hosts` либо `APP_SOURCE_HOSTS`: пустой список из исходного YAML намеренно не разрешает внешние подключения.

После настройки применяются миграции и запускается API:

```text
python -m backend.app.bootstrap migrate
python -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --reload
```

`--reload` предназначен для разработки API. Изменение миграций, зависимостей и окружения применяется отдельно. Worker запускается и перезапускается отдельно; без него доступны обычная аналитика и интерфейс, но новый вопрос возвращает `worker_unavailable`. Параметры источников, origins и нативный запуск подробнее описаны в [backend.md](backend.md) и [configuration.md](../operations/configuration.md).

Стандартный контейнер PostgreSQL не публикует свой порт наружу. Нельзя автоматически считать `127.0.0.1:5432` адресом его прикладной БД. Для нативной разработки нужен доступный локальный PostgreSQL либо явно настроенное отдельное окружение разработки.

## 3. Куда вносить изменение

| Изменение | Основные места |
| --- | --- |
| Текст, поле формы или состояние страницы | Нужный `frontend/src/features/<раздел>`, общие компоненты — `shared/ui` |
| Представление SQL-таблицы, чисел, CSV или графика | `frontend/src/shared/results`, `shared/ui/format.ts` |
| Навигация, URL, сессия или очистка приватного состояния | `frontend/src/app`, API-клиент и query keys в `shared/api` |
| HTTP-поле или операция | `backend/app/<предметный модуль>/api`, `backend/API.md`, клиентский `contracts.ts` |
| Новая хранимая сущность | ORM-модель предметного модуля и новая ревизия `backend/migrations` |
| Права пользователя | `access/policy.py`, проверки области в предметном модуле, UI действий и настройки ролей |
| Профиль источника и ограничение SQL | `sources/service.py`, маршруты источников и их политики |
| Формула обзора, сравнение или план | `analytics`; измерения разбора — `collaboration/measurements.py` |
| Диалог, сохранение запуска, повторная отправка | `assistant`; захват и публикация — `jobs` и `worker.py` |
| Поддерживаемая SQL-конструкция | Грамматика, AST и промпт пакета агента, затем ограниченный исполнитель бэкенда |
| Модель, контекст или поиск | `config.yaml`, адаптеры и retrieval пакета; согласованная подготовка в `runtime` |
| Запуск, образ или сохранность данных | `run.py`, `runtime`, Docker-файлы, `tools/backup.py` |

Новый каталог создаётся вокруг ответственности, а не ради формальной глубины. Не нужно добавлять универсальную обёртку над каждым маршрутом или таблицей. Повторяющееся правило должно иметь одного владельца: вычисление доступа — сервер, формат ответа — контракт API, общая таблица — `shared/results`.

В код не добавляются комментарии и docstring. Назначение выражается именами и небольшими функциями, объяснение решений — README соответствующего модуля и руководством. Это не повод скрывать сложное правило в неочевидном выражении.

## 4. Порядок работы над задачей

1. Сформулировать наблюдаемое действие: кто выполняет его, какие данные видит и какой результат сохраняется.
2. Найти владельца сценария и существующий аналог. Проверить HTTP-контракт, состояние UI и правила области доступа.
3. Определить последствия для сохранённых данных, повторной отправки, активного задания и старых ссылок. Для изменения схемы подготовить новую миграцию.
4. Изменить конечный сценарий целиком: серверную схему, поведение, клиентский тип, форму/результат и документацию.
5. Проверить основной исход и существенную границу: чужую область, повтор, отмену, точность либо ошибку — в зависимости от изменения.
6. Перезапустить затронутый процесс и убедиться в нужном поведении. Для правки текста или документации это не означает полный запуск модели и PostgreSQL.

Изменение роли проверяется не только скрытой кнопкой, но и прямым запросом к объекту. Изменение показателя — результатом на известных данных, а не сходством SQL. Изменение сохранённого расчёта не должно подменять его условия текущими фильтрами страницы.

## 5. Проверки по размеру изменения

| Область | Основные проверки |
| --- | --- |
| UI-функция или форма | Связанные Vitest-тесты, TypeScript, нужные состояния экрана |
| API и бизнес-сценарий | Соответствующий набор `backend/tests`, разрешённый и запрещённый доступ |
| SQL-язык и исполнение | Тесты пакета, ограничение строк, реальные значения PostgreSQL |
| Схема БД | Миграция заполненной БД, ограничения связей и совместимость публичных ответов |
| Очередь | Отмена, аренда, повтор отправки, публикация после отзыва доступа |
| Модель | Контрольные вопросы, реальное выполнение, память, отмена и следующий запрос |
| Runtime и backup | Корневые `tests`, сохранение секретов/данных и восстановление в отдельную БД |

Основной Python-набор из корня:

```text
python -m pytest backend/tests packages/sql_agent/tests tests -q
python -m ruff check backend packages/sql_agent/src runtime tests tools run.py
python -m ruff format --check backend packages/sql_agent runtime tests tools run.py
```

Для отдельной задачи указывается конкретный файл или отбор `-k`. Команды широкого набора нужны перед изменением общей границы или выпуском, а не после каждого текстового изменения. Конфигурация Ruff находится в [ruff.toml](../../ruff.toml).

Frontend из его каталога:

```text
npm run typecheck
npm test
npm run build
```

`build` проверяет TypeScript и создаёт готовые файлы. Успешная сборка не проверяет доступность источника, правильность финансовой формулы или готовность worker. `npm run format:check` проверяет форматирование, `npm run format` применяет его.

Тесты PostgreSQL используют отдельный локальный кластер и `RAZBOR_TEST_DATABASE_URL`; требования и создаваемые ресурсы описаны в [backend/tests](../../backend/tests/README.md). Один браузерный сценарий требует изолированного приложения и `APP_UI_CREDENTIALS` с реквизитами аккаунта, описанными в [frontend/tests](../../frontend/tests/README.md). Пропуск сценария без этих условий не считается успешной проверкой.

Проверки с заданным генератором подтверждают контракт, но не качество LLM. Проверка строк по собранной GBNF не подтверждает совместимость с каждой нативной сборкой llama.cpp. Автономный набор не требует ML-библиотек или весов; настоящий ответ оценивается отдельно на известном результате.

Демонстрация продукта отделена от проверок. `python -m tools.demo` показывает подготовленную сеть, `python -m tools.demo --scenario onboarding` — первичную настройку; при первой подготовке используется `RAZBOR_DEMO_DATABASE_URL`. У сценариев свои постоянные базы и аккаунты, которые не передаются автоматическим наборам. Для просмотра достаточно обычных зависимостей `requirements.txt`, сборки frontend и PostgreSQL; подробности — в [demo](../demo/README.md).

[CI workflow](../../.github/workflows/verify.yml) запускает Python-набор на Windows и Linux, а frontend, PostgreSQL и Compose без AI — на Linux. Отдельный `real-ai` проверяет профиль Qwen3.5 4B только при ручном включении либо маркере `[real-ai]` в сообщении push-коммита. Наличие workflow не означает, что конкретная ревизия уже прошла все эти проверки; прогон 4B не подтверждает расход памяти 9B/27B или Docker Desktop на целевом ноутбуке.

## 6. Документация и состав исходников

README основной директории сначала объясняет, зачем она нужна пользователю или системе, затем устройство и связи, затем детали поведения и практические команды. Внутренние функции не перечисляются без объяснения их роли. Код связывается относительными Markdown-ссылками, которые работают в GitHub и локальном просмотре.

При изменении сценария обновляются его README, [описание продукта](../PRODUCT.md) и API-контракт, если затронуто публичное поведение. При изменении запуска или секретов обновляется эксплуатационная инструкция. Результаты разового прогона, временные планы и исследовательские черновики не заменяют документацию текущей версии.

В Git остаются исходники, миграции, тесты, файлы зависимостей, конфигурация и документация. `node_modules`, `.venv`, `dist`, `build`, `.egg-info`, кеши, веса, runtime-данные и приватные фикстуры — локальные артефакты. Файлы с секретами и резервные архивы не добавляются в исходники.

## 7. От изменения к выпуску

Backend, worker, frontend, SQL-пакет и миграции поставляются согласованной версией. Перед изменением рабочей схемы создаётся [резервная копия](../operations/backup.md). Миграции выполняются один раз до запуска новой рабочей версии; runtime-автосоздание таблиц не заменяет Alembic.

При изменении Python-кода API перезапускается; worker перезапускается отдельно. При изменении frontend создаётся новая сборка. Новая зависимость, ресурсы wheel или Dockerfile требуют пересборки образа. Изменение YAML требует реального перезапуска процессов, а не только редактирования смонтированного файла.

Полный порядок запуска, границы контейнеров, хранение данных и поведение при сбое находятся в [эксплуатации](../operations/README.md) и [Docker](../operations/docker.md). Разработка считается завершённой, когда пользовательский сценарий реализован, проверена его существенная граница и документация соответствует получившейся версии.

# Автоматические проверки

Проверки защищают основные контракты продукта: пользователь видит только разрешённые данные, SQL остаётся чтением, суммы не теряют точность, повтор операции не создаёт дубль, ошибка не выдаётся за результат. Набор намеренно компактный: связанные случаи объединены в содержательные сценарии, а одинаковые варианты SQL проверяются таблицами примеров. Это не полное покрытие каждого поля и экрана.

Ручной просмотр продукта вынесен в отдельные [демонстрационные сценарии](../demo/README.md). Они сохраняют данные и предназначены для знакомства с интерфейсом и ролями. Автоматические проверки не используют их аккаунты, базы или каталог состояния.

## Устройство и выбор проверки

Все команды ниже выполняются из корня репозитория. Подготовка Python и Node описана в [руководстве разработчика](README.md). Нужны установленные `requirements-dev.txt`; для frontend — Node.js и зависимости из lock-файла. Сам запуск проверки не устанавливает зависимости, браузеры и веса.

Если инструментов ещё нет, начните с [установки](../operations/install.md) и [подготовки Node](../demo/README.md#1-nodejs-и-python-окружение). `python` в этом руководстве — Python установленного окружения: `.\.venv\Scripts\python.exe` в Windows или `.venv/bin/python` в Linux. Команда Windows Store этим условием не является.

| Команда | Что проверяет | Внешнее окружение |
| --- | --- | --- |
| `python tools/check.py budget` | Лимит 3000 физических строк, включая помощники, runner и конфигурации | Только Python |
| `python tools/check.py quick` | Автономные Python-проверки, Vitest и TypeScript | Python и Node; без серверов и моделей |
| `python tools/check.py runtime` | Настройки, запуск, целостность моделей, резервирование и предусловия инструментов | Python; внешние команды подменены |
| `python tools/check.py backend` | HTTP, сессии, права, обсуждения, очередь и ограничения SQL | Python; временная SQLite, управляемый исполнитель |
| `python tools/check.py agent` | Контекст, грамматика, AST и управление генерацией | Python; без ML-библиотек и скачанных моделей |
| `python tools/check.py frontend` | Точность чисел, экспорт, API-клиент, SQL результата, повтор отправки и типы | Node; API не нужен |
| `python tools/check.py postgres` | Миграции, права чтения, точные суммы, ограничения строк и выполнение SQL | Отдельный локальный PostgreSQL |
| `python tools/check.py browser` | Вход, точка, разбор, комментарий и выход через UI/API | Отдельная готовая установка и браузер |

Состав выбранной команды можно увидеть без выполнения:

```text
python tools/check.py quick --dry-run
python tools/check.py --help
```

Режимы выполняют команды последовательно и останавливаются при первой ошибке. `--dry-run` показывает состав, но не проверяет готовность зависимостей. Полное описание контрактов находится рядом с компонентами: [backend](../../backend/tests/README.md), [агент](../../packages/sql_agent/tests/README.md), [frontend](../../frontend/tests/README.md), [инструменты запуска](../../tests/README.md).

## Обычная правка

```text
python tools/check.py quick
```

Проверяются backend, библиотека агента и корневые инструменты, затем frontend и TypeScript. Настоящий PostgreSQL исключён даже при заданном `RAZBOR_TEST_DATABASE_URL`. Для этой команды не требуется работающий API, worker или Docker.

Во время локальной правки достаточно связанного файла или сценария:

```text
python -m pytest backend/tests/test_scoped_sql.py -q
python -m pytest packages/sql_agent/tests/sql_agent_tests/test_pipeline.py -q
npm --prefix frontend test -- tests/results.test.tsx
```

Прямой `python -m pytest -q` собирает наборы согласно [pytest.ini](../../pytest.ini). При наличии `RAZBOR_TEST_DATABASE_URL` он также выполняет PostgreSQL-проверки; без переменной они пропускаются. Перед выпуском интерфейса дополнительно нужен `npm --prefix frontend run build`.

Не увеличивайте набор копиями одного окружения. Новое правило доступа добавляйте как разрешённый и запрещённый случай существующего сценария; новую конструкцию SQL — как допустимый и недопустимый пример. Проверки вспомогательных команд и браузера тоже входят в общий бюджет тестового кода: не переносите их за пределы `tests` ради формального уменьшения размера.

Runner считает все строки исходников в четырёх тестовых каталогах, включая пустые, а также собственный код, smoke, acceptance, pytest, Playwright, Vite, тестовый Compose, CI, `requirements-dev.txt` и `frontend/package.json` целиком. Список дополнительных файлов задан в `test_lines()` в [tools/check.py](../../tools/check.py); при добавлении внешнего помощника включите его туда. Лимит проверяется каждым режимом и отдельно в CI. Demo не входит в этот подсчёт: это самостоятельная функция ручного знакомства с продуктом, которую автоматические сценарии не используют как источник данных.

## PostgreSQL

Используйте отдельный локальный кластер. `RAZBOR_TEST_DATABASE_URL` должен указывать на административную роль, способную создавать базы, роли и выдавать права. Поддерживаются loopback-адреса `127.0.0.1`, `localhost`, `::1`. Тестовое имя базы само по себе не изолирует остальные базы сервера.

При наличии Docker можно запустить предназначенный для проверок PostgreSQL:

```text
docker compose -f tools/test-postgres.compose.yml up -d --wait
```

[Compose](../../tools/test-postgres.compose.yml) использует проект `razbor-tests`, отдельный том и порт `127.0.0.1:55433`. Если образа `postgres:16-alpine` нет, Docker загрузит его. Для уже работающего выделенного PostgreSQL этот шаг не нужен.

PowerShell:

```powershell
$env:RAZBOR_TEST_DATABASE_URL = "postgresql://razbor_test:local-test-only@127.0.0.1:55433/razbor_tests"
python tools/check.py postgres
```

Bash:

```bash
RAZBOR_TEST_DATABASE_URL='postgresql://razbor_test:local-test-only@127.0.0.1:55433/razbor_tests' python tools/check.py postgres
```

Для своей БД замените реквизиты действительными; специальные символы пароля в URL кодируются. Набор создаёт случайную БД `razbor_it_*` и роль чтения, применяет миграции к новой БД и удаляет только собственные ресурсы после завершения. Административная БД из URL не мигрируется. Набор не предназначен для рабочего кластера компании.

Остановка контейнера сохраняет том:

```text
docker compose -f tools/test-postgres.compose.yml down
```

Demo использует свой `RAZBOR_DEMO_DATABASE_URL` и отдельное окружение. Переменные и состояния этих двух задач не подменяют друг друга.

## Браузер

Один сценарий Playwright работает с заранее запущенным приложением и существующим руководителем-владельцем. Он создаёт точку, разбор и комментарий, затем проверяет выход. Сценарий не запускает сервер и оставляет записи в его БД, поэтому ему нужна отдельная тестовая установка. Финансовый источник и модель не нужны.

Создайте приватный `.runtime/ui-credentials.json` с `url`, `email`, `password`. Точный формат и требования к аккаунту приведены в [frontend/tests](../../frontend/tests/README.md). Используйте обычный аккаунт выделенной тестовой установки, а не аккаунты демонстрационных сценариев.

PowerShell:

```powershell
$env:APP_UI_CREDENTIALS = "$PWD/.runtime/ui-credentials.json"
$env:PLAYWRIGHT_CHANNEL = "msedge"
python tools/check.py browser
```

Bash:

```bash
APP_UI_CREDENTIALS="$PWD/.runtime/ui-credentials.json" python tools/check.py browser
```

`PLAYWRIGHT_CHANNEL=msedge` выбирает установленный Edge. Без него нужен Chromium для Playwright. Если браузера ещё нет, его установка выполняется отдельно:

```text
npm --prefix frontend exec -- playwright install chromium
```

Для просмотра действий в окне выполните из `frontend` команду `npm run test:browser -- --headed`, сохранив абсолютный путь к файлу аккаунта. `check.py` сам разрешает относительный путь перед переходом в `frontend`; при прямом запуске npm относительные пути считаются от каталога frontend.

## Собранное приложение и настоящая модель

[smoke.py](../../tools/smoke.py) проверяет новое отдельное развёртывание без модели: первоначальную настройку, вход, точку, разговор, разбор, комментарий, пустой обзор и выход. Он создаёт первого владельца и оставляет данные. Уже настроенная установка ему не подходит.

[acceptance.py](../../tools/acceptance.py) проверяет вопрос к готовому worker, контрольные суммы и обновление SQL-отчёта. Нужны установленные веса и изолированный экземпляр приложения; сценарий не заменяет подготовку модели. Его данные и подготовленная БД источника остаются после выполнения.

```text
python tools/smoke.py
python tools/acceptance.py
```

Это альтернативные целевые проверки, а не две последовательные команды для одной свежей БД. Параметры существующего аккаунта для acceptance, адреса и конфигурации описаны в [tools](../../tools/README.md). Для отдельного развёртывания нужны собственные контейнеры, тома, порт и секреты. Один другой `--env-file` в той же папке не изолирует Compose: имя проекта `run.py` зависит от пути репозитория.

## Как понимать результат

Успешный автономный набор подтверждает контракты с контролируемыми входами. PostgreSQL добавляет настоящие миграции, права и SQL-семантику; браузер — взаимодействие интерфейса и API; acceptance — известный ответ настоящей модели. Компактный набор не доказывает качество ответов на произвольные вопросы, совместимость GBNF с каждой сборкой llama.cpp или работу всех экранов и устройств.

У `check.py` код `0` означает успешное выполнение выбранных команд, `2` — ошибку предусловий, `130` — прерывание пользователем. Ошибка дочерней команды сохраняет её код. Пропуски pytest видны отдельно и не считаются проверенным поведением. Браузерный режим runner без необходимых реквизитов завершается ошибкой; прямой Playwright без них пропускает сценарий.

[CI](../../.github/workflows/verify.yml) проверяет Python на Windows/Linux, frontend, PostgreSQL и Docker smoke. Настоящий AI-сценарий включается отдельно ручным `real_ai` или маркером `[real-ai]` в push-коммите. Объём действительно выполненных проверок указывайте при оценке изменения.

# Понимание проекта и его развитие

Документация объясняет, как вопрос на обычном языке превращается в таблицу, какие решения за этим стоят и как проверить их работу. Пользовательское знакомство начинается с результата, а детали раскрываются рядом с тем кодом, который их реализует.

## Где искать ответ

| Документ | Для чего читать |
| --- | --- |
| [Корневое руководство](../README_RU.md) | Понять идею, возможности, требования и единый запуск |
| [Устройство приложения](../src/README.md) | Проследить путь вопроса и связи между модулями |
| README в каталогах `src` и [frontend](../frontend/README.md) | Разобраться в роли конкретного модуля и перейти к коду |
| [FEATURES.md](FEATURES.md) | Посмотреть предложения по развитию и критерии готовности |
| [VALIDATION.md](VALIDATION.md) | Узнать, что проверено, что пропущено и какие прогоны ещё нужны |
| [Тесты](../tests/README.md) | Запустить проверки и правильно понять их результат |

Параметры приложения хранятся в [config.yaml](../config.yaml), чтобы документация объясняла их назначение, а не дублировала изменяющуюся таблицу значений.

## Как читать документацию по задаче

Если нужно понять, почему вопрос вернул не те данные, начните с пути вопроса в `src/README.md`, затем перейдите к поиску и генерации. Если таблица найдена, но соединения дают неожиданную сумму, полезны правила SQL и описание промпта. Если проблема возникает ещё до вопроса, документация подготовки запуска и каталог моделей ближе к причине, чем устройство агента.

Например, добавление оконных функций затрагивает несколько частей. Грамматика должна разрешить новую конструкцию, валидатор — определить её допустимые области и аргументы, промпт — объяснить её использование, а тесты — отличить корректный запрос от близкого ошибочного. README соответствующих модулей показывают эти связи и помогают не ограничиться одним изменённым файлом.

Предложения в `FEATURES.md` описывают направление развития, а не обещают уже доступные возможности. `VALIDATION.md`, наоборот, фиксирует сделанное и подтверждённое проверками. Разделение позволяет одновременно обсуждать будущие функции и честно понимать состояние текущего приложения.

## Как поддерживать документацию

При изменении поведения обновляется README соответствующего модуля: сначала его назначение, затем логика с необходимыми деталями и ссылками на код, затем условия использования и связи с соседними частями. Реализованные возможности следует отделять от предложений в `FEATURES.md`.

Состояние проверок фиксируется по фактическому выполнению. Автономные тесты не заменяют запуск с настоящими моделями, PostgreSQL и браузером; измерение памяти относится к конкретной модели и настройкам рабочего прогона.

Ссылки на код должны оставаться относительными, чтобы документацию можно было читать и в редакторе, и в репозитории на другом компьютере. Локальный путь автора или ссылка внутреннего просмотрщика IDE не объясняет устройство проекта и не подходит как постоянная ссылка.

# Демонстрационные режимы

Demo позволяет пройти работу с продуктом в браузере: сравнить результаты точек, обсудить проблему между ролями или собрать новое рабочее пространство с нуля. Оно использует настоящий backend, frontend и PostgreSQL. Вымышленными являются исходные данные сети, а расчёты, права доступа и сохранение изменений работают обычным способом.

Есть два независимых сценария. Каждый хранит собственную прикладную БД, аккаунты и настройки; изменение одного не меняет другой.

| Сценарий | Для чего | Адрес по умолчанию | Локальное состояние |
| --- | --- | --- | --- |
| `network` | Посмотреть готовую сеть, аналитику и взаимодействие шести ролей | `http://127.0.0.1:8766` | `.runtime/demo` |
| `onboarding` | Пройти настройку пустого пространства владельцем | `http://127.0.0.1:8767` | `.runtime/demo-onboarding` |

Demo существует отдельно от [автоматических проверок](../development/testing.md). Для него не нужны pytest, Playwright или зависимости разработки. Оно не запускает worker и модели; новые вопросы агенту здесь не выполняются. Сохранённые AI-ответы и отчёты не имитируются. Для проверки генерации нужен [обычный запуск с моделью](../operations/README.md).

## Подготовка demo с нуля

Нужны Python 3.11+ (проектное окружение — 3.12), зависимости приложения, PostgreSQL 16 и собранный frontend. Для сборки frontend используется Node.js 24 с npm. Docker необязателен: ниже есть отдельный контейнер только для локального PostgreSQL, если своего сервера нет.

Сначала установите Python по [инструкции Windows/Linux](../operations/install.md). Для быстрого отдельного PostgreSQL через Compose подготовьте Docker по той же инструкции. Если хотите demo полностью без Docker, выберите нативный PostgreSQL ниже. `.tools` не входит в репозиторий и не является зависимостью этих шагов.

### 1. Node.js и Python-окружение

Windows, PowerShell:

```powershell
winget install --exact --id OpenJS.NodeJS.LTS --source winget --accept-source-agreements --accept-package-agreements
```

Заново откройте терминал и проверьте `node --version`: нужна ветка 24. Если актуальная LTS уже сменилась, установите ветку 24 через [официальный установщик](https://nodejs.org/en/download). Из корня репозитория:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
npm.cmd --prefix frontend ci
npm.cmd --prefix frontend run build
```

Явный `python.exe` и `npm.cmd` работают без активации PowerShell-скриптов и изменения execution policy.

Ubuntu 24.04: установите Python, venv и curl, затем Node 24 через [nvm](https://github.com/nvm-sh/nvm):

```bash
sudo apt-get update
sudo apt-get install -y python3 python3-venv curl ca-certificates
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh -o /tmp/razbor-install-nvm.sh
bash /tmp/razbor-install-nvm.sh
```

Заново откройте Bash, чтобы подхватить nvm. Затем из корня проекта:

```bash
nvm install 24
nvm use 24
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
```

После сборки должен существовать `frontend/dist/index.html`. `requirements.txt` уже устанавливает базовый `sql_agent`. PyTorch, GGUF и `requirements-dev.txt` для demo не нужны. Установку повторяют после изменения зависимостей, сборку — после изменения frontend; команда demo не делает эти действия сама.

### 2. Запустите отдельный PostgreSQL

Если Docker уже работает, самый короткий вариант — [demo Compose](../../tools/demo/compose.yml), один PostgreSQL на `127.0.0.1:55434`. Для **нового** demo-окружения в PowerShell:

```powershell
New-Item -ItemType Directory -Force .runtime | Out-Null
if (-not (Test-Path .runtime/demo-postgres.env)) {
    $demoPassword = .\.venv\Scripts\python.exe -c "import secrets; print(secrets.token_urlsafe(24))"
    Set-Content -Path .runtime/demo-postgres.env -Encoding ASCII -Value "RAZBOR_DEMO_POSTGRES_PASSWORD=$demoPassword"
}
docker compose --env-file .runtime/demo-postgres.env -f tools/demo/compose.yml up -d --wait
$demoPassword = (Get-Content .runtime/demo-postgres.env | Where-Object { $_.StartsWith('RAZBOR_DEMO_POSTGRES_PASSWORD=') }).Split('=', 2)[1]
$env:RAZBOR_DEMO_DATABASE_URL = "postgresql://postgres:$demoPassword@127.0.0.1:55434/postgres"
```

Bash:

```bash
mkdir -p .runtime
if [ ! -f .runtime/demo-postgres.env ]; then
    (umask 077; .venv/bin/python -c 'import secrets; print("RAZBOR_DEMO_POSTGRES_PASSWORD=" + secrets.token_urlsafe(24))' > .runtime/demo-postgres.env)
fi
docker compose --env-file .runtime/demo-postgres.env -f tools/demo/compose.yml up -d --wait
read -r razbor_demo_setting < .runtime/demo-postgres.env
razbor_demo_password=${razbor_demo_setting#RAZBOR_DEMO_POSTGRES_PASSWORD=}
export RAZBOR_DEMO_DATABASE_URL="postgresql://postgres:$razbor_demo_password@127.0.0.1:55434/postgres"
```

Пароль сохраняется в исключённом из Git локальном файле и не меняется при повторе рецепта. Не подставляйте новый пароль уже существующему кластеру. Если demo уже настроено на другой PostgreSQL, оно продолжит использовать сервер из своего `state.json`; новый DSN его не переносит.

**Без Docker на Windows:** возьмите PostgreSQL 16 через [официальную страницу установщиков](https://www.postgresql.org/download/windows/). В мастере оставьте сервер и командные инструменты, задайте собственный пароль `postgres`, выберите свободный порт, запомните каталог данных. Stack Builder для demo не нужен. После установки убедитесь в «Службах» Windows, что установленная служба PostgreSQL запущена; включите автоматический запуск. Затем задайте DSN по следующему разделу с фактическим портом и паролем.

**Без Docker на новой Ubuntu 24.04:**

```bash
sudo apt-get install -y postgresql-16
sudo systemctl enable --now postgresql
sudo -u postgres psql -c '\password postgres'
```

Последняя команда предложит ввести пароль дважды. Используйте этот пароль и порт `5432` в DSN ниже; специальные символы внутри URL нужно кодировать. Это вариант для нового локального сервера, а не инструкция изменения пароля рабочей БД компании.

### 3. Проверьте и запустите

В PowerShell:

```powershell
.\.venv\Scripts\python.exe -m tools.demo --check
.\.venv\Scripts\python.exe -m tools.demo
```

Bash:

```bash
.venv/bin/python -m tools.demo --check
.venv/bin/python -m tools.demo
```

`--check` проверяет импорты зависимостей, сборку frontend, доступность порта и PostgreSQL. Для нового сценария проверяет права административной роли; для готового — сохранённую прикладную БД. Он не создаёт базы, не применяет миграции и не записывает состояние. Успешный результат — код `0`. При отказе устраните указанную причину до обычного запуска.

Для второго сценария добавьте `--scenario onboarding` **к обеим командам**. Дождитесь адреса demo в терминале, оставьте сервер работающим и откройте его в браузере. `--accounts` выполняется во втором терминале тем же интерпретатором. HTTP-сервер не остаётся работать после `--check` или `--prepare-only`.

### Как читать остальные команды этого руководства

Далее `python` означает **тот интерпретатор, в который установлены зависимости**: `.\.venv\Scripts\python.exe` в PowerShell или `.venv/bin/python` в Bash. Он не означает Windows Store alias. Если используете уже подготовленную копию с `.tools/python/python.exe`, этот явный путь допустим только после проверки зависимостей; такая копия не является установкой с нуля.

Существующее demo после перезагрузки требует снова работающий PostgreSQL. Для Compose запустите Docker и повторите `up -d --wait` выше; для нативного сервера запустите его службу. Сам инструмент PostgreSQL не поднимает.

## Первый запуск с локальным PostgreSQL

Первичная подготовка требует административное подключение к **отдельному локальному** серверу с правом создавать роли и базы. Demo принимает только `localhost`, `127.0.0.1` или `::1`. Оно создаёт ресурсы со случайными именами и не использует рабочую БД приложения.

PowerShell:

```powershell
$env:RAZBOR_DEMO_DATABASE_URL = 'postgresql://postgres:<пароль>@127.0.0.1:55434/postgres'
python -m tools.demo
```

Linux:

```bash
export RAZBOR_DEMO_DATABASE_URL='postgresql://postgres:<пароль>@127.0.0.1:55434/postgres'
python -m tools.demo
```

Подставьте свой порт и пароль; специальные символы реквизитов кодируются для URL. `55434` — порт предлагаемого ниже demo-контейнера. Для уже установленного PostgreSQL укажите его порт.

По умолчанию выбирается `network`. После подготовки терминал покажет адрес интерфейса. В другом терминале выведите аккаунты:

```text
python -m tools.demo --accounts
```

Для пустого пространства используйте:

```text
python -m tools.demo --scenario onboarding
python -m tools.demo --scenario onboarding --accounts
```

Первая команда занимает терминал до `Ctrl+C`; команду показа аккаунтов выполняйте в другом терминале. При первом создании второго сценария снова нужно административное подключение. Для последующих запусков подготовленного сценария оно не требуется: приложение подключается сохранённой обычной ролью.

## Готовая сеть: какие действия пройти

Сценарий `network` создаёт Арбат в Москве и Невский в Санкт-Петербурге, два показателя, месячные планы, открытый и завершённый разборы, обсуждения и техническое обращение. Логины и случайные пароли выдаёт `--accounts`.

Начните с директора. В обзоре выберите «Выручка после возвратов» и **1–31 октября 2026 года**. Даты фиксированы, поэтому при другом текущем месяце их нужно выбрать вручную.

| Область | Факт октября | План октября |
| --- | ---: | ---: |
| Арбат | 400 000 ₽ | 500 000 ₽ |
| Невский | 300 000 ₽ | 250 000 ₽ |
| Вся сеть | 700 000 ₽ | 750 000 ₽ |

В сентябрьской выборке — 500 000 ₽. Рост к ней составляет 40%, выполнение октябрьского плана — 93,33%. Источник содержит записи за 27–30 сентября и 1–4 октября; это учебная выборка, а не полный месяц. Приложение не заполняет отсутствующие продажи выдуманными нулями. Для сравнения с месячным планом выбран весь календарный месяц.

Пройдите следующие маршруты:

1. **Директор → обзор → точка Арбат.** Сравните города и точки, откройте детализацию показателя. Измените период и показатель на количество чеков; результат пересчитывается из PostgreSQL. SQL показывается у результатов агента и SQL-отчётов; в demo без worker такие результаты не создаются.
2. **Директор → разбор «Арбат: как выполнить месячный план».** Посмотрите исходное измерение, комментарий управляющего и ответ аналитика о возвратах. В разборе остаётся вопрос управляющему о двух действиях для выполнения плана.
3. **Управляющий → назначенный разбор → ответ.** Войдите управляющим, ответьте на адресный вопрос. Снова войдите директором и откройте уведомление с переходом в обсуждение. При необходимости завершите разбор с конкретным итогом.
4. **Владелец франшизы → Невский.** Посмотрите финансовые данные только своей точки и завершённый разбор «Невский: зафиксировать успешную практику». Арбат этому аккаунту недоступен.
5. **Аналитик → показатели.** Изучите формулу выручки, поле даты и привязку к точке. Можно добавить своё определение; изменение бизнес-формулы должно быть осознанным, поскольку последующие расчёты используют его.
6. **Администратор → технические обращения.** Откройте «Уточнить полноту ежедневной загрузки», добавьте технический ответ и завершите с решением. У этой роли есть управление источниками и участниками, но нет финансового доступа.

Региональный руководитель видит обе назначенные точки, планы и разборы. Директор является владельцем пространства и управляет участниками. У каждого аккаунта свой реальный набор разрешений; смена роли не сводится к изменению подписей интерфейса.

Для одновременного сравнения ролей используйте отдельные браузерные профили. Cookie привязана к хосту, а не к порту: вход в обычное приложение и demo на одном хосте в одном профиле может заменить сессию. Сами данные при этом не смешиваются.

## Пустое пространство: что проверить при настройке

Сценарий `onboarding` создаёт только директора — владельца пустого пространства. Источника, точек, показателей, планов и обсуждений ещё нет. Он подходит для проверки первого пользовательского опыта: понятно ли, с чего начать и почему пока нет финансовых результатов.

После входа пройдите настройку в порядке, который предлагает интерфейс:

1. Создайте точку с устойчивым кодом. Этот код должен соответствовать значениям колонки точки в источнике.
2. Подключите свой локальный демонстрационный PostgreSQL-источник с ролью только для чтения. Проверьте соединение, выберите доступные таблицы и колонки, настройте привязку строк к точкам.
3. Создайте показатель с корректными полями значения, даты и точки. Откройте обзор с периодом, для которого в источнике есть записи.
4. Добавьте участника, назначьте роль и область точек. Войдите им в отдельном профиле, проверьте видимые разделы и доступный результат.

Без собственного источника можно изучить пустые состояния, создание точки и участника; финансовая аналитика останется пустой. `onboarding` намеренно не подключает источник из `network` автоматически. Это сохраняет самостоятельность сценария первого запуска. Разрешённый хост источника совпадает с локальным хостом PostgreSQL, использованным при подготовке demo.

## Повторный запуск, остановка и параметры

```text
python -m tools.demo --scenario network
python -m tools.demo --scenario onboarding
```

Изменения сохраняются между запусками. Существующее пространство не заполняется заново. При запуске проверяется состояние и применяются миграции. `Ctrl+C` останавливает только HTTP-сервер; PostgreSQL продолжает работать.

Подготовить окружение без HTTP-сервера:

```text
python -m tools.demo --scenario network --prepare-only
python -m tools.demo --scenario onboarding --prepare-only
```

Выбрать другой порт **при первой подготовке**:

```text
python -m tools.demo --scenario network --port 8776
```

Порт сохраняется в состоянии. Другое значение для уже подготовленного сценария отклоняется, чтобы URL, cookie-origin и реквизиты оставались согласованными. Два сценария можно держать открытыми одновременно в разных терминалах на разных портах.

В каталоге выбранного сценария находятся `state.json` с ресурсами и секретами приложения, `accounts.json` с аккаунтами и `launch.lock` для защиты от второго запуска. У `network` есть `source.json` с реквизитами учебного источника. Файлы исключены из Git; на Linux приватные файлы создаются с правами `0600`. Административный пароль PostgreSQL инструмент в состояние demo не записывает.

Автоматического `reset` нет. Удаление JSON не удаляет созданные базы и роли. Если подготовка оборвалась, инструмент очищает только подтверждённо созданные им ресурсы; при неопределённом результате сохраняет состояние для разбора. Не удаляйте его до проверки указанных ресурсов.

## Отдельный PostgreSQL в Docker

[tools/demo/compose.yml](../../tools/demo/compose.yml) создаёт один контейнер PostgreSQL 16 в проекте `razbor-demo`. Он доступен только на `127.0.0.1:55434`; данные находятся в отдельном named volume `razbor-demo_postgres_data`. Это не production Compose: API и frontend продолжают запускаться командой Python на хосте, worker отсутствует.

Для первого создания сгенерируйте локальный пароль:

```text
python -c "import secrets; print(secrets.token_urlsafe(24))"
```

Создайте приватный файл `.runtime/demo-postgres.env` с одной строкой, подставив сгенерированное значение:

```text
RAZBOR_DEMO_POSTGRES_PASSWORD=<сгенерированный-пароль>
```

Запустите PostgreSQL из корня репозитория:

```text
docker compose --env-file .runtime/demo-postgres.env -f tools/demo/compose.yml up -d --wait
```

Если образ отсутствует, именно эта явная Docker-команда загрузит его. Python demo Docker не вызывает. После готовности контейнера задайте `RAZBOR_DEMO_DATABASE_URL` с пользователем `postgres`, сохранённым паролем и портом `55434`, затем выполните нужную команду demo из раздела первого запуска.

Остановка с сохранением данных:

```text
docker compose --env-file .runtime/demo-postgres.env -f tools/demo/compose.yml stop
```

Повторный `up -d --wait` использует тот же volume. Пароль из файла нужен для первого создания кластера; изменение переменной позже не меняет пароль уже созданной PostgreSQL-роли. Сохраняйте файл вместе с локальным окружением, особенно если планируете первичную подготовку второго сценария. Не запускайте `down -v`, если хотите сохранить учебные данные.

## Если запуск не удался

| Симптом | Что проверить |
| --- | --- |
| Нет `frontend/dist/index.html` | Выполните сборку frontend; demo не делает её автоматически |
| Не найден Python-пакет | Используется ли окружение с установленным `requirements.txt` и базовым `sql_agent` |
| Не удаётся создать demo | Для первого запуска нужны `RAZBOR_DEMO_DATABASE_URL`, работающий локальный PostgreSQL и право создавать БД и роли |
| PostgreSQL не принимает подключения | Запустите локальный PostgreSQL или demo-контейнер. После перезагрузки компьютера сервер может быть остановлен; команда demo сама его не запускает |
| Порт занят | Остановите свой предыдущий экземпляр через `Ctrl+C`; demo не завершает чужие процессы |
| Файлы состояния не согласованы | Сохраните каталог сценария и проверьте перечисленные в нём ресурсы; автоматического пересоздания нет |
| В обзоре нет чисел готовой сети | Выберите октябрь 2026 года и показатель; проверьте доступ текущей роли |
| Вопрос агенту не даёт результата | В demo нет worker; используйте обычный запуск с моделью для AI-сценария |

Устройство инструмента и места изменения сценариев описаны в [tools/demo/README.md](../../tools/demo/README.md). Продуктовые правила находятся в [backend](../../backend/README.md), а визуальные компоненты — во [frontend](../../frontend/README.md).

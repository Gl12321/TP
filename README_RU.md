# SQL Agent

**Вы описываете обычными словами, что хотите узнать из базы данных, — приложение выполняет запрос и показывает готовую таблицу.**

Например: «Покажи выручку по месяцам за прошлый год» или «Какие товары заказывают чаще всего?». Приложение само определяет, какие таблицы нужны, как их связать и какие значения посчитать. Писать SQL вручную для этого не требуется. Под готовой таблицей можно раскрыть блок «SQL этого результата», посмотреть выполненный запрос и скопировать его для проверки.

Это способ быстро исследовать свои данные: сравнивать периоды, находить нужные записи, считать суммы и строить сводные таблицы. Вы загружаете SQLite-базу, выбираете данные для анализа и задаёте вопрос в браузере. Модели и обработка данных работают на вашем компьютере.

## Пример использования

Допустим, у вас есть база интернет-магазина с заказами, покупателями и товарами. Чтобы узнать, как меняются продажи, вы задаёте вопрос: «Посчитай сумму оплаченных заказов по месяцам за 2025 год». Если база содержит даты заказов, суммы и признак оплаты, ответом будет таблица такого вида. Числа ниже приведены только для примера:

| Месяц | Сумма оплаченных заказов |
| --- | ---: |
| Январь 2025 | 125 000 |
| Февраль 2025 | 148 000 |
| Март 2025 | 139 000 |

Затем можно задать другой самостоятельный вопрос: «Покажи десять товаров с наибольшим количеством продаж за 2025 год». Приложение заново выберет нужные таблицы и способ расчёта. Каждый вопрос обрабатывается самостоятельно; история диалога и уточнения вроде «а теперь только за март» пока не используются как контекст.

При обычной работе достаточно понимать, какой результат вам нужен. Полезно указать период, нужную группировку и правила отбора: например, учитывать ли отменённые заказы. Знание имён столбцов не обязательно, но понятные названия и описания в самой базе помогают приложению правильно связать вопрос с данными.

## Как вопрос становится таблицей

При загрузке приложение переносит данные в PostgreSQL и составляет каталог: какие есть таблицы и столбцы, что они содержат и как связаны. Этот каталог помогает ориентироваться в базе, даже если в ней много таблиц.

Каталог и данные выполняют разные роли. Каталог нужен, чтобы выбрать способ получения ответа: где лежат суммы, какие поля обозначают даты, через что соединяются заказы и покупатели. Сами значения остаются в БД и обрабатываются запросом. Такой подход позволяет считать ответ по всем подходящим записям, не помещая всю базу в контекст модели.

Дальше каждый вопрос проходит четыре шага:

1. **Найти нужные данные.** Для вопроса о выручке понадобятся, например, заказы, даты и суммы. Приложение ищет подходящие таблицы и добавляет связи между ними. Этим занимается [поиск по каталогу](src/rag/README.md).
2. **Составить способ расчёта.** Локальная модель получает вопрос и описание выбранных таблиц, затем составляет SQL. Модель работает со структурой базы; сами строки обрабатывает PostgreSQL. За генерацию отвечают [модель и промпты](src/llm/README.md).
3. **Проверить и выполнить запрос.** Приложение проверяет, что используются существующие таблицы и допустимые операции. Запрос выполняется с правами только на чтение. Если возникает исправимая ошибка, агент передаёт её модели для следующей попытки. Здесь взаимодействуют [агент](src/agent/README.md), [проверка SQL](src/sql/README.md) и [доступ к БД](src/database/README.md).
4. **Показать ответ.** В браузере появляется таблица с результатом и SQL, которым она получена. Если данных или возможностей приложения недостаточно, оно показывает причину. Отображением и отменой запроса управляет [интерфейс](frontend/README.md).

Смысл показателя должен следовать из вопроса и данных. Например, «выручка» может означать сумму всех заказов или только оплаченных: такие условия стоит указывать явно. Проверка SQL обнаруживает технические ошибки, но не выбирает за пользователя определение бизнес-показателя.

Пустая таблица означает, что запрос выполнен, но подходящих строк не найдено. Это отличается от ситуации, когда приложение не смогло построить запрос: во втором случае показывается причина. Если результат слишком велик, интерфейс сообщает, что выведена только его часть. Тогда вопрос можно сузить по периоду, условиям или нужной группировке.

## Как устроен проект

[Агент](src/agent/graph.py) связывает поиск, генерацию, проверку и выполнение в один процесс. Каждый этап решает свою задачу и передаёт следующему результат через [общие типы данных](src/domain/README.md). Поэтому можно менять модель или улучшать поиск, сохраняя остальные части приложения.

Разделение следует этапам работы с вопросом. Поиск отвечает за то, какие данные доступны модели; генератор — за построение запроса; проверка — за допустимость этого запроса; исполнитель — за чтение результата из БД. Интерфейс получает события о ходе обработки и конечный ответ через API. Он не управляет моделью и не подключается к PostgreSQL напрямую.

Генерация ограничена грамматикой допустимых SQL-конструкций, а готовый запрос дополнительно разбирается и проверяется по структуре. Это два разных этапа: первый помогает модели построить запрос допустимой формы, второй проверяет конкретные таблицы, столбцы и операции. Подробности находятся в модуле SQL; для использования приложения знать устройство грамматики не требуется.

| Часть | Роль |
| --- | --- |
| [database](src/database/README.md) | Хранит данные, читает структуру БД и выполняет запросы |
| [rag](src/rag/README.md) | Находит в базе данные, относящиеся к вопросу |
| [llm](src/llm/README.md) | Превращает вопрос и описание данных в SQL |
| [sql](src/sql/README.md) | Задаёт допустимый язык запросов и проверяет результат генерации |
| [agent](src/agent/README.md) | Управляет этапами и исправлением ошибок |
| [api](src/api/README.md) | Принимает действия пользователя и передаёт ход обработки |
| [frontend](frontend/README.md) | Показывает загрузку данных, вопрос, SQL и готовую таблицу |
| [runtime](src/runtime/README.md) | Готовит модели и подключение перед запуском |

Для обычной аналитики доступны фильтры, объединение таблиц, группировки, суммы, количество, средние, сортировка и операции с датами. Точные возможности и текущие ограничения описаны в [документации SQL](src/sql/README.md).

Импорт и вопросы выполняются последовательно. Это позволяет одному комплекту моделей обслуживать приложение и не допускать ситуации, когда таблицы меняются посреди расчёта. Отмена запроса передаётся через те же слои до генерации или выполнения SQL; следующий запрос допускается после освобождения занятых ресурсов.

## Запуск

Нужны **Python 3.11+ и работающий Docker с Compose v2**. На Windows используется Docker Desktop в режиме Linux-контейнеров, на Linux — Docker Engine с Compose. Библиотеки приложения и PostgreSQL устанавливаются внутри контейнеров.

Из каталога проекта:

```text
python run.py
```

Если в Linux Python доступен только как `python3`, используйте `python3 run.py`; остальные флаги те же.

Команда собирает окружение, проверяет выбранную модель, скачивает недостающие файлы, готовит БД и запускает интерфейс. После сообщения о готовности откройте **http://localhost:8501**.

Первый запуск требует интернета и может быть долгим: загружаются образы, библиотеки и веса. При повторном запуске проверенные модели используются с диска. Прерванная загрузка продолжается при следующем запуске. Ошибка подготовки не позволяет запустить API с неполным комплектом моделей.

После открытия интерфейса загрузите один или несколько файлов SQLite и дождитесь завершения импорта. Выберите появившиеся схемы — это наборы таблиц из загруженных баз — и сформулируйте вопрос. Во время обработки виден её ход; после завершения появится таблица и раскрываемый блок с SQL. Загруженную базу можно использовать для следующих вопросов без повторного импорта.

Выбор модели:

```text
python run.py --list-models
python run.py --model qwen3.5-27b
```

Список берётся из [config.yaml](config.yaml). В нём также задаётся модель по умолчанию. Команда списка не скачивает веса; при первом обращении она собирает небольшое окружение подготовки.

Остановка с сохранением данных и моделей:

```text
python run.py --stop
```

Приложение работает в фоне. Параллельные запуски блокируются на время подготовки; при смене модели прежний API останавливается до загрузки новой модели в память.

## Настройки и данные

Все обычные настройки собраны в [config.yaml](config.yaml): модель по умолчанию, каталог моделей, размер контекста, ограничения результатов, время обработки и параметры поиска. Чтобы изменить их, отредактируйте YAML и повторите команду запуска.

Пароли БД и токен доступа создаются автоматически и сохраняются в `.runtime/compose.env`. Их не нужно вводить в браузере. Этот файл исключён из Git; его нужно сохранять вместе с БД, поскольку повторная генерация паролей не меняет пароль уже созданной базы.

Веса остаются в `models/`, индекс и служебные данные — в `data/`, сама PostgreSQL — в постоянном Docker volume. Остановка приложения ничего из этого не удаляет. В интерфейсе есть отдельная операция удаления всех пользовательских схем: она удаляет данные БД, поэтому требует подтверждения.

Повторная загрузка файла с тем же именем заменяет соответствующую схему. Если перенос данных завершить не удалось, изменения этого файла откатываются. Обновление поискового каталога — отдельный этап: при его сбое схема помечается как требующая переиндексации и временно исключается из вопросов. Переиндексация восстанавливает каталог по данным PostgreSQL.

Большая модель требует памяти не только для весов, но и для обработки вопроса. На компьютере с 24 ГБ RAM начните с модели по умолчанию; профиль 27B имеет уменьшенный контекст, но его работу нужно проверить на вашей машине. Docker должен иметь доступ к достаточному объёму RAM; особенно это важно для Docker Desktop. Подготовка проверяет целостность файлов, а при загрузке модели приложение проверяет доступную память.

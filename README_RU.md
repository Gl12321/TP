# Разбор

**Напишите обычными словами, какие данные нужны, получите готовую таблицу из своей базы и разберите результат вместе с командой.**

«Разбор» — рабочее пространство для сети магазинов, заведений или франшиз. Руководитель видит показатели и планы по городам и точкам, аналитик задаёт единые определения расчётов, управляющий объясняет ситуацию на своей точке. Для вопроса, которого нет на готовом экране, есть ассистент: он составляет SQL, выполняет разрешённое чтение подключённой базы и возвращает таблицу с основанием расчёта.

Например, руководитель замечает снижение выручки, спрашивает «Покажи продажи по точкам за сентябрь» и получает результат. Его можно проверить по SQL, сохранить в отчёт и обсудить с управляющим в разборе. Адресный вопрос получает конкретного получателя, ответ остаётся рядом с исходными числами, а завершение фиксируется отдельным итогом. Штатный показатель можно измерить повторно за другой период, сохранив первое наблюдение.

Личные разговоры, общие отчёты и обсуждения разделены. Участник работает только со своими точками и разрешёнными источниками; технический администратор может обслуживать подключение без финансового доступа. Обзор, планы, роли, обсуждения и уведомления выполняются обычным кодом. Локальная языковая модель нужна для новых вопросов к данным и их смыслового продолжения.

## Что можно делать

| Сценарий | Результат |
| --- | --- |
| Сравнить сеть, города и отдельные точки | Факт, план, сопоставимый прошлый период и динамика по дням/неделям |
| Задать вопрос к своей базе | Таблица, SQL, условия расчёта, график и CSV |
| Сохранить полезный расчёт | Отчёт с неизменяемым исходным результатом и историей пересчётов |
| Передать наблюдение ответственному | Разбор с основанием, комментариями, адресными вопросами, ответами и итогом |
| Исправить проблему источника | Техническое обращение администратору с историей решения |
| Подключить команду и данные | Приглашения, роли, области точек, профили PostgreSQL, показатели и планы |

Полное описание возможностей, прав и конкретных сценариев взаимодействия сотрудников — в [PRODUCT.md](docs/PRODUCT.md).

## Как устроен проект

Продукт состоит из трёх основных частей:

| Часть | Ответственность |
| --- | --- |
| [Frontend](frontend/README.md) | React и TypeScript: страницы, формы, таблицы, SQL, графики и совместная работа |
| [Backend](backend/README.md) | Python/FastAPI: сессии, права, источники, показатели, история, обсуждения и очередь заданий |
| [SQL-агент](packages/sql_agent/README.md) | Самостоятельная Python-библиотека: поиск подходящих таблиц, промпты, генерация и проверка SQL |

Служебная PostgreSQL хранит состояние приложения. База бизнеса подключается отдельно и остаётся источником аналитики. API рассчитывает штатные показатели и обслуживает интерфейс; отдельный worker выполняет задания через библиотеку `sql_agent`. Очередь и результаты сохраняются в PostgreSQL, поэтому закрытие браузера не теряет запущенную работу.

Модель получает разрешённое описание структуры, а готовый запрос проходит проверку. Backend ограничивает таблицы, поля и строки областью сотрудника; источник используется с учётной записью только для чтения. Корректный SQL не заменяет согласованное определение бизнес-показателя: его смысл и исходные данные задаёт команда.

Схема компонентов, границы ответственности и движение запроса описаны в [архитектуре](docs/ARCHITECTURE.md).

## Запуск после подготовки окружения

На компьютере нужны **Python 3.11+** и работающий **Docker с Compose v2**. Windows использует Docker Desktop с Linux-контейнерами; Linux — Docker Engine с Compose. Node.js и Python-зависимости приложения собираются внутри образов и для этого способа не устанавливаются на хост отдельно.

Если этих инструментов ещё нет, начните с [установки с нуля](docs/operations/install.md): там команды установки Python, WSL 2 и Docker, перезагрузка, права пользователя и проверка результата. Одна команда проекта запускает **подготовленное** окружение; она не устанавливает Python или Docker на компьютер.

В Windows, после установки Python Launcher и запуска Docker Desktop, из корня проекта:

```powershell
py -3.12 run.py --check
py -3.12 run.py --model qwen3.5-9b
```

В Linux, после установки Python и запуска Docker Engine:

```bash
python3 run.py --check
python3 run.py --model qwen3.5-9b
```

Продолжайте после успешного `--check`: проверка должна подтвердить работающий Engine с Linux-контейнерами. Если `python` открывает Microsoft Store, это заглушка, а не установленный Python; используйте проверенный `py -3.12` или явный путь к интерпретатору. Подготовленная `.tools/python` существует только в отдельных рабочих копиях и не скачивается вместе с репозиторием.

Откройте `http://localhost:8000`, когда адрес появится в терминале. Для создания первого аккаунта понадобится выводимый код первоначальной настройки. Повторный запуск использует существующие аккаунты и данные. `--check` проверяет инструменты хоста; сборка образов и генерация моделью происходят при настоящем запуске.

Launcher собирает необходимые образы, подготавливает базу и миграции, запускает интерфейс и worker. Уже подготовленные модели используются с диска; отсутствующие файлы выбранной модели и поиска загружаются автоматически. При готовом окружении достаточно той же команды. Для первого запуска без кеша нужны доступ к сети, место под образы/веса и память выбранного профиля.

Доступны `qwen3.5-4b`, `qwen3.5-9b` и `qwen3.5-27b`. Каталог и параметры находятся в [config.yaml](config.yaml), назначение моделей — в [документации агента](docs/development/sql-agent.md). Размер файла модели не равен общему потреблению памяти приложением.

Остальные действия добавляются к той же команде `py -3.12 run.py` в Windows или `python3 run.py` в Linux:

| Флаг | Действие |
| --- | --- |
| `--check` | Проверить Python, Compose и Engine без установки, сборок и весов |
| `--list-models` | Показать каталог; Docker и служебный образ необходимы |
| `--without-ai` | Запустить обычное приложение без worker и весов |
| `--stop` | Остановить контейнеры, сохранив данные |

`--without-ai` запускает интерфейс и API без загрузки весов и без worker: можно настроить пространство, работать с обычной аналитикой, обсуждениями и сохранёнными результатами; новые вопросы и пересчёт SQL-отчётов недоступны. `--stop` останавливает контейнеры, сохраняя базы, модели и секреты.

Новое пространство начинается с настройки точек, источника и показателя. Перед подключением внешней базы оператор добавляет её хост в `application.source_hosts` файла YAML: по умолчанию список пуст. Наличие работающего интерфейса само по себе не означает, что бизнес-данные уже подключены.

## Демонстрация продукта

Demo открывает подготовленную сеть с шестью ролями, финансовыми данными и примерами совместной работы. Сценарий `onboarding` открывает отдельное пространство для знакомства с первичной настройкой. Сценарии используют собственные базы и сохраняют изменения; тестовые наборы их данные не используют.

Это нативный запуск: нужны установленный Python, зависимости из `requirements.txt`, собранный frontend и **запущенный отдельный PostgreSQL**, который команда demo сама не запускает. При первой подготовке нужен административный `RAZBOR_DEMO_DATABASE_URL`; после подготовки сервер всё равно должен работать. Node.js нужен для первоначальной сборки интерфейса. Модели и worker не запускаются.

[Demo с нуля](docs/demo/README.md#подготовка-demo-с-нуля) показывает установку Node, Python-окружение, запуск PostgreSQL, подготовку и проверку обоих сценариев. После подготовки, в Windows:

```powershell
.\.venv\Scripts\python.exe -m tools.demo --check
.\.venv\Scripts\python.exe -m tools.demo
```

В Linux используется `.venv/bin/python` с теми же аргументами. Порты, аккаунты и последовательность просмотра — в [руководстве demo](docs/demo/README.md).

## Автоматические проверки

Сначала подготовьте Python-окружение с `requirements-dev.txt` и frontend с `npm ci` по [инструкции разработки](docs/development/README.md#2-окружение-windows-и-linux). Затем `.\.venv\Scripts\python.exe tools/check.py quick` в Windows или `.venv/bin/python tools/check.py quick` в Linux проверяет основные контракты Python-кода, frontend и TypeScript без сервера PostgreSQL и моделей. Компактный набор сосредоточен на границах доступа, SQL, точности финансовых данных и безопасном повторе действий. Он не подменяет ручной просмотр всех экранов или оценку качества настоящей модели.

Отдельно запускаются проверки PostgreSQL и браузера. Их окружение и данные отделены от демонстрации продукта. Команды Windows/Linux, зависимости и смысл результата — в [руководстве проверок](docs/development/testing.md).

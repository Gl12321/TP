# Данные и выполнение запросов

Готовая таблица в ответе должна содержать значения из базы, а не числа, придуманные моделью. Этот модуль хранит импортированные данные в PostgreSQL, сообщает приложению их структуру и выполняет проверенный SQL, возвращая настоящие строки результата.

Для подготовки данных нужны права создавать и заменять таблицы. Для ответа на вопрос достаточно чтения. Эти операции используют разные подключения, чтобы ошибка генерации не получила административных возможностей.

## Основные операции

[client.py](client.py) владеет двумя пулами соединений: административным и для аналитического чтения. Их создаёт и закрывает [жизненный цикл API](../api/app.py); импорт Python-модуля не открывает подключения.

[metadata.py](metadata.py) читает схемы, колонки и связи между таблицами и возвращает [общие типы](../domain/schema.py). Эти сведения нужны и поиску, и генерации, и проверке SQL. Текстовое представление DDL сохраняется вместе со структурой, но промпт строится из типизированных полей таблицы.

[migration](migration/README.md) переносит SQLite в PostgreSQL одной транзакцией на файл. [executor.py](executor.py) выполняет SQL, который уже прошёл [проверку](../sql/README.md). [identifiers.py](identifiers.py) отвечает за имена: экранирование, ограничение PostgreSQL в 63 байта UTF-8 и запрет системных схем.

Операция `drop_all_schemas()` удаляет все схемы, кроме `public`, `information_schema` и имён с префиксом `pg_`, независимо от того, кто их создал. [API](../api/routes/schemas.py) отвечает за авторизацию операции, исключение параллельных изменений и очистку индекса.

## Как исполняется аналитический запрос

Каждый запрос получает отдельную транзакцию `READ ONLY`, локальные таймауты выполнения и ожидания блокировки. `search_path = pg_catalog` исключает поиск одноимённых функций в пользовательских схемах, а `standard_conforming_strings = on` делает обработку строковых литералов определённой. Имена таблиц в SQL должны включать схему.

Строки читаются серверным курсором. Исполнитель ограничивает их количество и суммарный размер накопленных значений; дополнительная строка позволяет сообщить об усечённом результате. Одна слишком большая строка вызывает `result_too_large`. Отдельная [сериализация результата](../sql/results.py) ограничивает размер JSON-ответа.

Эти пределы ограничивают память приложения, но не промежуточную работу PostgreSQL и не размер одной ячейки, которую сервер уже начал передавать. Время работы ограничивается таймаутом. Сигнал отмены проверяется во время SQL и между строками; операция завершается после закрытия курсора, отката и освобождения соединения.

Синтаксические ошибки, неизвестные колонки и ошибки типов или группировки могут вернуться [агенту](../agent/README.md) для исправления запроса. Недостаток прав, таймаут и потеря соединения завершают вопрос без повторной генерации.

## Пример получения таблицы

Для вопроса о сумме заказов по месяцам исполнитель получает готовый SELECT с группировкой. Он не обращается к модели и не выбирает подходящие таблицы заново: к этому моменту [агент](../agent/README.md) уже собрал контекст, а [валидатор](../sql/validation.py) проверил запрос. PostgreSQL рассчитывает суммы, после чего строки последовательно добавляются в `QueryResult`.

Если агрегат вернул значения Decimal, они не должны незаметно округлиться до float при передаче через API. Поэтому получение значений и их сетевое представление разделены: исполнитель сохраняет исходные значения, а сериализатор выбирает подходящий формат ответа. Интерфейс получает рассчитанный результат, а не второе вычисление той же метрики на клиенте.

При отмене запрос не просто исчезает из интерфейса. Исполнитель дожидается прекращения работы с курсором и завершения транзакции, после чего возвращает соединение в пул. Так следующий вопрос не наследует незавершённый запрос, его локальные таймауты или состояние предыдущей транзакции.

## Роль чтения

До готовности API `verify_read_role()` проверяет, что роль запросов не является административной, не состоит в административных ролях, не владеет БД, не имеет доступа к серверным файлам и программам и не может изменять существующие пользовательские таблицы. Эта проверка не создаёт роли и не выдаёт права. Порядок подготовки подключения задаёт [общий запуск](../../README_RU.md).

При работе с собственной PostgreSQL роли запросов нужны `USAGE` на схемы и `SELECT` на таблицы. Для новых объектов, создаваемых ролью `importer`, права можно определить заранее:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE importer GRANT USAGE ON SCHEMAS TO reader;
ALTER DEFAULT PRIVILEGES FOR ROLE importer GRANT SELECT ON TABLES TO reader;
```

Роли в примере должны уже существовать. Для существующих объектов права выдаются отдельно; правила описаны в [документации PostgreSQL](https://www.postgresql.org/docs/16/sql-alterdefaultprivileges.html). При отказе доступа приложение не переключается на административное подключение.

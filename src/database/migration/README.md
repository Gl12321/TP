# Перенос SQLite в рабочую базу

Импорт позволяет взять существующий SQLite-файл и задавать вопросы по его данным. Таблицы переносятся в отдельную схему PostgreSQL; приложение сохраняет их структуру и связи, чтобы затем находить нужные данные и строить запросы.

Если файл заменяет уже загруженную схему, неудачный перенос должен сохранить прежние данные. Поэтому проверка исходного файла выполняется до изменения PostgreSQL, а замена схемы и запись строк проходят одной транзакцией.

## Порядок переноса

1. Проверить размер и заголовок файла, открыть SQLite только для чтения.
2. В исходной транзакции проверить целостность, внешние ключи и размер структуры, затем прочитать метаданные.
3. Подготовить отдельную копию структуры для PostgreSQL, сохранив исходные метаданные SQLite.
4. Проверить зависимости прежней схемы, заменить её и перенести строки пакетами в одной транзакции PostgreSQL.
5. Создать индексы, затем внешние ключи, включая циклические ссылки и ссылки на уникальные индексы; настроить существующие последовательности.
6. Зафиксировать изменения целиком. Ошибка откатывает также удаление старой схемы.

[validation.py](validation.py) проверяет SQLite без SQLAlchemy. [mapping.py](mapping.py) переводит типы, значения по умолчанию и связи. [importer.py](importer.py) управляет соединениями и транзакцией. Вызов `DatabaseImporter.migrate_db(schema_name, sqlite_path)` синхронный; [API](../../api/routes/schemas.py) выполняет его в рабочем потоке, передаёт точное имя схемы и удаляет временный файл после обработки. Регистр имён сохраняется; системные схемы и `public` недопустимы.

## Какие данные переносятся

Поддерживаются обычные таблицы с целочисленными, вещественными, decimal, текстовыми, бинарными, логическими, JSON и календарными колонками; первичные, уникальные и внешние ключи; обычные и частичные индексы. Предикаты частичных индексов и CHECK должны быть совместимы с PostgreSQL, иначе импорт откатывается.

SQLite допускает более свободные значения, чем PostgreSQL. Поэтому INTEGER переносится в BIGINT, строковые типы — в TEXT, а NUMERIC не получает принудительные precision/scale: иначе возможно незаметное округление. Преобразования чисел и BOOLEAN драйвером SQLite отключены. Например, значение `2` в BOOLEAN не превращается незаметно в `TRUE`, а отклоняется при записи. Несовместимое с объявленным типом значение приводит к отказу с сохранением прежней схемы.

Поддерживаются литеральные DEFAULT и `CURRENT_DATE`, `CURRENT_TIME`, `CURRENT_TIMESTAMP`. Другие выражения по умолчанию отклоняются до изменения PostgreSQL. Виртуальные таблицы, вычисляемые и скрытые колонки, индексы по выражениям или нестандартным COLLATE, колонки без отражаемого типа и ссылки на подключённые SQLite-базы не поддерживаются. Представления и триггеры не переносятся.

Последовательность изменяется только при подтверждении её существования через `pg_get_serial_sequence` у единственного первичного ключа. Для пустой таблицы следующим будет номер 1, для непустой — число больше максимального положительного ключа. История удалённых значений SQLite AUTOINCREMENT не переносится.

## Согласованность с поиском

Поисковый индекс описывает структуру базы, поэтому после замены таблиц его нужно обновить. Перед изменением PostgreSQL импорт вызывает необязательный `before_replace`; API сохраняет в нём отметку неактуального индекса. Callback выполняется после предварительных проверок, поэтому заведомо некорректный файл не блокирует поиск по прежним данным. Ошибка callback предотвращает импорт.

После переноса [каталог RAG](../../rag/indexing/README.md) перестраивается. Если работа оборвалась, схема не используется поиском до успешной переиндексации. У PostgreSQL и ChromaDB нет общей транзакции; отметка неактуальности сохраняет это ограничение и после перезапуска.

Например, пользователь повторно загрузил `sales.sqlite`, но одна из новых строк не подходит типу PostgreSQL. Транзакция откатывает замену, и прежние таблицы `sales` сохраняются. Если отметка индекса уже была выставлена, для возвращения схемы в поиск нужна переиндексация: приложение не предполагает, что два независимых хранилища обязательно остались согласованными после сбоя.

Если тот же файл оказался повреждённым уже при предварительной проверке SQLite, до замены схемы дело не доходит. Прежний индекс в этом случае не отмечается как устаревший. Такое различие сохраняет доступность исправных данных при заведомо непригодной новой загрузке.

Если удаление прежней схемы через CASCADE затронет объект другой схемы, импорт отклоняется до удаления. Проверка использует дерево `pg_depend` и [адреса объектов PostgreSQL](https://www.postgresql.org/docs/16/functions-info.html#FUNCTIONS-INFO-OBJECT-TABLE). Внешние изменения структуры нужно проводить при остановленном API, затем перестраивать индекс: блокировка приложения не управляет сторонними административными сессиями.

При расширении импорта новая возможность должна сохранять смысл исходных значений и откат всей замены. Добавление преобразования типа недостаточно проверить на одной строке: важны NULL, граничные значения, ключи и случай, когда неподходящее значение появляется в последнем пакете. Эти свойства проверяются отдельно от качества SQL, которое выдаёт модель.

# Общий язык приложения

Разным частям приложения нужно одинаково понимать, что такое таблица, найденные данные и результат вопроса. Например, поиск выбирает таблицу, модель получает её колонки, а проверка SQL убеждается, что запрос использует именно эти колонки. Здесь определены общие типы, которые связывают эти этапы.

## Структура данных и результат

[schema.py](schema.py) описывает таблицы, колонки, первичные и внешние ключи. Таблица определяется парой `(schema, name)`: это сохраняет различие между одноимёнными таблицами в разных схемах. `TableRef.key` служит для отображения, а не для восстановления имени из строки.

[query.py](query.py) описывает один вопрос и его исход. `QueryContext` связывает идентификатор запроса, сообщения о ходе работы и сигнал отмены. `QueryResult` содержит SQL, названия колонок и строки результата; `AgentResult` добавляет статус и причину неудачи. Строки хранятся массивами, чтобы одинаковые названия колонок не приводили к потере значений.

`QueryError` отличает ошибку, которую модель может исправить, от причины остановить работу. `GenerationRefusal` обозначает ситуацию, когда данных недостаточно или вопрос выходит за поддерживаемые возможности SQL.

## Почему формы данных важны

Например, `sales.orders` и `archive.orders` — разные таблицы, хотя короткое имя совпадает. Более того, точка может оказаться частью самого имени. Раздельные поля схемы и таблицы позволяют сохранять их идентичность без разрезания строки по разделителю и без зависимости от того, как имя показано пользователю.

У результата похожая задача. Запрос может вернуть две колонки `name`: имя покупателя и имя товара. Если представить строку словарём с одним ключом `name`, одно значение потеряется. Пара `columns` и `rows` сохраняет обе позиции; интерфейс может дать им разные подписи, не меняя данные.

Статус вопроса также не выводится из количества строк. Пустая таблица после корректного SQL, отказ из-за недостатка данных и оборванное соединение имеют разные причины и требуют разного поведения интерфейса. Общие типы дают агенту и API один способ передать это различие.

## Связь с остальным кодом

[Агент](../agent/README.md), [поиск](../rag/README.md), [база данных](../database/README.md), [генератор](../llm/README.md) и [API](../api/README.md) используют эти типы. Сам `domain` зависит только от стандартной библиотеки и не знает об их реализации.

Для каждого вопроса создаётся новый `QueryContext`. Модели, пулы соединений и HTTP-объекты остаются в своих модулях: их срок жизни отличается от срока жизни одного вопроса.

Например, нажатие кнопки отмены меняет сигнал в контексте текущего вопроса. Генерация, поиск и выполнение SQL проверяют этот сигнал, не зная, что он пришёл из Streamlit. Тот же механизм можно использовать в другом клиенте без добавления зависимости от интерфейса в каждый компонент.

При добавлении нового поля стоит определить, относится ли оно к данным предметной области или к конкретной библиотеке. Имена колонок и признак усечения результата нужны нескольким слоям; объект HTTP-ответа или внутренний тензор модели сюда не относятся. Эта граница удерживает общие типы небольшими и пригодными для независимых проверок.

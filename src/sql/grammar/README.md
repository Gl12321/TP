# Язык аналитических запросов

Грамматика задаёт, какие запросы модель может написать для получения таблицы. Она покрывает базовую аналитику: выбор строк, объединение связанных таблиц, суммы и количества по группам, фильтрацию и сортировку. Во время генерации движок допускает только продолжения, соответствующие этим правилам.

Это помогает получать SQL в определённом формате и с известными именами таблиц. Грамматика работает вместе с [проверкой SQL](../README.md): она ограничивает форму текста, а валидатор проверяет связи между частями готового запроса.

## Как собирается язык

[builder.py](builder.py) получает структуру выбранных таблиц и добавляет правила их имён и колонок к трём частям GBNF. Одна и та же структура используется [промптом](../../llm/prompts.py), поэтому модель видит именно те имена, которые может сгенерировать.

| Файл | Что определяет |
| --- | --- |
| [lexical.gbnf](lexical.gbnf) | Пробелы, числа, строки, даты, интервалы и операторы |
| [expressions.gbnf](expressions.gbnf) | Арифметику, условия, CASE, функции и агрегаты |
| [select.gbnf](select.gbnf) | SELECT, JOIN, фильтры, группировку, сортировку и ограничения |
| [builder.py](builder.py) | Проверку метаданных, псевдонимы и экранирование терминалов |

## Поддерживаемые конструкции

`SELECT DISTINCT`, `*`, квалифицированные колонки и выходные псевдонимы;
`INNER JOIN`, `LEFT JOIN` с `ON`; сравнения, `NOT`, `AND`, `OR`, скобки,
`IN` со списком, `BETWEEN`, `IS [NOT] NULL/TRUE/FALSE`, `LIKE`, `ILIKE`;
`+ - * / %`, отрицательные и дробные числа; `CASE WHEN`, `COALESCE`, `NULLIF`;
`COUNT(*)`, `COUNT(DISTINCT expression)`, `SUM`, `AVG`, `MIN`, `MAX`;
`GROUP BY`, `HAVING`, `ORDER BY` с ASC/DESC и NULLS FIRST/LAST для каждого элемента;
`LIMIT`, `OFFSET`; `DATE`, `TIMESTAMP`, `INTERVAL`, `CURRENT_DATE`, `DATE_TRUNC`, `EXTRACT`.

Приоритет выражений: арифметика с умножением перед сложением; сравнение; NOT; AND; OR. `BETWEEN ... AND ...` — одно условие.

Скалярные выражения не содержат агрегатов. SELECT/HAVING/ORDER используют расширенные выражения; аргумент агрегата всегда скалярный. `SUM(*)` и вложенные агрегаты не входят в язык.

Для практической аналитики это означает, что можно сначала отобрать строки по периоду или статусу, затем посчитать сумму по группам и оставить только группы выше заданного значения. WHERE относится к исходным строкам, HAVING — к уже сформированным группам. Разделение выражений в грамматике не позволяет поставить агрегат туда, где он не имеет такого смысла.

## Имена и формат

Таблицы сортируются по `(schema, name)` и получают псевдонимы `t0`, `t1`, … . `SQLGrammarBuilder.aliases(tables)` возвращает тот же набор для промпта. Например, запрос сумм заказов по покупателям имеет такой вид:

```sql
SELECT t0."name", SUM(t1."amount") AS "total"
FROM "sales"."customers" AS t0
LEFT JOIN "sales"."orders" AS t1 ON t0."id" = t1."customer_id"
GROUP BY t0."name"
ORDER BY "total" DESC
```

Псевдоним привязан к таблице во всём текущем контексте независимо от порядка JOIN. Ключевые слова пишутся в верхнем регистре. Имена таблиц и колонок всегда заключены в двойные кавычки; кавычка внутри имени удваивается. Затем готовый SQL-идентификатор отдельно экранируется как строка GBNF. Это два разных этапа экранирования. Строковые значения используют одинарные кавычки и удвоение `'` внутри.

Грамматика ограничивает доступные имена, но не доказывает наличие их таблиц в FROM, уникальность выбранных источников или соответствие GROUP BY. Эти условия проверяет [SQLValidator](../validation.py). Типы аргументов SQL-функций в конечном счёте проверяет PostgreSQL.

Канонические псевдонимы нужны для согласования генерации с контекстом. Если одна и та же таблица всегда называется `t1` в текущем вопросе, промпт, допустимые имена колонок и проверка результата относятся к одному источнику. Порядок появления таблицы в SQL при этом можно менять, не переназначая псевдонимы в описании схемы.

## Ограничения и отказ от генерации

Не поддерживаются CTE, подзапросы, UNION, оконные функции, CROSS/RIGHT/FULL JOIN, самосоединения, пользовательские функции и произвольные CAST. `COUNT(DISTINCT ...)` принимает одно выражение; DISTINCT у других агрегатов недопустим. Простая форма `CASE value WHEN ...` заменяется на `CASE WHEN value = ...`.

Если вопрос нельзя выразить этим языком или для него недостаточно данных, модель должна иметь возможность отказаться от SQL. В режиме `allow_refusal=True` корневое правило, создаваемое `builder.py`, допускает также `INSUFFICIENT_CONTEXT` или `UNSUPPORTED_QUERY` целиком, без SQL или пояснения после кода. Сам язык SELECT не меняется. [Агент](../../agent/README.md) обрабатывает эти ответы до проверки и выполнения; по умолчанию режим отказа выключен.

## Как расширять грамматику

При добавлении конструкции нужно сохранить разделение скалярных выражений и выражений с агрегатами, согласовать [правила AST](../validation.py) и [инструкции модели](../../llm/prompts.py). Требуются примеры допустимых запросов и близких к ним запросов, которые должны отклоняться.

Например, поддержка новой функции должна определить число и виды аргументов, допустимость агрегатов внутри и места использования результата. Затем нужно проверить её сочетание с существующими операциями и скобками. Расширение одного списка имён не задаёт этих правил и может разрешить конструкцию, которую остальная система не умеет проверять.

Грамматика проверяется целиком: неиспользуемое правило само по себе не означает поддержку конструкции. [test_sql_grammar.py](../../../tests/test_sql_grammar.py) проверяет язык, экранирование, оба режима отказа и, при доступной нативной библиотеке, компиляцию GBNF. Ни грамматика, ни валидатор не доказывают правильность бизнес-метрики — для неё нужны контрольные вопросы с известными результатами.

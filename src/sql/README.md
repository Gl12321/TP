# Проверка запроса до выполнения

Модель может предложить SQL, который выглядит правдоподобно, но использует чужую таблицу, неверную колонку или неподдерживаемую операцию. Этот модуль ограничивает возможную генерацию и отдельно проверяет полученный запрос перед передачей в базу.

Здесь решается, допустима ли структура запроса. Соответствие бизнес-смыслу вопроса требует контрольных примеров, а реальные значения результата получает [исполнитель PostgreSQL](../database/executor.py).

## Два уровня проверки

[Грамматика](grammar/README.md) задаёт допустимые продолжения текста во время генерации: SELECT, поддерживаемые выражения и имена из выбранного контекста. [grammar/builder.py](grammar/builder.py) собирает её для текущих таблиц и назначает те же псевдонимы, которые используются в [промпте](../llm/prompts.py).

[validation.py](validation.py) разбирает готовый SQL в дерево выражений через SQLGlot. Эта проверка видит связи между частями запроса: например, объявлена ли таблица до использования её колонки в JOIN и согласованы ли выбранные поля с группировкой. В БД передаётся возвращённый валидатором нормализованный SQL; исходная строка не выполняется.

[results.py](results.py) подготавливает табличный результат к передаче: сохраняет представление значений и ограничивает размер ответа. Общие формы результата и ошибки определены в [domain](../domain/README.md).

Например, имя колонки может входить в каталог, но её таблица не участвовать в конкретном FROM. Для грамматики это допустимое имя из контекста; для запроса целиком — ошибка области видимости. Аналогично выражение `SUM(amount)` разрешено само по себе, но недопустимо в WHERE. Именно такие различия требуют проверки дерева, а не только поиска запрещённых слов в строке.

Генератор и валидатор поэтому не дублируют друг друга. Первый уменьшает пространство возможных ответов ещё во время генерации, второй принимает решение о конкретном готовом запросе. Даже при изменении модели правило обязательной проверки перед исполнением сохраняется.

## Поддерживаемые правила

- Ровно один `SELECT` с источниками вида `schema.table`; только таблицы и колонки текущего контекста. Системные схемы и имена других баз запрещены.
- Функции и узлы AST проверяются по разрешённому списку. Неизвестные конструкции, пользовательские функции, окна, CTE и подзапросы отклоняются.
- Имена колонок, уникальность псевдонимов и видимость таблиц проверяются для каждого `JOIN ON`.
- Агрегаты недопустимы в `WHERE`, `GROUP BY`, `JOIN ON` и внутри других агрегатов. Выражения SELECT/HAVING/ORDER должны соответствовать GROUP BY.
- `*` допустима в проекции и `COUNT(*)`. `IN` принимает список литералов.
- Выходной псевдоним допустим как отдельный элемент `ORDER BY`, но не внутри формулы и не в WHERE/HAVING. GROUP BY требует исходное выражение или позицию.
- Позиции GROUP/ORDER BY разворачиваются в выражения SELECT; при `SELECT *` позиции не поддерживаются. Приведения типов разрешены только для DATE/TIMESTAMP-литералов.
- Длина SQL, глубина дерева выражений и значения LIMIT/OFFSET ограничены.

Даже при группировке по первичному ключу остальные поля нужно указывать явно: валидатор не выводит функциональные зависимости. Полную спецификацию генерируемого языка содержит [README грамматики](grammar/README.md).

## Результат проверки и связь с агентом

`SQLGrammarBuilder.build(tables)` создаёт грамматику, а `SQLValidator().validate(generated, tables)` возвращает нормализованный SQL. Пустой или некорректный каталог вызывает `ValueError` при сборке грамматики. Недопустимый SQL вызывает `QueryError` с кодом `invalid_sql` и признаком возможности исправления.

Отсутствующая в контексте таблица или колонка получает код `missing_context`: [агент](../agent/README.md) может один раз уточнить поиск. Отсутствие SQLGlot — ошибка конфигурации `missing_dependency`, которая не запускает повторную генерацию.

Для генерации агент использует `build(tables, allow_refusal=True)`. Кроме SELECT, эта грамматика допускает самостоятельные ответы `INSUFFICIENT_CONTEXT` и `UNSUPPORTED_QUERY`. Агент обрабатывает их до валидатора. По умолчанию `allow_refusal=False`, и допускается только SQL.

Грамматика и AST не доказывают корректность типов, понимания вопроса или бизнес-метрики. PostgreSQL проверяет типы и выполнимость. [База данных](../database/README.md) дополнительно ограничивает права, режим транзакции, время и объём выдачи.

Допустимый запрос всё ещё может считать другую метрику: например, сумму заказов вместо суммы оплаченных заказов. Чтобы обнаруживать такие случаи, нужны данные с различающимися ожидаемыми результатами и проверочные вопросы. Добавлять всё больше синтаксических ограничений вместо предметной проверки качества недостаточно.

## Расширение языка

Новую возможность нужно согласованно добавить в грамматику, правила AST, инструкции модели и проверки принятия и отклонения запросов. Включить имя узла в `_ALLOWED_NODES` недостаточно: необходимо определить допустимые аргументы и области видимости.

Набор проверок запускается командой `python -m unittest discover -s tests -p "test_sql_*.py"` из корня проекта. Проверки AST требуют SQLGlot. Для языка используется [распознаватель GBNF](../../tests/gbnf_support.py); при наличии локальной Windows-библиотеки `.tools/llama-*/llama.dll` дополнительно вызывается настоящий компилятор без загрузки модели. Условия пропусков описаны в [tests](../../tests/README.md).

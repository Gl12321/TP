# Настройки и управление ресурсами

Приложению нужны общие правила: где находятся данные, сколько памяти оставить системе, как долго ждать ответ и когда можно освободить занятый ресурс. Этот каталог передаёт такие настройки компонентам и содержит операции, которые используются в нескольких модулях.

## Что здесь происходит

[config.py](config.py) собирает настройки при явном вызове `get_settings()`. Общие параметры находятся в [config.yaml](../../config.yaml); порядок запуска и выбор модели описаны в [корневом руководстве](../../README_RU.md). Сам импорт модуля не запускает модели и не открывает соединения с БД.

[presets.py](presets.py) читает каталог моделей и разрешает выбранный профиль в конкретные файлы и параметры. Его используют и подготовка запуска, и рабочее приложение. Благодаря этому имя модели означает один и тот же набор весов на этапе скачивания и на этапе загрузки в память.

Подключение для импорта и подключение для чтения различаются. Генератор SQL не получает административную роль как запасной вариант. При формировании URL имена и пароли экранируются, поэтому специальные символы не меняют адрес подключения.

[concurrency.py](concurrency.py) позволяет дождаться завершения фоновой операции при отмене асинхронной задачи. Это нужно, например, когда модель уже вычисляет очередной блок: отмена ожидания Python ещё не означает, что нативный код прекратил использовать память. Блокировка и ресурс освобождаются после фактического завершения работы, в том числе при повторной отмене.

[logging.py](logging.py) настраивает технические логи процесса. Они нужны для диагностики сбоев; сообщения о ходе конкретного вопроса передаются отдельно через [QueryContext](../domain/query.py).

## Как применяются настройки

YAML задаёт общую конфигурацию, которую можно читать и изменять в одном месте. Явные параметры создания `Settings`, окружение, `.env` и файловые секреты имеют приоритет над YAML. Это позволяет использовать один набор обычных параметров, передавая данные подключения отдельно от каталога моделей.

Например, увеличение длины контекста LLM относится к профилю модели, а ограничение размера возвращаемой таблицы — к исполнению запросов. Оба значения читаются централизованно, но применяются разными компонентами. Общий файл настроек не превращает `core` в модуль, который сам генерирует SQL или обрезает строки результата.

Настройки кэшируются в процессе. Изменение YAML предназначено для следующего запуска приложения; оно не заменяет уже загруженную модель посреди вопроса. Ошибка в имени профиля должна обнаруживаться при подготовке, до начала пользовательской работы.

[memory.py](memory.py) оценивает память, доступную текущему процессу. В Docker свободная RAM компьютера может быть больше разрешённой контейнеру, поэтому учитывается также остаток лимита cgroup v1/v2 на стандартном `/sys/fs/cgroup`. Эта проверка помогает отказаться от загрузки слишком большой модели до исчерпания RAM. Она отражает текущее состояние; пиковое потребление во время генерации и нестандартные точки монтирования cgroup требуют отдельной проверки.

Ограничения защищают разные ресурсы и не заменяют друг друга. Таймаут SQL ограничивает время запроса в PostgreSQL, предел строк — объём накопленного ответа, а резерв RAM — условие работы модели. Увеличение одного лимита не означает, что остальные автоматически стали подходящими.

## Связь с модулями

[API](../api/dependencies.py) читает настройки и собирает компоненты. [LLM](../llm/README.md), [RAG](../rag/README.md) и [база данных](../database/README.md) применяют переданные им ограничения в местах, где выполняется работа. `core` не создаёт эти компоненты и не управляет сценарием вопроса.

При добавлении общей функции её стоит оставлять здесь только тогда, когда она действительно нужна нескольким слоям. Правило исправления аналитического запроса принадлежит агенту; правило ожидания уже запущенного рабочего потока применимо и к модели, и к импорту, поэтому подходит для `concurrency.py`.

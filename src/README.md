# От вопроса к таблице

Пользователь описывает нужный результат обычными словами: например, «покажи продажи по месяцам за этот год». Этот код находит подходящие данные, составляет запрос к базе и возвращает строки с рассчитанными значениями. Пользователю не нужно заранее знать названия таблиц и писать SQL.

Обработка разделена на этапы, потому что поиск данных, понимание вопроса и выполнение запроса требуют разных инструментов. Языковая модель предлагает SQL; решение о том, можно ли его выполнить, принимают отдельные проверки и сама база данных.

## Один вопрос целиком

Допустим, в загруженной базе есть заказы, товары, покупатели и служебные таблицы. Пользователь спрашивает: «Какие пять товаров принесли больше всего выручки за март?» Поиск выбирает заказы и товары, добавляет таблицу позиций заказа, если через неё проходит связь, и передаёт генератору их структуру.

Модель должна определить, какую сумму считать, как соединить таблицы и каким периодом ограничить строки. Полученный SQL проходит проверку, затем PostgreSQL рассчитывает результат. Интерфейс получает названия товаров и рассчитанные суммы, а рядом показывает запрос, чтобы вычисление можно было проверить.

Если нужных колонок или однозначного определения выручки нет, таблица не подменяется догадкой модели: предусмотрен исход с отказом. Если запрос верен, но подходящих строк нет, это отдельный успешный исход с пустой выборкой. Для пользовательского сценария эти различия важнее, чем название библиотеки, выполняющей очередной этап.

## Как связаны модули

| Этап | Модуль | Зачем он нужен |
| --- | --- | --- |
| Принять вопрос и показать ход работы | [api](api/README.md) | Соединяет интерфейс с приложением и передаёт результат |
| Найти данные для ответа | [rag](rag/README.md) | Выбирает таблицы по смыслу вопроса и добавляет связи между ними |
| Построить запрос | [llm](llm/README.md) | Передаёт модели вопрос и структуру выбранных таблиц |
| Проверить запрос | [sql](sql/README.md) | Ограничивает язык генерации и проверяет обращения к данным |
| Получить настоящие строки | [database](database/README.md) | Импортирует SQLite, читает структуру PostgreSQL и выполняет SQL |
| Связать этапы в один сценарий | [agent](agent/README.md) | Управляет попытками, исправлениями и завершением вопроса |

[domain](domain/README.md) задаёт общие понятия: таблицу, колонку, результат и ошибку. [core](core/README.md) содержит настройки и общие операции управления ресурсами. Эти модули позволяют менять реализацию отдельного этапа без передачи HTTP, объектов модели или соединений с БД через всё приложение.

Компоненты собираются в [api/dependencies.py](api/dependencies.py). Жизненный цикл API создаёт один комплект моделей и соединений, затем закрывает их при остановке. Вызов агента получает отдельное состояние, поэтому выбранные схемы, ошибки и отмена относятся только к текущему вопросу.

Подготовка данных проходит отдельно от ответа на вопрос. При импорте приложение переносит строки в PostgreSQL и обновляет индекс описаний таблиц. При вопросе используются готовая база и готовый индекс; генератор получает структуру подходящих таблиц, а не копию всей базы в тексте промпта.

Такое разделение позволяет независимо улучшать качество поиска, инструкции модели и проверку запросов. Например, новый способ ранжирования таблиц не должен менять HTTP-протокол, а изменение оформления результата не должно затрагивать транзакции PostgreSQL.

## Где менять поведение

Новая аналитическая возможность обычно затрагивает [грамматику](sql/grammar/README.md), [проверку SQL](sql/validation.py), [инструкции модели](llm/prompts.py) и соответствующие [тесты](../tests/README.md). Все четыре части должны согласованно понимать новую конструкцию.

Замена модели относится к конфигурации и LLM-компоненту. Новому источнику данных нужны чтение метаданных и выполнение запросов с общими типами `domain`. Логика исправления вопроса при этом остаётся в агенте.

Настройки находятся в [config.yaml](../config.yaml), запуск описан в [корневом руководстве](../README_RU.md). Пояснения к реализации хранятся в README рядом с кодом.

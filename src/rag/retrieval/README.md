# От вопроса к набору таблиц

Модели нужно передать достаточно структуры для ответа, сохранив ограниченный размер контекста. Этот модуль выбирает таблицы по смыслу вопроса и восстанавливает связи между ними. Так, для суммы заказов по категориям между заказами и категориями может понадобиться промежуточная таблица товаров.

## Как выбираются данные

[retriever.py](retriever.py) получает вектор вопроса и ищет близкие описания в [каталоге](../indexing/README.md). Фильтр по разрешённым схемам относится к текущему вызову; выбор одного пользователя не изменяет общий объект поиска.

[reranker.py](reranker.py) повторно оценивает каждую пару «вопрос, описание таблицы», отбрасывает кандидатов ниже порога и сортирует остальных по оценке. При одинаковой оценке порядок определяется схемой и именем таблицы, чтобы результат не зависел от случайного порядка индекса.

[context.py](context.py) сверяет выбранные документы с актуальной структурой PostgreSQL. Затем `ContextBuilder` добавляет кратчайшие пути по внешним ключам между выбранными таблицами. Направление внешнего ключа не ограничивает поиск пути, а составные ключи сохраняются полностью.

Например, поиск вернул `orders` и `products`, а связывает их только `order_items`. Включение этой промежуточной таблицы даёт модели поля `order_id` и `product_id`, по которым возможен JOIN. Без неё модель видела бы два подходящих по смыслу источника, но не знала бы корректного способа соединить строки.

Пути выбираются детерминированно по текущим метаданным. Поиск связи не выходит за выбранные пользователем схемы, даже если во всей БД существует подходящая цепочка через другую схему. Это сохраняет границу выбранных данных на этапе подготовки контекста, до генерации SQL.

## Что получает генератор

Результат — список [TableSchema](../../domain/schema.py) с колонками и связями только из разрешённых схем. Таблица добавляется вместе со всем необходимым путём. Если набор превышает ограничение числа таблиц, возвращается `context_too_large`; часть найденных данных не отбрасывается молча.

[LLM-компонент](../../llm/README.md) дополнительно проверяет число токенов в готовом диалоге. При переполнении нужно сузить вопрос или выбор схем: обрезание описания посреди колонки или удаление связующей таблицы может изменить смысл будущего SQL.

Наличие внешнего ключа помогает построить соединение, но не доказывает, что выбран правильный смысл запроса. Например, соединение нескольких таблиц может размножить строки и завысить сумму. [Промпт](../../llm/prompts.py) объясняет модели это ограничение, [SQL-проверка](../../sql/README.md) проверяет структуру запроса, а качество выбора данных оценивается контрольными вопросами.

Проверка свежести нужна независимо от того, насколько подходящим оказался результат поиска. Описание может быть очень близким к вопросу, но относиться к старой версии таблицы. В таком случае возвращается ошибка актуальности индекса, а не попытка использовать похожие имена из новой структуры.

Порог reranker и ограничения поиска задаются конфигурацией. Подходящий порог зависит от модели и предметных данных; его значение не является универсальной оценкой достоверности ответа.

# Поиск данных для вопроса

В базе может быть много таблиц, а для конкретного вопроса нужны лишь несколько. Этот модуль находит их по смыслу вопроса и подготавливает описание структуры для модели. Например, вопрос о продажах по городам может потребовать таблицы заказов, покупателей и адресов, даже если пользователь не знает их названий.

Поиск работает с описаниями таблиц и колонок. Значения готового ответа затем вычисляет PostgreSQL: поисковый индекс не заменяет базу данных.

## Два этапа

[Индексация](indexing/README.md) заранее сохраняет структуру таблиц и числовые представления их описаний. [embedder.py](embedder.py) превращает текст в вектор; близость векторов помогает найти таблицы, связанные с вопросом по смыслу.

[Поиск](retrieval/README.md) получает кандидатов из индекса, повторно оценивает их соответствие вопросу и добавляет таблицы, нужные для связей. Итоговый контекст содержит проверенную структуру выбранных данных; [генератор](../llm/README.md) использует её для построения SQL.

Embedder общий для каталога и поиска: вопрос и описания должны сравниваться в одном пространстве. Reranker — отдельная модель, которая оценивает пары «вопрос, описание» точнее первоначального векторного поиска. Модели и параметры выбираются через [общую конфигурацию](../../config.yaml).

## Пример выбора контекста

Пользователь спрашивает, в каких городах выросла сумма заказов. Вопрос может не содержать ни одного точного имени из схемы: в ней могут быть таблицы `orders`, `customers` и `addresses`. Поиск по смыслу позволяет предложить эти таблицы даже без буквального совпадения слов.

Однако просто вернуть три похожих описания недостаточно. Для соединения заказов с городом может потребоваться конкретная цепочка внешних ключей. Поэтому после ранжирования отдельный построитель контекста сверяет структуру с БД и добавляет недостающие связующие таблицы. Генератор получает связный набор описаний, а не только первые результаты поисковой выдачи.

Сначала выполняется сравнительно широкий поиск кандидатов, затем более дорогая оценка подходящих пар. Такое разделение позволяет ограничить число обращений к reranker. Оно также делает причины ошибки понятнее: таблица могла не попасть в кандидаты, оказаться ниже порога ранжирования или не поместиться вместе со связями в контекст.

## Ресурсы и связи

[API](../api/dependencies.py) создаёт модели один раз при запуске и передаёт их компонентам. Подготовка файлов моделей относится к [общему запуску](../../README_RU.md); внутри обработки вопроса используется только локальная копия. [_runtime.py](_runtime.py) разрешает путь к ней и управляет ожиданием фоновой работы.

Тексты обрабатываются ограниченными пакетами. Длинные описания обрезаются токенизатором поиска, поэтому качество на широких таблицах нужно проверять предметными примерами. Итоговый контекст отдельно проверяется токенизатором LLM.

Вызовы каждого экземпляра модели последовательны. Отмена прекращает обработку между пакетами; уже запущенный нативный пакет завершается до освобождения ресурса. Метаданные передаются через [типы domain](../domain/schema.py). Поведение без загрузки моделей проверяет [test_rag.py](../../tests/test_rag.py).

При улучшении поиска полезно проверять не только окончательный SQL, но и список выбранных таблиц. Если нужная таблица отсутствует в контексте, более крупная языковая модель не получает её структуру и не исправляет первопричину автоматически. Для предметной базы важны понятные описания, корректные связи и контрольные вопросы, на которых видно, где именно теряется нужная информация.

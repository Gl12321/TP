# Каталог таблиц для поиска

Чтобы по вопросу «какие товары продаются лучше» найти нужные таблицы, приложению требуется поисковое описание базы. Каталог сохраняет названия, колонки, связи и описания вместе с их векторами. Благодаря этому поиск не перечитывает и не кодирует всю структуру при каждом вопросе.

Индекс представляет определённую версию структуры PostgreSQL. Если таблицы поменялись, прежнее описание нельзя использовать как достоверное: модель могла бы получить уже несуществующую колонку или пропустить новую связь.

## Создание и обновление

[catalog.py](catalog.py) содержит `SchemaCataloger`. Он получает [читатель метаданных](../../database/metadata.py), общий [embedder](../embedder.py) и путь к Chroma. `index_schema(name)` отмечает схему как неактуальную, читает структуру PostgreSQL, удаляет прежние документы этой схемы и записывает новые пакетами. Отметка снимается только после полного успеха; пустая схема также очищает старые документы.

[serializer.py](serializer.py) сохраняет в JSON колонки, типы, первичные и внешние ключи, DDL и описания. Идентификатор документа — пара `[schema, table]`, поэтому точки и запятые в именах не создают коллизий. Документы старого формата отклоняются с `index_outdated` и требуют перестроения.

Например, после нового импорта колонка `price` могла смениться на `unit_price`, а часть таблиц исчезнуть. Обновление схемы не дописывает новые документы поверх старых: прежний набор удаляется, затем записывается актуальный. Иначе поиск мог бы продолжать находить удалённые поля, а модель получала бы противоречивое описание базы.

Полная структура сохраняется рядом с вектором, потому что близости текстов недостаточно для построения SQL. После поиска нужны исходные имена, типы и составные ключи. Сериализация позволяет восстановить их без разгадывания текста, который использовался для получения эмбеддинга.

## Что происходит при сбое

До замены или удаления схемы [API](../../api/routes/schemas.py) вызывает `mark_dirty(name)`. Состояние сохраняется атомарной заменой JSON-файла рядом с Chroma. Незавершённый импорт или обновление индекса оставляет схему заблокированной для поиска даже после перезапуска; успешная переиндексация снимает ограничение.

`reset_store()` очищает документы, сохраняя объект коллекции. Прерванная очистка блокирует поиск во всех схемах до повторного успешного сброса. И поиск `query()`, и чтение `read_tables()` проверяют актуальность состояния.

Отметка неактуальности записывается до опасной операции, а снимается после последнего успешного шага. Если процесс завершится между этими моментами, следующий запуск увидит незавершённую работу. Если бы признак ошибки хранился только в памяти, перезапуск выглядел бы как восстановление, хотя документы на диске остались бы неполными.

## Связь с базой и поиском

У PostgreSQL и Chroma нет общей транзакции. Отметки неактуальности позволяют [поиску](../retrieval/README.md) обнаружить незавершённое обновление вместо работы с половиной нового каталога. Каталог рассчитан на один процесс API, который изменяет индекс.

Изменения БД вне приложения автоматически не отмечаются. Построитель контекста дополнительно сравнивает найденные таблицы со свежими метаданными, но после внешнего изменения схем всё равно требуется переиндексация. Файлы состояния описаны в [data](../../../data/README.md); удаление такого файла вручную не заменяет восстановление индекса.

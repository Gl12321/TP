# Сценарий ответа на вопрос

Агент превращает вопрос пользователя в готовую таблицу: выбирает нужные данные, просит модель составить запрос, проверяет его и получает результат из БД. Если запрос содержит исправимую ошибку, агент передаёт модели причину и даёт ограниченное число попыток исправиться.

## Как принимаются решения

[graph.py](graph.py) соединяет этапы в граф. Сначала поиск предлагает подходящие таблицы, затем построитель контекста добавляет нужные связи. Генератор получает вопрос вместе с этой структурой, а его ответ проходит проверку SQL и выполнение. Итогом становится таблица, пустая выборка или понятная причина, почему ответ не получен.

[state.py](state.py) хранит данные текущего вопроса: контекст, попытки и последнюю ошибку. [correction.py](correction.py) решает, возможна ли ещё одна попытка. При трёх разрешённых исправлениях допускается исходная генерация и ещё три генерации после ошибок. Если модель повторяет уже неудачный SQL при том же контексте, цикл останавливается.

Ошибка недостающей таблицы или колонки допускает одно уточнение поиска. Контекст и грамматика обновляются вместе. Если структура изменилась, прежний SQL можно проверить заново: причина его предыдущей неудачи могла исчезнуть. Потеря соединения, нехватка памяти, таймаут и отмена не исправляются повторным обращением к модели.

Если необходимых данных нет или вопрос невозможно выразить поддерживаемым языком, генератор может вернуть `INSUFFICIENT_CONTEXT` или `UNSUPPORTED_QUERY`. Агент завершает вопрос со статусом `not_found`; такой ответ не передаётся исполнителю SQL.

## Пример исправления

Пользователь просит сумму заказов по месяцам. Модель выбирает нужные таблицы, но составляет выражение даты, которое PostgreSQL не может применить к типу колонки. Исполнитель возвращает причину ошибки, и агент формирует следующую попытку с исходным вопросом, прежним SQL и этим объяснением. Модель получает конкретную задачу исправить запрос, а не повторяет исходную генерацию без обратной связи.

Другой случай — в запросе появилась колонка, отсутствующая в переданном контексте. Агент один раз уточняет поиск, затем заново формирует контекст и грамматику. Если данных всё равно недостаточно, ограничение попыток не позволяет бесконечно перебирать варианты.

Если же PostgreSQL недоступен, новый текст SQL не восстановит соединение. Поэтому информация о возможности исправления передаётся вместе с ошибкой, а политика повторов не пытается угадывать её по тексту сообщения. Пустой результат также не считается поводом заставить модель искать другой ответ: подходящих строк действительно может не быть.

## Границы ответственности

Агент получает [поиск](../rag/retrieval/README.md), [генератор](../llm/README.md), [проверку SQL](../sql/README.md) и [исполнитель](../database/executor.py) через конструктор. Он управляет порядком работы, не создавая модели и подключения внутри этапов.

Перед генерацией размер всего диалога проверяется токенизатором модели с резервом на ответ. Если контекст слишком велик, пользователю предлагается сузить вопрос; необходимые связующие таблицы не удаляются молча ради продолжения.

Ход работы и отмена передаются через [QueryContext](../domain/query.py). [API](../api/README.md) доставляет эти события интерфейсу. Проверки отдельных решений находятся в [test_agent.py](../../tests/test_agent.py), переходов настоящего графа — в [test_graph_flow.py](../../tests/test_graph_flow.py).

При изменении сценария важно сохранять понятный конечный исход для каждого пути: результат, отказ, ошибка или отмена. Добавление нового этапа не должно оставлять пользователя с бесконечным индикатором работы. Поэтому тесты проверяют не только отдельные функции, но и переходы до завершения настоящего графа.

# Модели для понимания вопроса и структуры

Приложение использует три модели с разными задачами. Одна находит похожие по смыслу описания таблиц, другая уточняет их порядок, а языковая модель составляет SQL. Разделение позволяет отправлять генератору только нужную часть структуры базы.

## Какие файлы нужны

| Модель | Роль | Формат локальных файлов |
| --- | --- | --- |
| LLM | Превратить вопрос и описание таблиц в SQL | GGUF с собственным шаблоном диалога |
| Embedder | Сравнить вопрос с описаниями таблиц по смыслу | Локальный каталог модели или заполненный кеш Hugging Face |
| Reranker | Повторно оценить найденные таблицы для вопроса | Локальный каталог модели или заполненный кеш Hugging Face |

Доступные варианты и параметры задаются в [config.yaml](../config.yaml). Модель выбирается флагом общего запуска; команды просмотра вариантов и запуска приведены в [корневом руководстве](../README_RU.md). Подготовка проверяет локальные файлы и получает недостающие до готовности приложения. Во время обработки вопроса [LLM](../src/llm/README.md) и [RAG](../src/rag/README.md) работают с локальными копиями.

## Первый и повторный запуск

[Подготовка моделей](../src/runtime/models.py) отделена от запуска API. Например, при выборе другой LLM может отсутствовать только её GGUF, тогда как embedder и reranker уже готовы. Веса поиска не нужно загружать заново только потому, что изменился генератор SQL.

Для GGUF проверяются ожидаемый размер, заголовок формата и SHA-256 из каталога. Подходящий файл, который уже находится на диске, можно использовать без повторной загрузки. Отметка готовности создаётся только после проверки; одинаковое имя файла само по себе не доказывает, что скачана нужная версия.

Для моделей поиска каталог задаёт версию репозитория, требуемые файлы и их контрольные суммы: SHA-256 для весов в Git LFS, Git blob SHA-1 для остальных файлов. Проверяется содержимое каждого файла. Подходящие локальные файлы используются и без интернета, даже если отметка готовности ещё не создана; повреждённые или недостающие скачиваются отдельно.

После проверки сохраняется manifest с размерами и временем изменения файлов. При последующих запусках он позволяет пропустить повторное чтение всех весов, обнаружить исчезнувший или изменившийся файл и повторить проверку содержимого. Загрузкой и продолжением передачи занимается Hugging Face Hub.

Такой порядок не позволяет рабочему API начать обработку вопроса в момент, когда часть весов ещё не получена. Ошибка подготовки останавливает запуск до загрузки моделей в приложение; повторный запуск использует сохранённые файлы.

## Замена модели

Для LLM нужны поддержка архитектуры движком, подходящий `tokenizer.chat_template` и достаточный объём памяти. Размер GGUF не равен полному расходу RAM: дополнительно используются контекст генерации, рабочие буферы и остальные компоненты приложения. Квантование уменьшает размер весов, но настройки контекста всё равно влияют на потребление памяти.

Сам формат GGUF описывает хранение модели для движка, но не определяет её качество. Размер и способ квантования относятся к конкретному набору весов; инструкции и шаблон диалога определяют, как его использовать. Поэтому новый профиль включает и источник файла, и параметры генерации, а не только удобное имя для команды.

При добавлении нового варианта сначала нужны проверяемый источник, версия и контрольная сумма, затем проверка совместимости движка и шаблона, а после — предметные вопросы и замер ресурсов. То, что файл загрузился, не доказывает ни правильность SQL, ни устойчивую работу в заданном объёме памяти.

Смена embedder требует перестроить [поисковый индекс](../src/rag/indexing/README.md): векторы разных моделей нельзя сравнивать как один набор. Смена только LLM не меняет эти векторы. Незавершённая загрузка, например файл `.part`, не является готовой моделью.

# Модели: от вопроса к таблице

Модели нужны для свободного вопроса к базе: одна составляет SQL, две небольшие помогают найти подходящие таблицы. Они не управляют пользователями, не принимают решения за руководителя и не генерируют комментарии сотрудников. Обзор сети, планы, карточки точек и обсуждения работают по обычной бизнес-логике приложения.

Пользователь выбирает основную модель при запуске. В worker загружается один профиль; на диске можно хранить несколько и переключать их между запусками. Подготовленные файлы переиспользуются. Все основные профили в проекте относятся к **Qwen3.5**.

## Как устроен набор

| Компонент | Модель | Задача |
| --- | --- | --- |
| Генератор | Выбранный профиль Qwen3.5 | Перевести вопрос и разрешённый контекст в один SELECT либо код уточнения |
| Embedder | `intfloat/multilingual-e5-small` | Сравнить смысл вопроса с описаниями таблиц |
| Reranker | `cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` | Повторно оценить найденные таблицы и упорядочить кандидатов |

E5 использует префиксы `query: ` для вопроса и `passage: ` для документа, нормализованные векторы размерности 384. Reranker возвращает оценку релевантности пары текстов. Это оценка для сортировки, а не вероятность правильности итогового расчёта.

После поиска библиотека добавляет необходимые связи и проверяет бюджет контекста. Основная модель получает только разрешённые метаданные, условия и определения показателей. Строки готового результата не отправляются другой модели для написания ответа.

## Три профиля основной модели

| Флаг `--model` | Квантование | Размер файла | Назначение |
| --- | --- | ---: | --- |
| `qwen3.5-4b` | Q5_K_M | 2,93 ГиБ | Самый лёгкий из предусмотренных профилей |
| `qwen3.5-9b` | Q5_K_M | 6,13 ГиБ | Профиль проекта по умолчанию |
| `qwen3.5-27b` | Q3_K_M | 12,58 ГиБ | Более тяжёлый профиль для задач, оправдывающих его расход ресурсов |

Это размер GGUF на диске, а не полный расход оперативной памяти. Дополнительно нужны рабочие буферы генератора, состояние контекста, encoder, reranker, Python, PostgreSQL, браузер и ОС. На компьютере с 24 ГБ RAM размер файла 27B сам по себе не гарантирует устойчивую работу. При выборе профиля нужно учитывать доступную память и задержку полного запроса.

GGUF — формат весов для выбранного движка llama.cpp. Квантование уменьшает размер и может влиять на качество. Файл также содержит токенизатор и шаблон диалога, от которых зависит корректная подача промпта. Замена на файл другого формата требует другого адаптера генерации, а не только переименования пути.

Штатная конфигурация использует CPU, контекст 4096 токенов и не более 512 токенов ответа. Увеличение контекста и количества одновременно загруженных worker повышает расход памяти. Размер модели не отменяет ограничений SQL-языка и не гарантирует правильной финансовой формулы.

## Где находятся файлы и версии

[config.yaml](../config.yaml) содержит репозиторий модели, точный commit revision, имя файла, размер и SHA-256 основной модели. Для encoder и reranker закреплены revision и контрольные суммы каждого нужного файла. Это источник истины; не следует заменять revision на `main` в рабочем развёртывании.

Основные GGUF лежат непосредственно в `models/`, вспомогательные модели — в `models/embedder/` и `models/reranker/`. Рядом сохраняются файлы готовности после проверки. Веса и служебные manifest исключены из Git; этот README остаётся в репозитории.

[Подготовка моделей](../runtime/models.py) проверяет заголовок, размер и SHA-256 GGUF, а у моделей поиска — закреплённые файлы. Manifest позволяет повторно использовать неизменившиеся файлы без нового скачивания. При отсутствии или изменении файла выполняется подготовка и проверка. Вопрос пользователя не запускает загрузку весов: worker открывает модели локально, в offline-режиме.

## Выбор и запуск

Из корня настроенного проекта:

```text
python run.py --list-models
python run.py --model qwen3.5-4b
python run.py --model qwen3.5-9b
python run.py --model qwen3.5-27b
```

Нужно выполнить одну команду запуска с нужным профилем. `--list-models` только показывает каталог. По умолчанию используется профиль из YAML. `python run.py --without-ai` запускает приложение без подготовки и загрузки моделей; новые SQL-ответы тогда недоступны. Требования запуска и состав процессов — в [руководстве эксплуатации](../docs/operations/README.md).

Библиотека не скачивает альтернативную модель при ошибке и не меняет профиль незаметно. При недостатке ресурсов следует остановить worker и выбрать меньший профиль. Проверка памяти внутри адаптера — предохранитель; она не резервирует память у ОС.

## Изменение моделей

Для нового профиля нужны совместимость архитектуры и шаблона с установленным llama.cpp, фиксированные файлы и контрольные суммы, контрольные вопросы с ожидаемыми результатами PostgreSQL и измерение полной нагрузки. Особенно важны числовые агрегаты, кратность JOIN, календарные периоды, русский язык, отмена и повторный запрос.

При смене embedder его идентичность и параметры должны менять fingerprint индекса, чтобы старые векторы не смешались с новыми. При смене reranker нужно проверить формат выхода: текущий адаптер ожидает один logit на пару.

Техническая интеграция описана в [адаптерах](../packages/sql_agent/src/sql_agent/adapters/README.md) и [руководстве разработчика агента](../docs/development/sql-agent.md). Настройки ресурсов и контейнеров — в [конфигурации](../docs/operations/configuration.md) и [Docker](../docs/operations/docker.md).

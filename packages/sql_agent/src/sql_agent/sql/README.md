# Проверка аналитического SQL

Этот модуль отвечает за то, чтобы результат генерации был одним разрешённым SELECT, обращался к известным источникам и не расширял список доступных полей. Это граница между текстом модели и запросом, который можно передать исполнителю приложения.

## Как устроена проверка

[grammar](grammar/README.md) ограничивает форму и имена ещё во время генерации. [validation.py](validation.py) затем разбирает AST через sqlglot: проверяет операции, источники, область видимости JOIN, агрегаты, группировки, функции и лимиты.

`SELECT *` и `tN.*` раскрываются в явный список колонок из переданного каталога. Поэтому добавленное в исходной БД скрытое поле не попадёт в выдачу из-за звёздочки. Нормализованный SQL возвращается вызывающему коду; сама библиотека не открывает соединение с БД.

[results.py](results.py) переводит значения результата в JSON: Decimal остаётся строкой с исходной точностью, даты — ISO-строкой, двоичные данные — объектом с Base64. Нефинитные float не передаются как недопустимые JSON-числа. `encode_event` дополнительно ограничивает размер сериализованного сообщения.

## Что остаётся исполнителю

Исполнитель через `ReadOnlyExecutor` проверяет актуальные права, внедряет обязательное ограничение строк, работает отдельной ролью чтения и в транзакции `READ ONLY`, задаёт таймауты и ограничивает размер результата. В SaaS это [ScopedExecutor](../../../../../backend/app/sources/service.py).

AST не доказывает правильность финансового показателя и не заменяет права PostgreSQL. Корректность кратности JOIN, формулы и периода проверяется сравнением настоящего результата с эталоном.

## Изменение языка

Новая конструкция должна одновременно поддерживаться грамматикой, AST, промптом и исполнителем. Положительные примеры подтверждают нужное поведение, отрицательные — сохранение границ. Подробный порядок расширения описан в [руководстве разработчика](../../../../../docs/development/sql-agent.md).

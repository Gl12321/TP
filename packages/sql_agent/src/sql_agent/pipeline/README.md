# Обработка аналитического вопроса

Конвейер связывает вопрос, поиск нужных таблиц, генерацию и настоящее выполнение SQL. Его задача — довести один запрос до понятного исхода: таблицы, уточнения, отказа, отмены или ошибки. Повторная попытка не должна незаметно менять первоначальную аналитическую цель.

## Как устроен цикл

[agent.py](agent.py) получает каталог через `AllowedCatalog`, выбирает контекст, формирует сообщения и GBNF, вызывает генератор, проверяет AST и передаёт SQL исполнителю. Перед выполнением он заново получает снимок каталога. Изменение доступа или структуры источника прекращает расчёт.

Поиск учитывает вопрос, выбранные условия и основание продолжения. Таблицы явно выбранного показателя `filters.metric_key` и предыдущего успешного расчёта закрепляются в контексте. Недоступное основание отклоняется; обязательные таблицы нельзя выбросить ради размера промпта.

[correction.py](correction.py) определяет, можно ли исправлять ошибку и не повторяет ли модель тот же неудачный запрос. По умолчанию разрешены три исправления после первой генерации. По ошибке недостающего контекста поиск уточняется один раз. Новый набор контекста позволяет повторно оценить SQL, который раньше не подходил.

## Состояния и ограничения

Ответы модели `CLARIFY_PERIOD` и `CLARIFY_METRIC` возвращаются как уточнение, `INSUFFICIENT_CONTEXT` и `UNSUPPORTED_QUERY` — как отсутствие доступного ответа. Они не передаются в БД.

Все этапы подчиняются одному дедлайну. `QueryContext` передаёт сигнал отмены и события этапов вызывающему приложению. Счётчик `attempts` учитывает генерации, включая первую. Пустая таблица после корректного SELECT считается успехом.

Хранение заданий, аренда worker, доставка событий браузеру и публикация результатов находятся в бэкенде. Конвейер не повторяет задание после перезапуска процесса самостоятельно.

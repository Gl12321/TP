# Эксплуатация и проверка приложения

Эти команды проверяют собранное приложение через те же HTTP-операции, которыми пользуется браузер. Они дополняют модульные тесты: успешный импорт Python ещё не доказывает, что миграции, сессия, маршруты и статический фронтенд работают вместе.

[smoke.py](smoke.py) предназначен для нового изолированного развёртывания. Он создаёт первого владельца, точку, диалог и разбор, добавляет комментарий, проверяет отсутствие выдуманных итогов без источника и отзывает сессию выходом. На уже настроенной базе команда отказывается работать до внесения изменений.

```text
python run.py --without-ai
python tools/smoke.py
python run.py --stop
```

Сценарий используется в [Docker-проверке CI](../.github/workflows/verify.yml). Он не скачивает модель и не подтверждает качество генерации SQL. Тесты самого ядра находятся в [packages/sql_agent/tests](../packages/sql_agent/tests/README.md), API и изоляции — в `backend/tests`.

[backup.py](backup.py) сохраняет прикладную БД вместе с ключом подключений и настройками. Восстановление создаёт отдельную БД, проверяет архив, применяет миграции и завершает старые задачи через [bootstrap](../backend/app/bootstrap.py). Активные сессии в восстановленной копии отзываются. Старое окружение сохраняется до явного запуска с новым файлом секретов. Пошаговые команды — в [эксплуатации](../docs/OPERATIONS.md).

Обе команды используют стандартную библиотеку Python. Для резервирования обычной установки PostgreSQL CLI вызывается внутри контейнера БД. Параметр `--pg-bin` указывает каталог `pg_dump`, `pg_restore` и `psql` при проверке на локальном PostgreSQL без контейнеров. Версия этих утилит должна соответствовать серверу; на Windows имена `.exe` выбираются автоматически.

[acceptance.py](acceptance.py) проверяет полный путь с настоящей моделью: подключает тестовый PostgreSQL, задаёт показатель, сверяет готовый обзор, отправляет русский вопрос в очередь worker и сравнивает полученные суммы с эталоном. Затем сохраняет отчёт и обновляет его, проверяя неизменность исходного результата. В источнике есть скрытая третья точка и закрытый столбец; в ответ они не должны попасть.

Этот сценарий предназначен только для изолированного развёртывания на loopback-адресе. По умолчанию он требует новую БД приложения, создаёт первого владельца и тестовый источник в контейнере. В тестовом YAML адрес `db` должен быть разрешён в `application.source_hosts`. Для уже подготовленного локального стенда можно явно передать `--credentials`, `--source-manifest` и `--env-file`; эти файлы содержат секреты и хранятся вне Git. Ручной запуск workflow с `real_ai: true` выполняет сборку и этот сценарий на Linux; обычный push тяжёлые веса не скачивает.

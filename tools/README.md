# Инструменты проекта

В этой директории находятся независимые команды для трёх задач: показать продукт на подготовленных данных, проверить изменения автоматически и сохранить рабочие данные. Демонстрация сохраняет состояние между просмотрами. Проверки используют собственные данные и завершаются результатом выполнения. Резервирование работает с явно выбранной установкой.

## Назначение инструментов

| Команда | Задача | Требуемое окружение |
| --- | --- | --- |
| [check.py](check.py) | Запустить выбранную группу автоматических проверок | Зависит от режима: Python, Node, PostgreSQL или браузер |
| [demo](demo/README.md) | Показать готовую сеть или первичную настройку с обычным интерфейсом | Зависимости приложения, frontend/dist, отдельный PostgreSQL; без модели |
| [test-postgres.compose.yml](test-postgres.compose.yml) | Поднять локальный PostgreSQL для интеграционных проверок | Docker с Compose; собственный проект, том и порт 55433 |
| [smoke.py](smoke.py) | Быстро проверить собранный продукт без модели | Новое изолированное приложение с API и БД |
| [acceptance.py](acceptance.py) | Сверить вопрос к настоящей модели с контрольными числами | Изолированное приложение, готовый worker и тестовый PostgreSQL-источник |
| [backup.py](backup.py) | Создать архив прикладной БД или восстановить его в новую БД | Рабочий PostgreSQL, секреты и утилиты PostgreSQL |

`smoke.py`, `acceptance.py` и `backup.py` используют стандартную библиотеку Python. Их внешние компоненты уже должны работать; эти сценарии не запускают обычное рабочее приложение.

## Демонстрация продукта

Для новой машины сначала выполните [подготовку demo с нуля](../docs/demo/README.md#подготовка-demo-с-нуля). Здесь `python` означает интерпретатор с установленными зависимостями, а PostgreSQL должен уже работать; команда demo сама сервер не запускает.

```text
python -m tools.demo --check
python -m tools.demo
python -m tools.demo --scenario onboarding
```

Первый сценарий показывает сеть с шестью ролями и данными; второй — настройку нового пространства. По умолчанию они используют разные порты и каталоги состояния. Для первой подготовки нужен `RAZBOR_DEMO_DATABASE_URL` отдельного PostgreSQL, зависимости `requirements.txt` и готовый frontend. `--prepare-only` подготавливает состояние без HTTP-сервера, `--accounts` показывает учётные записи выбранного сценария.

Демонстрация не входит в `check.py` и не использует `RAZBOR_TEST_DATABASE_URL` или браузерные фикстуры. Данные, аккаунты, ограничения и порядок просмотра описаны в [руководстве demo](../docs/demo/README.md); устройство кода — в [tools/demo](demo/README.md).

## Проверки при разработке

```text
python tools/check.py quick
```

Режим объединяет компактные проверки Python, frontend и TypeScript без настоящего PostgreSQL, ML-библиотек и весов. Отдельные режимы `runtime`, `backend`, `agent`, `frontend`, `postgres`, `browser` выбирают нужную границу. PostgreSQL получает `RAZBOR_TEST_DATABASE_URL`; браузер получает только `APP_UI_CREDENTIALS` отдельной тестовой установки. Команды, зависимости и границы покрытия описаны в [руководстве проверок](../docs/development/testing.md).

## Smoke без модели

`smoke.py` создаёт первого владельца, точку, разговор и разбор, добавляет комментарий, проверяет отсутствие выдуманных чисел без источника и завершает сеанс. На уже настроенной базе скрипт отказывается выполнять сценарий до изменения данных.

На заранее запущенном новом изолированном развёртывании из корня проекта:

```text
python tools/smoke.py
```

По умолчанию используется `http://localhost:8000` и `.runtime/compose.env`. Другой адрес задаётся `--url`, секреты — `--env-file`. Сценарий проверяет HTTP и собранный интерфейс, но не запускает модель и не оценивает SQL-генерацию.

Созданный аккаунт и тестовые записи остаются в БД. Поэтому повторный smoke против той же базы откажется выполнять первоначальную настройку. Он предназначен для отдельного одноразового экземпляра, а не для периодической проверки рабочей команды.

Другой `--env-file` сам по себе не изолирует Compose: `run.py` определяет имя проекта по пути корня репозитория. Запуск `run.py --without-ai` в рабочей копии остановит её worker. Для отдельной проверки нужны отдельные контейнеры, тома и порт; отдельная копия каталога даёт другое имя Compose-проекта, но свободный порт всё равно выбирается отдельно. `run.py --stop` останавливает контейнеры, сохраняя данные. Подготовка окружения описана в [руководстве по тестированию](../docs/development/testing.md).

## Полный расчёт с моделью

`acceptance.py` подключает контрольный PostgreSQL-источник, задаёт показатель, сверяет штатный обзор, отправляет русский вопрос в worker и сравнивает результат с известными значениями. Затем сохраняет отчёт и пересчитывает SQL, проверяя неизменность исходного снимка. Встроенный контрольный источник содержит недоступную точку и закрытое поле, которые не должны появиться в ответе. Этот сценарий не создаёт планы и не проверяет выполнение плана.

```text
python tools/acceptance.py
```

Команда предназначена для изолированного экземпляра на loopback-адресе с уже готовой моделью. По умолчанию она создаёт первый аккаунт и тестовый источник в Compose. В тестовом YAML хост `db` должен входить в `application.source_hosts`. Существующий экземпляр требует явно переданного `--credentials` с учётными данными тестового аккаунта; сценарий использует первое пространство этого аккаунта. `--source-manifest` позволяет использовать отдельно подготовленный источник; `--url` и `--env-file` выбирают приложение и его окружение.

Созданные источники, показатели, разговоры и отчёты сохраняются. Встроенная фикстура также оставляет БД `acceptance_*` и роль `acceptance_reader_*`; автоматической очистки нет, в том числе при незавершённой проверке. Полный сценарий проводят на отдельном одноразовом экземпляре. Демонстрационные базы для него не используются.

Приватные JSON/env-файлы не добавляют в Git. Скрипт изменяет тестовые данные и не предназначен для проверки на реальном пространстве команды. В [CI](../.github/workflows/verify.yml) этот сценарий относится к отдельной задаче `real-ai`.

## Резервирование

`backup.py` создаёт архив из dump прикладной БД, YAML и ключа приложения. Восстановление проверяет целостность, создаёт отдельную новую БД, применяет миграции и завершает восстановленные незаконченные задачи. Пользовательские сессии в копии отзываются; текущая БД не перезаписывается.

```text
python tools/backup.py create .runtime/backups/razbor.zip
python tools/backup.py restore .runtime/backups/razbor.zip --database razbor_recovered --output-env .runtime/recovered.env
```

Архив содержит ключ для расшифровки подключений и требует закрытого хранения. В Compose утилиты PostgreSQL выполняются внутри `db`. Для нативного PostgreSQL параметр `--pg-bin` указывает каталог `pg_dump`, `pg_restore` и `psql`; Windows-суффикс `.exe` выбирается автоматически. Параметры `--env-file` и `--pg-bin` передаются перед действием `create`/`restore`.

Порядок подготовки, проверки и переключения на восстановленную базу — в [руководстве резервного копирования](../docs/operations/backup.md). Состав контейнеров описан в [Docker](../docs/operations/docker.md); предметные проверки — в [tests](../tests/README.md).

# Подготовка и запуск приложения

Первый запуск должен приводить к тому же рабочему состоянию, что и повторный: приложение получает базу, выбранную модель и необходимые файлы поиска. Пользователю не приходится вручную раскладывать веса или запускать несколько процессов. Эту последовательность задаёт [run.py](../run.py); модуль `runtime` выполняет подготовку внутри контейнеров.

Подготовка отделена от работающего приложения. API обслуживает вход, историю, отчёты и обсуждения независимо от загрузки модели. Worker получает уже проверенные локальные файлы и выполняет генерацию без обращения к Hugging Face. [Backend](../backend/README.md) владеет пользователями и заданиями; [SQL-пакет](../packages/sql_agent/README.md) получает явные настройки и ничего не скачивает при импорте.

## Как собирается рабочее окружение

[config.py](config.py) читает общий [YAML](../config.yaml), проверяет каталог и объединяет параметры генерации с настройками выбранного профиля. Все три профиля используют Qwen3.5: 4B и 9B в Q5_K_M, 27B в Q3_K_M. По умолчанию выбран 9B. Размеры в каталоге относятся к файлам, а не ко всей занятой оперативной памяти.

[models.py](models.py) загружает только выбранный GGUF и два вспомогательных набора. Для каждого файла закреплены версия репозитория и контрольная сумма. Успешная проверка сохраняется атомарно; при повторном запуске неизменившиеся файлы используются с диска. Смена модели не удаляет ранее скачанные веса. Три файла на диске не означают три модели в памяти.

[database.py](database.py) создаёт отдельную базу `razbor` и обычную роль приложения. Административный пароль используется только при подготовке PostgreSQL. API и worker его не получают. Существующая база старого SQL-приложения сохраняется в том же томе; она не становится источником SaaS автоматически.

После подготовки роли launcher запускает миграции, API с собранным React-клиентом, проверку моделей и worker. Сначала проверяется новая конфигурация и собираются образы, затем останавливается старый worker. Адрес интерфейса и код первой настройки выводятся сразу после готовности API: браузер можно открыть, пока ещё подготавливается модель. Сбой загрузки не уничтожает скачанные файлы или данные. Работающий API позволяет открыть сохранённые материалы, пока генерация недоступна.

## Команды

Из корня проекта, с Python 3.11+ и работающим Docker Compose v2:

```text
python run.py
python run.py --model qwen3.5-4b
python run.py --model qwen3.5-27b
python run.py --list-models
python run.py --without-ai
python run.py --stop
```

В Linux команда может называться `python3`. Флаги одинаковы. `--without-ai` запускает интерфейс и backend без скачивания весов и старта worker. Это полезно для настройки команды и проверки приложения; ответы ассистента требуют обычного запуска с моделью.

Секреты создаются в `.runtime/compose.env` и сохраняются между запусками. Код первоначальной настройки показывается в терминале и нужен для первого администратора. Каталог `.runtime`, веса и локальные данные исключены из Git. `--stop` сохраняет именованные тома и файлы моделей.

Разрешённые адреса внешних источников, параметры cookie и лимиты находятся в YAML. Пустой `application.source_hosts` запрещает подключения: оператор явно добавляет адрес отчётного PostgreSQL перед настройкой источника. Пароли источников вводятся через приложение и хранятся зашифрованными; в YAML их нет.

Локальная проверка запускающего скрипта выполняется в [tests/test_startup.py](../tests/test_startup.py). Она проверяет порядок действий, сохранность секретов и обработку сбоев с подменёнными внешними командами. Для подтверждения контейнерной сборки нужен отдельный Docker-прогон; наличие тестов скрипта его не заменяет.
